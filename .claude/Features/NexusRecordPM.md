## NexusRecord


Pommora answers *where is this now*; the record answers *where was this then*. It has two halves: **Provenance**, a JSON written into every bundle in `.trash` or an Archive that says where a departed entity belonged and what it carried, and **Baseline**, a per-machine projection of what the last open saw, kept in `nexus.db`. Both join on ids — a rename rots a name, an id survives it — with titles riding along as labels. The code is `Core/Bundles/` for the bundle, its record, its placement, and its restore, `Core/Nexus/remintLedger.ts` for the baseline, and `Core/Nexus/remint.ts` for duplicate ids.

### Provenance

Every delete to the Nexus's own trash and every archive produces a bundle: a folder in `.trash`, or in `.nexus/archive/<Collection ID>` for an archived page or Set, under the folder chain the entity came from and named for a stamped copy of its own leaf, holding the artifact under its original name beside a `_record.json`. The record travels with what it describes, so a hand-move of the bundle moves the two as one unit.

**The Bundle.** Each record carries the entity's parent as one of four references — the Nexus root, a container by sidecar id, a Context by registry id, or `unaddressable` when the parent can't be resolved — and a payload by kind. A Context carries its registry entry and its own Space order, plus the membership map its stripped key held, per swept root; a Space carries the roots that tagged it; Pages and ordinary containers carry parent and identity and the ids of the containers above the parent (`trail`), plus each Link value their delete stripped from a page or Space outside them, keyed by that holder's id and the property's; every record but a property's carries the siblings it sat between in its origin's order (`place`), a Context's in the registry's order and again in the Property Panel's (`panel`); a global property delete has no artifact, and its bundle holds the record alone — the definition, the Collections that assigned it, and every value keyed by its holder's id.

**Write-Ahead.** The record is written before the destruction it describes. The bundle is minted while the artifact is still live, the record lands inside it before any sweep, and the artifact moves before the configuration pass, so a delete cut short leaves evidence rather than silence: a bundle holding no artifact is a deletion that never finished, skipped by the listing and never removed. A Space or Context delete strips its keys from every member file once its folder has moved; a member it can't write stays owed with Try Again, and the delete stands. A record thinner than the truth, such as one past a member file it couldn't parse, says so with a `partial` flag. A page, Set, or Collection delete strips the Link values naming a page it took, from the tree or an Archive, by the rule [[ConnectionsPM]] states, from the pages and Spaces outside it, both stores' pages included, once its artifact has moved, in one sweep over the files the index relates to those titles and the Spaces the tree and the Trash hold naming them, its record holding each value the sweep takes from before it runs, read as a Space's or Context's capture reads its holders; a file it can't write, or a linker whose ID another file shares, stays owed with Try Again, and the delete stands.

**Restore.** The resolver takes a record and the current tree and returns a placement — directory, final name, and for a Space or Context the final title — or a typed refusal: parent gone, parent can't hold this kind, parent unaddressable, id already live. A page or Set moved out of either store by hand finishes as that store's restore where it landed, found by the id its bundle's record holds; a Space moved back into its registered Context's folder finishes the same way, tagging its members again, and one moved back while the app was closed finishes at the next open, unless its delete still owes a strip, which finishes the delete instead; a Context moved back stays outside the registry until restored; a copy, which leaves the bundle whole, stays a page of its own, and after an index rebuild nothing pairs, so such a page returns current without its delete's Link values. A live id outranks every other answer. Final titles are the resolver's rather than the recorded ones, since a freed title may have been re-minted while the original sat in trash, so a collision disambiguates for every kind, stepping aside past what the tree or the disk holds there, and a page, Set, Collection, or Space lands back between the siblings it left. An artifact returns from either store by a move, current since every cascade reached it; once it lands, its own links re-spell to the pages beside it they named, the live world is re-spelled for its arrival and for the names that named only it, and the stripped values come back to the page each named, through the one rule the rename cascade uses. A Context re-enters the registry between the neighbors it left before its folder moves, so a refused move rolls the entry back, and once it lands returns to its place in the Property Panel's order with its own Space order; membership re-applies by id against the as-restored folder names, and the restore names any page still present that didn't take its tag back. While **Restore Links On Deletion** is on, a page, Set, or Collection restore writes each Link value its delete stripped back onto the page or Space it came from, by the property's id and rebuilt under the landed title when the page stepped aside, wherever that holder has none — in the Trash as live — the restore naming any still present that didn't; a property no longer defined as a Link is left out. A property restores by rebuilding — the definition re-enters the registry, each Collection gets it back, the values a Remove had stashed return to their Collection's stash, and each value is written home where it still validates and its page or Space holds none of its own, the restore naming any that didn't, while a Link value naming a page gone is left out — and refuses outright if its recorded definition no longer parses; a label or key another property has since taken steps aside as a create's would.

**The Trash Frame.** The record's principal reading half is the Trash frame of the Settings window, listing every bundle `.trash` holds, one row per deleted entity across the five artifact-bearing kinds, and one per deleted property under its definition's label. A Set's or Collection's row opens onto the pages and Sets inside it, each restored or given up on its own, which leaves the rest of its bundle in place. Main shapes each row — kind and title from the artifact, the deletion time from the bundle's stamp, a breadcrumb resolved live from the recorded parent id, and whether that parent still resolves — and the list is fetched when the leaf opens, when another Nexus opens, and after every delete, restore, or empty the app makes. A row's right-click restores it or gives it up: **Restore** returns the entity to the tree, or, where its recorded home no longer resolves, opens into the live places that kind may land; **Delete** hands the artifact to the operating system's trash, or erases it when **Permanently Delete Files** is on, and removes the spent bundle; a Collection given up takes its Archive with it; a page, Set, or Collection given up strips the Link values still naming its pages by the rule [[ConnectionsPM]] states, and hands the values its record kept to a namesake still in the Trash. Checked rows act together, and a batch names what it couldn't resolve. A deletion's own notification reads the record too: the delete answers the Undo that restores the bundle it minted, which **Undo** sends without the frame being opened. A property delete that couldn't update every file offers **Try Again** there instead, which finishes the update, and leaves Undo to the undo chord.

### Baseline

The open path reads the Nexus once the database opens and before the watcher starts, stamping what the read lists as missing an ID and reading again while a stamp lands, seeds the session with that tree, and hands it to the ledger, which latches what it saw as the baseline — a record per entity of id, kind, title, and path — over the previous one; an open waiting on a damaged hand-authored file runs none until it opens. An entity the read lists as unreadable (a corrupt sidecar, an Unknown page) keeps its previous record rather than dropping out as a deletion. A mid-session re-point leaves the baseline alone, since the watcher owns live-session attribution, and a re-mint's writes land as file events against the tree the session holds.

The baseline is also what settles a duplicated id. At the next open, the path the prior baseline recorded for an id is the original, and every other claimant takes a fresh id along with its metadata entry and copies of the device-local rows keyed to the old one — folds, heading columns, preview sets, a container's saved-view ids, a Space's block document. With no prior evidence, the eldest claimant by birth time is recorded and the following open adjudicates. Disk writes land first and row copies second, so a refused write leaves the duplicate deferred rather than half-minted.

#### Known Issues

- **The baseline pass is best-effort end to end** — a failed walk or row write retains the prior record, and the open proceeds.

#### Pending

- **A compare view** — reading a bundle's content against what stands in its place now.
- **Crash-safe moves and link renames** — the write→act→settle shape applied to the move cascade and the `[[link]]` rename cascade, whose relink entry is noted once the move has landed.
- **Change capture** — property and frontmatter changes as event payloads; the record shape widens additively.
- **Git as an opt-in second history provider** — a second store module beside `versions.db`, complementary to the record; Pommora never auto-commits.
