#### Findings

S-1. **High · The Range Reach Walks Back Once Per Line:** `Input/format.ts:336-339`, the range branch of `listReach`, calls `itemOf(k)` on every non-blank line it covers. `itemOf` (`:312-319`) walks upward over every non-blank, non-item line until it hits a blank line or an item, then runs `subBlockAt` forward again. A long run of non-blank, non-item lines (a code block, a table, hard-wrapped prose) costs O(N²). That path runs on every right-click with a selection (`readFormatState → listKindOf → listReach`, `menu.ts:47`, `cellStatic.tsx:528`) and again on the pick (`setList`). At base, `readFormatState` read only the first line's marker, so the cost is new. Measured on select-all with `listKindOf`: 1,000, 2,000, and 4,000 lines of prose took 19, 73, and 290 ms; a fenced block of the same sizes took 15, 57, and 499 ms; a 4,000-item list took 1.6 ms. **Smaller-cost shape:** resolve the owner once at `anchor`, then carry it forward, so each item's branch end is computed once:
    ```ts
    const endOf = (j: number | null): number => (j === null ? -1 : subBlockAt(scan, scan.lineStarts[j], scope)!.to)
    let owner = itemOf(anchor)
    let end = endOf(owner)
    for (let k = anchor; k <= lineIndexAt(scan, to); k++) {
      if (k !== owner && markerAt(k) !== null) end = endOf((owner = k))
      if (!isBlank(splitPrefix(scan.lines[k], scope).body))
        reached.add(owner !== null && scan.lineStarts[k] <= end ? owner : k)
    }
    ```
    `itemOf` then serves only the anchor, in both branches. **Line effect:** about +6 (+8 / −2), net-positive, which the fix to the Hard Rules' lag case justifies. Task 2-1's VERIFY could carry one line timing `listKindOf` over a 4,000-line selection, beside Task 1-2's rail-pass line. **Verified:** with the shape applied, the same probes read 1.2 ms (prose) and 0.9 ms (code) at 4,000 lines, and the full MarkdownPM suite was run four times. With the shape applied, the first run failed 8 tests in 2 files, and those weren't inspected. The second run, also with the shape applied, listed only `embedAbsorb`'s fence case failing at 5,122 ms, which passed on a targeted rerun. The untouched final tree passed 1,991 of 1,991, and so did a fourth run with the shape re-applied. Load flake is the likely cause of the early failures, but that's inferred. **Inferred:** that the forward pass and `itemOf` pick the same owner on every shape. By reading, both find the nearest item above whose `subBlockAt` branch covers the line, and a blank line ends both, but this was only checked through the suite.
