## Mobile Companion & Pommora Sync — Research

Outward research gathered 09-04-2026 for the [[Mobile Companion & Pommora Sync — Decision Log]]: sixteen questions, each answered by one researcher reading the cited sources, with the load-bearing claims re-checked by one skeptic per scope. Each section carries the claims, their sources, the researcher's verdict, and what stayed unresolved. The decision log records what the design took from it.

### Sync And Encryption

#### Joplin E2EE

- MASTER KEY GENERATION. A Joplin master (data) key is 256 CSPRNG bytes rendered as a 512-char hex string; its ID is a dashless UUIDv4 (32 hex chars) assigned on save, with created_time/updated_time/source_application/hasBeenUsed=false. The key is never derived from the password. Borrow: one random DEK per vault with a stable id, not a password-derived vault key. (https://raw.githubusercontent.com/laurent22/joplin/dev/packages/lib/services/e2ee/EncryptionService.ts)
- PASSWORD WRAPPING (KeyV1, method id 8). The password never touches item data; it wraps the master key: PBKDF2-SHA512 at 220,000 iterations -> 32-byte AES-256-GCM key, fresh random 12-byte IV, 16-byte tag, empty AAD, salt = SHA-256 of the service's 36-byte nonce state. Stored as `{encryption_method: 8, content: JSON{salt,iv,ct} base64, checksum: ''}` -- no checksum because the GCM tag already rejects a bad unwrap. Borrow the layout: a PBKDF2-derived KEK wraps a random DEK. (https://raw.githubusercontent.com/laurent22/joplin/dev/packages/lib/services/e2ee/EncryptionService.ts)
- WEB CRYPTO SEAM. Joplin's Node crypto provider is pure Web Crypto: importKey('raw', password, PBKDF2) -> deriveKey to a non-extractable AES-GCM CryptoKey -> subtle.encrypt/decrypt with additionalData + tagLength, 12-byte IV from getRandomValues, wire shape `{salt, iv, ct}` base64. Mobile implements the same `Crypto` interface with react-native-quick-crypto. Borrow the Node file nearly verbatim: because Node 24 and WKWebView both expose `crypto.subtle`, Pommora can ship one implementation behind one interface instead of Joplin's two. (https://raw.githubusercontent.com/laurent22/joplin/dev/packages/lib/services/e2ee/crypto.ts)
- PER-ITEM FORMAT: HEADER + METHOD IDS + CHUNK FRAMING. Every ciphertext is ASCII: `JED` + 2-hex version (`01`) + 6-hex metadata length + 2-hex method id + 32-hex master-key id, then chunks each framed as 6-hex length + data; header fields are a per-version template. Defaults: StringV1 (id 10, 64 KiB chunks, utf16le) for items, FileV1 (id 9, 128 KiB chunks, base64-decoded first) for resources; ids 1-7 are legacy SJCL. Borrow the self-describing versioned header (method + key id) so every blob decrypts on its own; avoid the hex/JSON/base64/utf16le layering -- Pommora should emit a compact binary header + raw AES-GCM bytes. (https://raw.githubusercontent.com/laurent22/joplin/dev/packages/lib/services/e2ee/EncryptionService.ts)
- PER-CHUNK KEY DERIVATION (Joplin's nonce-reuse defence). The master key is not used directly as the AES key: each chunk runs PBKDF2-SHA512 with only 3 iterations over the 512-hex master key, salted with SHA-256 of a 36-byte nonce state (random || 7-byte timestamp || 8-byte counter, counter bumped after every chunk), plus a fresh random 12-byte IV and empty AAD; each chunk is its own JSON {salt, iv, ct}. The comment calls the salt '256 bits random' but it is a hashed counter state, and increaseNonce fires only in the chunk loop. Avoid PBKDF2(3)-as-KDF; if Pommora wants a per-item subkey, HKDF-SHA256(DEK, random salt, info=item id) is the Web Crypto-native equivalent -- otherwise one DEK with a random 96-bit IV per whole-file blob is simpler. (https://raw.githubusercontent.com/laurent22/joplin/dev/packages/lib/services/e2ee/EncryptionService.ts)
- EMPTY AAD -- THE CLEAREST 'AVOID'. Every V1 method passes an empty additionalData, so the JED header (version, method id, key id) and the chunk framing are bound to no GCM tag. Concrete failure: FileV1 and StringV1 share identical PBKDF2/GCM parameters and differ only in the plaintext encoding argument ('base64' vs 'utf16le'), so flipping the header's method id 9<->10 decrypts cleanly to mis-encoded garbage with no error. Pommora should put protocol version, key id, item id (path HMAC) and mtime into `additionalData` so the server or a peer cannot relabel, move, or re-time a blob undetected. (https://raw.githubusercontent.com/laurent22/joplin/dev/packages/lib/services/e2ee/EncryptionService.ts)
- OUTER SYNC ENVELOPE. Encryption happens only at sync serialisation; the record on the sync target is a plaintext skeleton -- id, note_id, tag_id, parent_id, share_id, updated_time, deleted_time, type_, is_locked, extracted_resource_ids -- plus `encryption_applied=1` and the JED blob in `encryption_cipher_text`; on decrypt `updated_time` is copied from the outer record and decryption is not a change. Direct tension with Pommora's provisional envelope, which hides `mtime` inside the ciphertext: a server that cannot read mtime cannot arbitrate most-recent-wins, only clients can. Borrow: item id and mtime in the plaintext record (and bound via AAD); path and content inside the ciphertext. (https://raw.githubusercontent.com/laurent22/joplin/dev/packages/lib/models/BaseItem.ts)
- WRONG-PASSWORD DETECTION. KeyV1 keys carry no verifier field: `checkMasterKeyPassword` attempts the unwrap and returns false on any throw -- the AES-GCM tag on the wrapped key IS the verifier (only legacy SJCL2 kept a sha256 checksum of the plaintext). `masterPasswordIsValid` prefers unwrapping the PPK private key, then the default master key, and only when nothing is wrapped yet compares against the locally stored password. Borrow: Pommora's separate 'key verifier' in the vault info record is redundant once the DEK is AES-GCM-wrapped; a failed unwrap is the signal, at one PBKDF2 per attempt. (https://raw.githubusercontent.com/laurent22/joplin/dev/packages/lib/services/e2ee/EncryptionService.ts)
- KEY ROTATION. Three paths, none re-encrypts content. (a) Password change: every master key and the PPK private key are unwrapped with the old password and re-wrapped with the new one; items untouched. (b) Forgotten password = reset: every enabled key gets `enabled = 0`, the old PPK is archived, a new PPK and a fresh master key are generated; old content is permanently unreadable. (c) Wrapping-algorithm upgrade: `reencryptMasterKey(mk, password, password)` re-wraps in place under the current default method; `masterKeysThatNeedUpgrading` flags keys whose method is neither KeyV1 nor Custom (PPK-wrapped). Because each item's header names its key id, retired keys stay in the registry forever. Borrow (a) and (c) -- they are the payoff of the DEK-wrapped-by-KEK layout; Pommora's whole-file model could also support a true DEK rotation by re-uploading every item, which Joplin never does. (https://raw.githubusercontent.com/laurent22/joplin/dev/packages/lib/services/e2ee/utils.ts)
- KEY REGISTRY = info.json ON THE SYNC TARGET, MERGED CLIENT-SIDE. Wrapped master keys (content, method, timestamps, enabled, hasBeenUsed) ride in `info.json` with `version`, `e2ee {value, updatedTime}`, `activeMasterKeyId`, `ppk`, `appMinVersion`. Every sync fetches it, merges local vs remote (newest per-field timestamp; per-key newest updated_time; active-key tie-break: enabled beats disabled, then hasBeenUsed beats unused), and re-uploads under an exclusive lock. Multiple master keys exist precisely because two offline clients can each enable E2EE; the PPK avoids that by being generated only during sync and only if info.json lacks one. Borrow the info-record idea (Pommora's provisional vault info already matches) but let the server enforce create-once and refuse a stale base version, which makes the multi-key + hasBeenUsed merge machinery unnecessary. (https://raw.githubusercontent.com/laurent22/joplin/dev/packages/lib/services/synchronizer/syncInfoUtils.ts)

**Verdict:** Borrow the layout (random DEK wrapped by a PBKDF2 KEK -- the GCM tag on the wrapped DEK is the password verifier, drop the separate verifier; Web Crypto deriveKey -> non-extractable AES-GCM key; a versioned header naming method + key id; item id and mtime in the plaintext record so the server can arbitrate) and avoid the rest (empty AAD, PBKDF2(3) as a per-chunk KDF, hex/JSON/base64/utf16le ASCII bloat, and the multi-master-key + hasBeenUsed merge, which a server-enforced create-once vault info record makes unnecessary).

**Unresolved:** The three flowchart PNGs referenced by workflow.md (e2ee-setup, e2ee-sync, e2ee-share) were not read; the setup/sync sequence above is reconstructed from Synchronizer.ts and utils.ts, not the diagrams. Joplin Server's own handling of info.json/master keys beyond the client's FileApi put('info.json')/get('info.json') was not fetched. Whether encryptionNonce_ is deliberately left un-advanced after a KeyV1 master-key wrap (increaseNonce is only called in the chunk loop; the fresh random IV keeps it safe regardless) was not confirmed against any author statement. The ppk/webCrypto directory and RSA providers were not read; PPK/sharing is outside Pommora's scope.

#### Standard Notes Sync And 004

- Item addressing: a single Item model with a client-chosen uuid as the only identity, an opaque encrypted `content` string, a plaintext `content_type`, a per-item encrypted key `enc_item_key`, a `deleted` flag, and a microsecond `updated_at_timestamp` that the server (not the client) assigns; inter-item relationships live inside the encrypted content as `references`, invisible to the server. Pommora: the HMAC(pathKey, path) item id plays the same role as SN's uuid, but note SN's id is content-stable — a rename in Pommora changes the id, which is a rename-is-delete+create decision to make explicitly. (https://raw.githubusercontent.com/standardnotes/docs/main/docs/specification/sync.md)
- The sync cursor is a server-minted timestamp, not a change-log sequence: `sync_token` is base64 of `"2:<seconds>"` computed on the save side as max(saved item `updatedAt`) + 1 µs; `GetItems` decodes it back to microseconds and queries `updated_at_timestamp > lastSyncTime` (`>=` when following a `cursor_token`), and the first sync (no token) excludes tombstones while every later sync includes them (`deleted: lastSyncTime ? undefined : false`). Pommora: avoid the timestamp token — a write landing between this request's GET and its SAVE with a timestamp below the freshly minted token is never delivered; keep the planned monotonic change log instead. Borrow the version prefix on the token, the sync_token/cursor_token split, and the tombstone rule (first pull skips tombstones, incremental pulls carry them). (https://raw.githubusercontent.com/standardnotes/server/main/packages/syncing-server/src/Domain/UseCase/Syncing/SaveItems/SaveItems.ts)
- Pagination: when the page limit (default 150, capped by a server max) or a content-size transfer limit is hit, the server returns a `cursor_token` encoding the last delivered item's `updated_at_timestamp`; the client sends it back and the next page uses `>=`, so the boundary item can be re-delivered and clients must apply idempotently. Pommora: borrow the pattern (cursor = position in the ordered stream, limit + byte budget), but with a change-log sequence the cursor becomes an exact `>` on the sequence and the re-delivery wrinkle disappears. (https://raw.githubusercontent.com/standardnotes/server/main/packages/syncing-server/src/Domain/UseCase/Syncing/GetItems/GetItems.ts)
- Server-side conflict detection is optimistic concurrency on the server-assigned timestamp: a save of an existing item passes only if the incoming `updated_at_timestamp` equals the server's exactly (a 1 ms / 1 s tolerance exists only for legacy clients without microsecond precision); otherwise the write is refused and returned as a `sync_conflict` carrying `server_item`, and `SyncItems` strips that same item out of `retrieved_items` so the client sees it once, in the conflict slot. Pommora: this is exactly the "store carries a base version and is refused when stale" rule already planned — borrow returning the current server copy alongside the refusal so the client needs no second round-trip. (https://raw.githubusercontent.com/standardnotes/server/main/packages/syncing-server/src/Domain/Item/SaveRule/TimeDifferenceFilter.ts)
- Conflicts are surfaced as a typed array, not HTTP errors: each entry is `{ type, server_item?, unsaved_item? }` and the type enum covers data conflicts (`sync_conflict`, returns server_item), identity collisions (`uuid_conflict`, returned when the uuid belongs to another user — resolved by the client minting a new uuid and re-syncing), and validation rejections (`content_type_error`, `content_error`, `readonly_error`, `uuid_error`, plus shared-vault errors), each returning the unsaved item. Pommora: borrow the per-item typed conflict envelope inside a 200 response — a batch store never fails wholesale because one item is stale. (https://raw.githubusercontent.com/standardnotes/app/main/packages/responses/src/Domain/Item/ConflictType.ts)
- Resolution is two-stage — server rejects, client decides — and the client's default outcome is a conflict copy, not a silent winner. `GenericItem.strategyWhenConflictingWithItem` takes the server version when content is identical (KeepApply), keeps the local edit and re-pushes when the local base matched the server's previous revision (KeepBase), and otherwise duplicates one side: the incoming copy if the user edited locally within the last 20 s, else the local copy (`KeepBaseDuplicateApply` vs `DuplicateBaseKeepApply`). `PayloadsByDuplicating` mints a new uuid, sets `duplicate_of` on the item and `conflict_of` inside the encrypted content, and rewrites referencing items. `DeltaRemoteRetrieved` routes a retrieved item that is locally dirty through the same `ConflictDelta`, so copies arise on the pull side too. Pommora: most-recent-wins by mtime is a legitimate simplification, but borrow the copy-on-genuine-divergence fallback (`Page (conflict).md` style) at minimum for the case where both sides changed content — SN's identical-content and matched-previous-revision short-circuits are cheap and remove most spurious copies. (https://raw.githubusercontent.com/standardnotes/app/main/packages/models/src/Domain/Abstract/Item/Implementations/GenericItem.ts)
- `saved_items` is an acknowledgement channel, not a data channel: the client merges only the server's returned timestamps into its local copy and never overwrites local content from it; the `ServerSyncSavedContextualPayload` type has no `content` field at all. Pommora: borrow this shape for the store response — return `{id, version/sequence}` per accepted item and nothing else, so an ack can never clobber an edit made while the request was in flight. (https://raw.githubusercontent.com/standardnotes/app/main/packages/models/src/Domain/Abstract/Contextual/ServerSyncSaved.ts)
- Deletion is a tombstone: the client sets `deleted: true` and syncs; on receipt the server keeps the row, nulls `content`, `enc_item_key`, `auth_hash`, and `items_key_id`, zeroes `content_size`, and stamps a fresh server `updated_at_timestamp` so the tombstone flows through every other device's next incremental pull; peers remove the item locally immediately on receiving a deleted item. Pommora: borrow verbatim — a tombstone is a change-log entry with the blob stripped, and the server holds no ciphertext for deleted items. (https://raw.githubusercontent.com/standardnotes/server/main/packages/syncing-server/src/Domain/UseCase/Syncing/UpdateExistingItem/UpdateExistingItem.ts)
- 004 key hierarchy: password → Argon2id (64 MiB, 5 iterations, salt = SHA256(identifier:seed)[0:32]) → 512-bit key split into `masterKey` (never leaves the device) and `serverPassword` (the login credential); a random 256-bit `itemsKey` is encrypted with the masterKey and synced as an ordinary item; each item gets its own random `item_key` which encrypts `content`, and the `item_key` is wrapped by the itemsKey as `enc_item_key` with `items_key_id` naming which itemsKey to use. One itemsKey per protocol version; a password change or protocol upgrade re-encrypts only the itemsKeys, and old data is re-encrypted progressively as it is touched. Pommora: this is the single most valuable borrow — the provisional design derives the vault key straight from the password via PBKDF2 and uses it on every blob, so a password change means re-encrypting the whole vault; instead put a random content key in the vault `info` record wrapped by the password-derived key, and split the derived key so the half sent to the server for auth is never the half that decrypts. (https://raw.githubusercontent.com/standardnotes/app/main/packages/snjs/specification.md)
- How 004 versions and binds each ciphertext: every encrypted string is colon-joined `['004', nonce, ciphertext, encoded_authenticated_data]` (the shipping code appends a fifth `additionalData` segment), XChaCha20-Poly1305 with a 192-bit nonce, and the AEAD associated data is base64 of key-sorted JSON `{u: item.uuid, v: '004'}` (plus `kp` root-key params when the payload is an itemsKey). The protocol version is read from the first three characters of the string (`ProtocolVersionFromEncryptedString`), versions carry hard expiry dates, and "strict sign in" lets a client refuse a server that reports a lower version. Pommora: Web Crypto AES-GCM takes `additionalData` in both Node 24 and WKWebView, so bind `{itemId, protocolVersion}` into the GCM tag for free — the server can then neither swap ciphertext between item ids nor downgrade a version — and prefix every blob (and the sync token) with a version segment rather than relying on the vault `info` record alone. (https://raw.githubusercontent.com/standardnotes/app/main/packages/encryption/src/Domain/Operator/004/UseCase/Symmetric/GenerateEncryptedProtocolString.ts)

**Verdict:** Borrow the key hierarchy (random content key wrapped by the password-derived key, split derived key, per-item key + key id, version-prefixed blobs with id+version in the AEAD tag), the per-item typed conflict envelope with server_item returned on refusal, timestamps-only save acks, and tombstones-with-nulled-blob; avoid the timestamp-valued sync_token (Pommora's monotonic change log is strictly better) and treat SN's conflict-copy fallback as the safety net under most-recent-wins for genuine two-sided divergence.

**Unresolved:** (1) Spec vs code drift: specification.md documents four colon-joined components while the shipping encoder emits five (`additionalData` in `V004StringComponents`); the code is authoritative for current clients, but I did not trace what `additionalData` holds for regular items. (2) Whether the client dedupes the `>=` boundary item re-delivered on cursor pages — `DeltaRemoteRetrieved` was read but page-boundary handling in `SyncService.ts` was not. (3) `DeltaRemoteUuidConflicts` (client handling of `uuid_conflict`) was not read; only the spec's "change the UUID and re-sync" instruction is cited. (4) `compute_integrity` / `integrity_hash` (the optional whole-account checksum) was not investigated. (5) Standard Notes' `sync.md` in the docs repo carries no last-updated marker, and the docs-repo 004 page says it is a copy of a `standardnotes/snjs` file I did not fetch; both mirrors I read (docs repo and app repo) match on every section I compared, but I cannot state the docs page's currency independently.

#### Obsidian Sync Encryption

- Obsidian Sync encrypts file PATHS/names end-to-end, not just content, and does so deterministically so the server can key on a stable opaque name per path. Pommora's HMAC-SHA256(pathKey, path) item id gives the server the same property (one stable identifier per path) and is fine to keep. (https://obsidian.md/changelog/2025-08-22-sync/)
- Sync v0 encrypted paths with AES-GCM using an IV derived from a hash of the path string (a deterministic-GCM pattern they later called exploitable); v3 switched paths and hashes to AES-SIV while content stayed AES-GCM. Obsidian's path ciphertext is reversible (a client can decrypt the server's name list without pulling content), whereas an HMAC id is one-way. Pommora should not adopt AES-SIV (absent from SubtleCrypto, so WKWebView can't run it); if remote listing without content download is ever needed (selective sync, showing what a tombstone removed), keep the HMAC id and store a separately AES-GCM-encrypted path field with a random IV beside it. (https://obsidian.md/changelog/2025-08-22-sync/)
- Obsidian documents that there is NO cryptographic binding between encrypted path and encrypted content: the path-to-content mapping, uploading device, and upload time are server-readable plaintext, and a compromised server could serve one file's ciphertext under another path. Pommora's envelope {path, mtime, content} already beats this, provided the client checks HMAC(pathKey, envelope.path) === item.id on every decrypt; the stronger form is passing the item id plus protocol version as AES-GCM additionalData so the binding is enforced by the tag itself. (The Limitations section was added in the commit "Add limitations section" dated 2025-11-11 per https://api.github.com/repos/obsidianmd/obsidian-help/commits?path=en/Obsidian%20Sync/Security%20and%20privacy.md&per_page=15.) (https://raw.githubusercontent.com/obsidianmd/obsidian-help/master/en/Obsidian%20Sync/Security%20and%20privacy.md)
- Obsidian encrypts content hashes deterministically for server-side dedup and documents the resulting file-confirmation attack. Pommora has no dedup need at personal-vault scale; skip content-hash dedup entirely rather than inherit the tradeoff. (https://raw.githubusercontent.com/obsidianmd/obsidian-help/master/en/Obsidian%20Sync/Security%20and%20privacy.md)
- The exact client crypto: password and salt are NFKC-normalized, scrypt(N=32768, r=8, p=1) yields a 32-byte base key, v3 then runs HKDF-SHA256 (empty salt, info 'ObsidianAesGcm') to get the AES key, and each blob is IV(12) || AES-256-GCM ciphertext || tag(16) containing one file revision. Pommora should keep PBKDF2 (scrypt is node:crypto-only; SubtleCrypto in both Node 24 and WKWebView has PBKDF2 and HKDF) but borrow the shape: NFKC-normalize the password before the KDF (an iOS keyboard and a Mac keyboard can emit different codepoints for the same visible password), then HKDF the base key into per-purpose subkeys with distinct info strings (contentKey, pathKey, verifierKey). The IV||ct||tag blob layout is portable as-is since SubtleCrypto emits ct||tag. (https://obsidian.md/blog/verify-obsidian-sync-encryption/)
- The per-vault KDF salt and the encryption version are generated by the app at vault creation, held server-side, and fetched at unlock time from the vault list. This directly validates Pommora's vault 'info' record (protocol version + KDF salt/params): the client fetches it, derives the key locally, and the server never sees the password. (https://obsidian.md/blog/verify-obsidian-sync-encryption/)
- Obsidian documents NO key-verification mechanism. The setup flow is 'enter the encryption password, select Unlock vault', the security page states the password is saved nowhere, and the only verification visible anywhere in the public material is the blog's decrypt routine relying on the AES-GCM tag check failing on a wrong key. Pommora's key-verifier record is therefore its own design, not a borrow; a sound shape is AES-GCM of a fixed literal under an HKDF-derived verifierKey (random IV) stored in the info record, with the client decrypting it at unlock to distinguish 'wrong password' from 'corrupt data' before touching any item. (https://raw.githubusercontent.com/obsidianmd/obsidian-help/master/en/Obsidian%20Sync/Set%20up%20Obsidian%20Sync.md)
- The vault password is separate from the account password, can differ per vault, is unrecoverable, and only the remote vault is encrypted (local stays plaintext). The documented reset path for a lost password is: back up, disconnect every device, create a fresh remote vault from the primary device, wait for full upload, reconnect the rest. Pommora should borrow all of it verbatim: E2E only (skip Obsidian's server-managed 'standard encryption' tier), no server-side recovery, and 'rebuild the remote from one device' as the sole reset procedure. (https://raw.githubusercontent.com/obsidianmd/obsidian-help/master/en/Obsidian%20Sync/Security%20and%20privacy.md)
- Encryption version is a per-vault property (0 since 2020-12-07, 3 since 2025-08-22); upgrading is destructive (remote data deleted and re-uploaded, version history lost) and gated on every device running an app version that supports the target. Pommora should borrow the model: protocol version lives in the info record, a client refuses a vault newer than it speaks, and a protocol bump is 'new vault + re-upload', never an in-place re-encryption. (https://raw.githubusercontent.com/obsidianmd/obsidian-help/master/en/Obsidian%20Sync/Upgrade%20Sync%20encryption.md)
- Obsidian's 'last modified wins' applies ONLY to non-Markdown files; Markdown conflicts are three-way merged with diff-match-patch, settings JSON is key-merged, and since 1.9.7 a per-device 'Create conflict file' option writes 'name (Conflicted copy device YYYYMMDDHHMM).md' instead of merging. Pommora's provisional mtime-wins-for-everything silently discards edits on the exact file type its vault consists of; the cheap borrow is the conflict-file fallback (loser's version saved beside the winner), with diff-match-patch merge as a later option. (https://raw.githubusercontent.com/obsidianmd/obsidian-help/master/en/Obsidian%20Sync/Troubleshoot%20Obsidian%20Sync.md)

**Verdict:** Borrow the structure (per-vault salt + version record fetched at unlock, NFKC-normalized password, HKDF per-purpose subkeys, deterministic opaque path ids, IV||ct||tag GCM blobs, password-separate-from-account with no recovery, destructive versioned migration, conflict-file fallback) but not the primitives (scrypt and AES-SIV are unavailable in SubtleCrypto), and exceed Obsidian on the one gap it admits by binding item id to ciphertext via GCM additionalData.

**Unresolved:** Obsidian publishes no key-verifier mechanism at all, so nothing there can be borrowed or compared; Pommora's verifier is its own. The docs never state that clients enumerate a remote vault by decrypting stored path ciphertexts; reversibility is inferred from AES-SIV being an encryption (not a hash), not from an explicit listing claim. The blog shows only the content subkey (HKDF info 'ObsidianAesGcm'); whether v3 derives a separate key for paths/hashes, what hash function the 'file hashes' use, and the WebSocket wire format beyond 'binary messages' are undocumented. The Limitations section date (11-11-2025) comes from the help repo's commit history; the Trail of Bits Sync audit is listed as December 2025 on obsidian.md/security, so no causal link between them is claimed.

#### Conflict Handling (Obsidian, Syncthing)

- Obsidian Sync resolves conflicts differently by file type: Markdown is three-way merged with Google's diff-match-patch; every other file type (canvases included) is "last modified wins", where the most recently modified version replaces earlier ones. (https://raw.githubusercontent.com/obsidianmd/obsidian-help/master/en/Obsidian%20Sync/Troubleshoot%20Obsidian%20Sync.md)
- Since Obsidian 1.9.7 the user chooses between "Automatically merge" (default; may produce duplicate text or formatting problems the user must fix) and "Create conflict file" (no auto-merge; both versions kept for manual review). The setting is device-specific and must be configured on every device; the Sync-settings page repeats the same warning. (https://raw.githubusercontent.com/obsidianmd/obsidian-help/master/en/Obsidian%20Sync/Troubleshoot%20Obsidian%20Sync.md)
- Obsidian's conflict file is named `original-note-name (Conflicted copy device-name YYYYMMDDHHMM).md`, carries the human-readable device name and a minute-precision timestamp, and holds the changes from the device that detected the conflict, while the original path keeps the REMOTE version. This is remote-wins-with-local-capture, not an mtime comparison. (https://raw.githubusercontent.com/obsidianmd/obsidian-help/master/en/Obsidian%20Sync/Troubleshoot%20Obsidian%20Sync.md)
- Obsidian settings/plugin JSON conflicts are resolved by a key-level merge, applying the local JSON's keys on top of the remote JSON, and conflict events are visible in the Sync log under "Merge Conflicts". (https://raw.githubusercontent.com/obsidianmd/obsidian-help/master/en/Obsidian%20Sync/Troubleshoot%20Obsidian%20Sync.md)
- Obsidian has a documented data-loss edge: a note created locally that receives a remote version of the same path within a couple of minutes is overwritten by the remote copy with no merge and no conflict file; the local version is only recoverable through File recovery. This is the anti-pattern to avoid: a fresh local create must be captured, never silently dropped. (https://raw.githubusercontent.com/obsidianmd/obsidian-help/master/en/Obsidian%20Sync/Troubleshoot%20Obsidian%20Sync.md)
- Syncthing's conflict rule is newest-mtime-wins with loser capture: when the same file is modified on two devices and the content actually differs, the copy with the OLDER modification time is renamed to `<filename>.sync-conflict-<date>-<time>-<modifiedBy>.<ext>` and the newer copy keeps the original path. (https://docs.syncthing.net/users/syncing.html#conflicting-changes)
- Syncthing breaks an equal-mtime tie deterministically using device identity: the copy from the device whose ID has the larger value in its first 63 bits becomes the conflict copy. Pommora needs an equivalent total order (e.g., device ID comparison) so two devices never disagree on the winner. (https://docs.syncthing.net/users/syncing.html#conflicting-changes)
- Syncthing captures the loser even when the winner is a deletion: if a modification conflicts with a delete and the delete wins, the modified file is preserved as a conflict copy rather than discarded. Pommora's tombstones should do the same so an edit beaten by a tombstone still lands in loser capture. (https://docs.syncthing.net/users/syncing.html#conflicting-changes)
- Syncthing deliberately treats conflict copies as ordinary files that propagate to every device, because the conflict is detected on one device but is equally a conflict everywhere and the system cannot know which copy the user considers best. (https://docs.syncthing.net/users/syncing.html#conflicting-changes)
- Syncthing exposes two knobs relevant to an mtime-based rule with loser capture: `maxConflicts` caps conflict copies kept per file (default 10; -1 unlimited; 0 disables capture), and `modTimeWindowS` allows an mtime slack when comparing files on filesystems with unstable timestamps (default 2s on Android FAT, 0 otherwise). Pommora should carry a retention cap and treat mtime equality with a tolerance, not exact-match. (https://docs.syncthing.net/users/config.html)

**Verdict:** Borrow Syncthing's shape (newer mtime wins, older copy captured with device id + timestamp, deterministic device-ID tie-break, edit-beaten-by-tombstone still captured, per-file retention cap, mtime tolerance window) plus Obsidian's human-readable device name in the loser's label; avoid Obsidian's remote-wins race that silently drops a fresh local create and its minute-precision timestamp. Pommora-specific: a loser written as a sibling `.md` would duplicate the original's `ID` key and trip folder/ID validation, so capture losers in the `.trash/` bundle shape (or another non-indexed location) rather than as an adjacent page.

**Unresolved:** The public help URLs (help.obsidian.md/sync/troubleshoot, redirecting to obsidian.md/help/sync/troubleshoot) render client-side and returned a 2.8 KB shell with no article text, so Obsidian citations point at the repo source file that publishes to that permalink (frontmatter `permalink: sync/troubleshoot`). Syncthing's docs never define what `<modifiedBy>` concretely contains (presumably a device-ID form; not stated in the text read). Obsidian does not say whether "last modified" means the device's file mtime or server receipt time, nor whether "Create conflict file" also applies to non-Markdown files. Nothing read speaks to mtime precision or stability in the iOS Documents folder via @capacitor/filesystem, so the `modTimeWindowS` recommendation is a flag to verify, not an established need.

#### Key Derivation

- OWASP (current cheat sheet) ranks Argon2id first, scrypt second, and PBKDF2-HMAC-SHA256 at 600,000 iterations as the FIPS/compat fallback; those are the parameter floors. (https://raw.githubusercontent.com/OWASP/CheatSheetSeries/master/cheatsheets/Password_Storage_Cheat_Sheet.md)
- Node 24's Web Crypto implements PBKDF2 for deriveBits/deriveKey; its Argon2 support (added v24.8.0) is gated on OpenSSL >= 3.2, and NODE-SCRYPT was removed from Web Crypto in v18.4/v16.17. In the project's actual Electron 42.4.0 binary (Node 24.16.0 on BoringSSL, process.versions.openssl reports "0.0.0") Argon2 does not exist at all: SubtleCrypto.supports('importKey','Argon2id') is false, importKey throws NotSupportedError "Unrecognized algorithm name", and node:crypto.argon2 throws ERR_CRYPTO_ARGON2_NOT_SUPPORTED (local run, ELECTRON_RUN_AS_NODE=1). (https://raw.githubusercontent.com/nodejs/node/v24.x/doc/api/webcrypto.md)
- PBKDF2-HMAC-SHA256 via crypto.subtle.deriveBits is native and fast in Electron main: 600,000 iterations took 37 ms and 1,000,000 took 62 ms; for comparison native node:crypto.scryptSync at OWASP's N=2^17, r=8, p=1 took 257 ms (local run, electron@42.4.0, M5 MacBook Air, ELECTRON_RUN_AS_NODE=1). The doc's own PBKDF2 example is the API shape used. (https://raw.githubusercontent.com/nodejs/node/v24.x/doc/api/webcrypto.md)
- The W3C Web Crypto spec defines exactly two password/secret-derivation algorithms with a deriveBits operation, HKDF and PBKDF2; scrypt and Argon2 appear nowhere in the spec, so any scrypt/Argon2 on WebKit must be JS or WASM. (https://raw.githubusercontent.com/w3c/webcrypto/main/spec/Overview.html)
- WebKit implements PBKDF2 deriveBits and, on Apple platforms, backs it with CommonCrypto's native CCKeyDerivationPBKDF, so the iOS side runs PBKDF2 in native code, not JS. (https://raw.githubusercontent.com/WebKit/WebKit/main/Source/WebCore/crypto/cocoa/CryptoAlgorithmPBKDF2Cocoa.cpp)
- WebKit's Web Crypto algorithm roster has no scrypt and no Argon2 implementation. (https://api.github.com/repos/WebKit/WebKit/contents/Source/WebCore/crypto/algorithms)
- MDN compat data records SubtleCrypto.deriveBits and deriveKey (including the PBKDF2 derived-key option) as supported since Safari 11, with iOS Safari mirroring desktop; Node's entry still carries a stale "Supports: NODE-SCRYPT" note that the Node doc says was removed in v18.4. (https://raw.githubusercontent.com/mdn/browser-compat-data/main/api/SubtleCrypto.json)
- @noble/hashes' pure-JS scrypt is usable but costly on a phone: N=2^16 is ~0.1 s / 64 MB on an M4 and doubles per N step, phones 1x-4x slower; OWASP's floor N=2^17,r=8,p=1 therefore needs 128*8*(2^17+2) ≈ 134 MB inside the WKWebView; noble's own README says JS Argon2 cannot be fast and points users to scrypt instead. A local Electron run of the noble scrypt already in the project's node_modules gave N=2^16 = 104 ms, N=2^17 = 191 ms on the M5, matching the README. (https://raw.githubusercontent.com/paulmillr/noble-hashes/main/README.md)
- A noble-hashes user measured noble's JS argon2id ~13x slower than libsodium's WASM argon2id (63 ms for 2^26 bytes in sodium); the maintainer's reply confirms JS Argon2 cannot be fast and that noble will stay JS-only — so Argon2id is reachable in both runtimes only by adding a WASM dependency, which the 'only Web Crypto guaranteed' constraint excludes. (https://github.com/paulmillr/noble-hashes/issues/105)
- crypto.subtle should be present in Capacitor's WKWebView: WebKit treats an origin as potentially trustworthy (secure context) when its host is localhost OR its scheme is served by a WKURLSchemeHandler, and Capacitor iOS defaults to scheme "capacitor" + hostname "localhost" served through WebViewAssetHandler, a WKURLSchemeHandler — both branches apply. (https://raw.githubusercontent.com/WebKit/WebKit/main/Source/WebCore/page/SecurityOrigin.cpp)

**Verdict:** Use PBKDF2-HMAC-SHA256 via crypto.subtle.deriveBits, 600,000 iterations minimum (a vault key derives once per unlock, so 1,000,000 costs ~60 ms native and is fine), 16-byte random salt, 256-bit output, with hash/iterations/salt stored in the vault info record so the count can be raised later; it is native on both sides (BoringSSL in Electron, CommonCrypto on iOS) and deterministic, so the two runtimes agree without sharing a library. Argon2 is eliminated by evidence (Electron's BoringSSL build has none in Web Crypto or node:crypto; WebKit has none; JS Argon2 is unusably slow), and scrypt loses on asymmetry (native scryptSync on Electron vs pure-JS noble on iOS, ~134 MB and hundreds of ms on the WKWebView main thread at OWASP's N=2^17) for a marginal gain in a self-hosted, ciphertext-only threat model; PBKDF2's real cost is that it is not memory-hard, so a GPU cracker holding the server's ciphertext gets full parallelism — the mitigation is the iteration count plus a decent vault password.

**Unresolved:** No measured timing exists for either PBKDF2 (CommonCrypto) or noble scrypt on a physical iPhone — the Simulator runs on the Mac CPU so it would not answer this, and no noble-hashes issue with phone-specific scrypt numbers was found; the only phone claim is the README's "1x-4x slower". crypto.subtle inside an actual Capacitor 8 WKWebView was inferred from WebKit source plus Capacitor defaults, not executed; the Capacitor config docs describe iosScheme (default "capacitor") but say nothing about secure context. Electron PBKDF2/scrypt timings were taken via ELECTRON_RUN_AS_NODE against the same electron@42.4.0 binary, not inside a live main process. Argon2id is reachable on both runtimes only through a WASM library (libsodium-class), which the stated Web-Crypto-only constraint rules out; not evaluated further.

#### Path Tokens

- Proton Drive is direct prior art: it computes an HMAC of the plaintext name keyed with a secret per-folder hash key and uses the hex digest as the server-side name token. (https://raw.githubusercontent.com/ProtonMail/WebClients/main/packages/shared/lib/keys/driveKeys.ts)
- Proton's HMAC name token exists only for collision checks; the hash key is a per-folder secret decrypted client-side, so the server never links same-named files across folders. (https://raw.githubusercontent.com/ProtonMail/WebClients/main/packages/drive-store/store/_links/useLink.ts)
- Obsidian Sync (the model for Pommora Sync) documents its own gap: the server holds the path-to-content mapping in plaintext with no cryptographic binding, so a compromised server can deliver one file's ciphertext under another path. (https://raw.githubusercontent.com/obsidianmd/obsidian-help/master/en/Obsidian%20Sync/Security%20and%20privacy.md)
- Cryptomator binds an encrypted name to its location by passing the parent directory ID as AES-SIV associated data, NFC-normalizes the name first so every platform derives the same bytes, and hides hierarchy by addressing directories through random dirIds in a flattened layout. (https://docs.cryptomator.org/en/latest/security/vault/)
- Standard Notes binds ciphertext to the item's random UUID via authenticated data, and addresses items by UUID rather than by any name or path. (https://raw.githubusercontent.com/standardnotes/app/main/packages/snjs/specification.md)
- rclone crypt's Standard mode encrypts names deterministically segment by segment, so the directory tree and name equality stay visible to the remote, and PKCS#7 padding to 16 bytes exposes name length in 16-byte buckets. (https://raw.githubusercontent.com/rclone/rclone/master/docs/content/crypt.md)
- gocryptfs derives separate subkeys for content and names via HKDF, accepts per-directory determinism as the price of addressability, and treats hashing an already-public ciphertext name as free of security cost. (https://nuetzlich.net/gocryptfs/forward_mode_crypto/)
- Syncthing's untrusted-device mode encrypts the file name deterministically (AES-SIV, no nonce) with the folder key and re-slashes the base32 output at fixed positions, so the stored layout carries no plaintext hierarchy; the spec states what the untrusted side still sees, and its name-derived file key means a rename re-encrypts every block. (https://docs.syncthing.net/specs/untrusted.html)
- Joplin sidesteps path addressing entirely: items are addressed by client-generated IDs, and Joplin Server stores that ID plus a few extracted properties in separate columns. (https://raw.githubusercontent.com/laurent22/joplin/dev/readme/dev/spec/server_items.md)
- Joplin's encrypted blob keeps only a fixed header in plaintext (identifier, version, length, method, master key ID); titles and everything else travel inside the encrypted serialized item. (https://raw.githubusercontent.com/laurent22/joplin/dev/readme/dev/spec/e2ee/index.md)

**Verdict:** Borrow HMAC-SHA256(pathKey, NFC-normalized relative path) with pathKey an HKDF subkey of the vault key and the item id bound into the blob (AES-GCM AAD, or verify envelope.path hashes to the id); a folder rename re-uploads every descendant because the {path,mtime,content} envelope changes, not because of the HMAC id — Cryptomator's random-dirId addressing avoids that burst at the cost of a stored id-to-path index.

**Unresolved:** How Obsidian Sync encrypts paths (deterministic or not) is undocumented beyond 'encrypted file paths'; Proton's prose security-model page 404'd, so the HMAC claim rests on client source alone; no source addresses case-folding on case-insensitive APFS before hashing; whether Joplin Server extracts parent ID for E2EE items is not stated.

#### Change-Log Semantics

- Dropbox's pull is {entries, cursor, has_more} with a stateless opaque cursor; a dead cursor is a typed 'reset' error that means 'start over with list_folder', and the route doc is itself the idempotent-apply algorithm: a FileMetadata replaces whatever is at the path, a DeletedMetadata for a path you don't have is ignored. (https://raw.githubusercontent.com/dropbox/dropbox-api-spec/main/files.stone)
- Joplin Server's delta cursor is the id of the last change row served; an unknown cursor throws ErrorResyncRequired; an empty page echoes the caller's cursor back; has_more is computed from the raw page size before compression; and create/update changes for items that no longer exist are withheld so only the delete change reaches the client. (https://raw.githubusercontent.com/laurent22/joplin/dev/packages/server/src/models/ChangeModel/ChangeModel.ts)
- Joplin's delta spec explicitly requires clients to treat a delete for an item they don't have as a no-op, to skip creates for items already present after a full resync, and warns that a stale cursor (older than the 180-day update-compression window) yields resyncRequired and a full re-pull rather than data loss. (https://raw.githubusercontent.com/laurent22/joplin/dev/readme/dev/spec/server_delta_sync.md)
- Joplin's client driver handles the resync signal mechanically: on error code 'resyncRequired' it nulls the cursor and re-issues the same delta call from the beginning; tombstones arrive as ordinary change rows with type 3 which the driver maps to isDeleted. (https://raw.githubusercontent.com/laurent22/joplin/dev/packages/lib/file-api-driver-joplinServer.ts)
- Joplin advances the persisted cursor per page and only after that page has been applied locally; on user cancel it deliberately does not persist, and the comment states that re-applying a page is safe because identical items are skipped as no-op updates. (https://raw.githubusercontent.com/laurent22/joplin/dev/packages/lib/Synchronizer.ts)
- Joplin has no server-side base-version precondition on push: the client stats and downloads the remote copy before uploading and calls it a conflict when the remote's updated_time is newer than the item's last sync_time; on the pull side it re-reads the latest local updated_time right before overwriting so a long delta pass can't clobber a local edit. Because sync_lock.md allows multiple concurrent SYNC locks, two uploaders can both pass this client-side check, which is the gap a server precondition closes. (https://raw.githubusercontent.com/laurent22/joplin/dev/packages/lib/Synchronizer.ts)
- Standard Notes' sync_token and cursor_token both decode to a server updated_at timestamp; the query uses '>=' when resuming a paginated pull (cursor_token) and '>' when resuming from a completed sync (sync_token), so the boundary item is re-delivered during pagination; tombstones are excluded on a first sync (no token) and included on every incremental pull; a cursor_token is issued from the last returned item's updated_at only when more remain. (https://raw.githubusercontent.com/standardnotes/server/main/packages/syncing-server/src/Domain/UseCase/Syncing/GetItems/GetItems.ts)
- Standard Notes' push precondition is an exact equality check between the client's echoed updated_at_timestamp and the server's; any mismatch rejects the save as a 'sync_conflict' that carries the server's copy back, so the client resolves locally and re-syncs. (https://raw.githubusercontent.com/standardnotes/server/main/packages/syncing-server/src/Domain/Item/SaveRule/TimeDifferenceFilter.ts)
- Standard Notes' 'version' is server-assigned, not client mtime: the store stamps updated_at from the server clock, returns it in saved_items so the client records only that timestamp (never the echoed content), and mints the next sync_token as max(saved updated_at) + 1 microsecond, or the server clock at the start of the save when nothing was saved, which is a clock-derived cursor rather than a log position. (https://raw.githubusercontent.com/standardnotes/server/main/packages/syncing-server/src/Domain/UseCase/Syncing/SaveItems/SaveItems.ts)
- The Standard Notes client persists retrieved payloads to local storage first and only then writes sync_token/cursor_token; the error handler never touches the tokens, so a failed or interrupted page is replayed from the previous position on the next request. (https://raw.githubusercontent.com/standardnotes/app/main/packages/snjs/lib/Services/Sync/SyncService.ts)

**Verdict:** Borrow: pull = {changes, cursor, has_more} over a monotonic integer seq (not Joplin's row id or Standard Notes' clock token), tombstones as ordinary delete changes, client persists the cursor per page only after that page is applied (Joplin/snjs), a typed resync error → clear cursor → full snapshot that omits tombstones (SN first-sync) applied with the Dropbox/Joplin no-op rules (delete-on-missing ignored, identical content skipped, own echoes no-ops); store = per-item server-assigned version with an equality precondition whose conflict response carries the server item and whose success response returns the new version for the client to record (SN); set item.version = the seq of the change that wrote it so the store precondition and the pull cursor share one counter and cursor validity is just seq >= min_retained.

**Unresolved:** dropbox.com developer pages (WebFetch 400; curl returned a 1 KB JS shell) and docs.standardnotes.com (403) were unreachable, so Dropbox's prose guidance on when to persist a cursor and how list_folder/continue treats deletions when include_deleted=false are unverified; the Stone spec is silent on both. Dropbox's legacy v1 /delta endpoint was never fetched. Joplin's spec lives at readme/dev/spec/ (readme/spec/sync.md 404s). Standard Notes' conflict-resolution prose was read from the GitHub docs repo, not the published site.

#### Node Built-Ins Server

- node:sqlite stopped printing an ExperimentalWarning and became a Stability 1.2 release candidate in Node 24.15.0; pin the Docker base to node:24.15 or later, not bare node:24, because earlier 24.x still warns and sits at 1.1. (https://github.com/nodejs/node/commit/aaf9af1672.patch)
- 'Release candidate' is still a substage of Stability 1, not Stability 2 — Node's own index says production use of Stability 1 features is not recommended, while 1.2 means no further breaking changes are anticipated. (https://nodejs.org/docs/latest-v24.x/api/documentation.html)
- Every DatabaseSync call blocks the event loop; the busy timeout defaults to 0 ms, the defensive flag defaults on since 24.14.0, and a `limits.length` option caps string/BLOB size — set `timeout` and `limits.length` explicitly on the server. (https://nodejs.org/docs/latest-v24.x/api/sqlite.html)
- BLOBs are whole values only: bind a TypedArray/DataView/Buffer, read back a Uint8Array (not a Buffer). There is no incremental BLOB I/O, so an uploaded blob must be fully buffered in memory (or spooled to a temp file) before `run()` can bind it. (https://raw.githubusercontent.com/nodejs/node/v24.x/src/node_sqlite.cc)
- The prepared-statement API is complete for a sync server: `prepare()` wraps sqlite3_prepare_v2 and returns StatementSync; `run()` returns `{changes, lastInsertRowid}`; `get()` returns the first row or undefined; `iterate()` streams rows (use it to page the change log); `readBigInts` guards out-of-range INTEGER reads; `createTagStore()` gives an LRU cache of prepared statements (added 24.9.0). (https://nodejs.org/docs/latest-v24.x/api/sqlite.html)
- WAL is not a node:sqlite option and the Node doc never mentions it; enable it once with `db.exec('PRAGMA journal_mode = WAL')` and SQLite persists it in the file across connections and reopens. (https://sqlite.org/pragma.html)
- node:http streams request bodies natively — IncomingMessage is a stream.Readable you consume with `for await (const chunk of req)` — but createServer has no request-body size option, so the byte cap is the handler's job; the documented server limits are maxHeaderSize (16 KiB), headersTimeout, and requestTimeout (300 s default, responds 408), which matters for slow large uploads. (https://nodejs.org/docs/latest-v24.x/api/http.html)
- Node's official Docker guidance for a single-process service: pass config as `-e` env vars with NODE_ENV=production, don't let Node be PID 1 (use `--init` or tini), run as the image's non-root `node` user (uid 1000), and bake `CMD ["node","index.js"]` so SIGTERM/SIGINT reach Node instead of npm. (https://raw.githubusercontent.com/nodejs/docker-node/main/docs/BestPractices.md)
- Joplin Server's env pattern worth borrowing: a committed `.env-sample` the operator copies to `.env` and passes with `docker run --env-file .env`; the process merges the env file under `process.env` so real environment overrides the file; and a typed `parseEnv` derives each key's type from its default (number/boolean/string) and throws on an unparseable number. (https://raw.githubusercontent.com/laurent22/joplin/dev/packages/server/src/app.ts)
- Joplin's Dockerfile.server: borrow the multistage node:24 → node:24-slim build, `useradd` non-root user, `ENTRYPOINT ["tini","--"]`, and `RUNNING_IN_DOCKER=1`; avoid installing PM2 inside the image and `CMD ["yarn","start-prod"]` (contradicts Node's CMD guidance), and avoid its data layout — SQLITE_DATABASE is a bare path env, STORAGE_DRIVER carries a second unrelated `Path=`, and temp/log dirs derive from the code's rootDir. Use one DATA_DIR env and derive db path, blob dir and temp from it. (https://raw.githubusercontent.com/laurent22/joplin/dev/Dockerfile.server)

**Verdict:** Borrow: node:sqlite on node:24.15+ (WAL via PRAGMA, explicit timeout + limits.length, whole-value BLOBs buffered per request) and raw node:http with a hand-rolled body byte cap; borrow Joplin's .env-sample + --env-file, process.env-over-file precedence, typed parseEnv, multistage/tini/non-root image. Avoid: Joplin's in-image PM2 and yarn CMD, and its split SQLITE_DATABASE/STORAGE_DRIVER/rootDir paths — one DATA_DIR env instead.

**Unresolved:** (1) The compile-time default of `limits.length` (SQLITE_MAX_LENGTH) in Node's bundled SQLite was not verified — the doc says defaults "may vary depending on how SQLite was built"; set it explicitly rather than relying on it. (2) WAL behavior on bind-mounted or network volumes was not checked (sqlite.org/wal.html not fetched). (3) No timeline for node:sqlite graduating to Stability 2 was found; it remains formally Stability 1 in 24.x. (4) The Node http doc has no server-side body-read example; the `for await` example cited is from the stream doc on an fs stream, applied to IncomingMessage by its documented Readable inheritance.

### Capacitor And iOS

#### Web Crypto In WKWebView

- WebKit exposes crypto.subtle (and crypto.randomUUID) only in a secure context; both are marked [SecureContext] in the Web IDL, so availability reduces to whether capacitor://localhost is a secure context. (https://raw.githubusercontent.com/WebKit/WebKit/main/Source/WebCore/page/Crypto.idl)
- WebKit's secure-context origin test passes on any one of four conditions: a scheme registered as secure, a localhost/loopback host, a scheme registered as local, or a scheme handled by a WKURLSchemeHandler. capacitor://localhost satisfies two of them independently (host is localhost; scheme is a registered handler), so it is a secure context even if Capacitor's hostname were changed. (https://raw.githubusercontent.com/WebKit/WebKit/main/Source/WebCore/page/SecurityOrigin.cpp)
- The scheme-handler rule was added deliberately on 03-19-2021 (WebKit bug 223423, commit 1985ef105c): before it only custom://localhost was secure; after it every origin on a registered custom scheme is. The localhost-host rule predates it. (https://api.github.com/repos/WebKit/WebKit/commits/1985ef105c3055bbfba9fe6a2d970173634e4ac5)
- A WKURLSchemeHandler scheme yields a real tuple origin (capacitor://localhost), not an opaque one: WebKit exempts handler-registered schemes from its non-special-scheme opaque-origin rule. This matters beyond crypto, since an opaque origin would be 'Not Trustworthy' per spec and would also break origin-keyed storage such as localStorage and IndexedDB. (https://raw.githubusercontent.com/WebKit/WebKit/main/Source/WebCore/page/SecurityOriginData.cpp)
- Capacitor iOS registers its asset handler through exactly that API, WKWebViewConfiguration.setURLSchemeHandler for the configured scheme (default 'capacitor'), so WebKit's handler-scheme registration is what marks it. The receiving side, WebPage::registerURLSchemeHandler, calls LegacySchemeRegistry::registerURLSchemeAsHandledBySchemeHandler(scheme) (verified at https://raw.githubusercontent.com/WebKit/WebKit/main/Source/WebKit/WebProcess/WebPage/WebPage.cpp, line 9083). (https://raw.githubusercontent.com/ionic-team/capacitor/main/ios/Capacitor/Capacitor/CAPBridgeViewController.swift)
- Capacitor's config reference documents the defaults and the reason: hostname defaults to 'localhost' and is recommended precisely so secure-context-only Web APIs work; iosScheme defaults to 'capacitor' and cannot be http/https because WKWebView already handles those (Apple's setURLSchemeHandler doc, fetched at https://developer.apple.com/tutorials/data/documentation/webkit/wkwebviewconfiguration/seturlschemehandler(_:forurlscheme:).json, says registering a scheme WebKit already handles such as https raises invalidArgumentException); androidScheme defaults to 'https'. (https://capacitorjs.com/docs/config)
- On Android, https became the default androidScheme in Capacitor 6 (for existing apps too); the upgrade note warns that changing the scheme changes the origin and orphans cookies/localStorage. Relevant if anything on Android is ever stored origin-keyed (IndexedDB, a cached vault key) and the scheme is later flipped. (https://raw.githubusercontent.com/ionic-team/capacitor-docs/main/docs/main/updating/6-0.md)
- Android WebView is Chromium, whose implementation of the Secure Contexts spec treats https://<any host> as trustworthy by scheme and http://localhost as trustworthy by host. Both Capacitor Android configurations (https default, or http kept for a legacy origin) are therefore secure contexts with crypto.subtle, provided hostname stays localhost under http. (https://raw.githubusercontent.com/chromium/chromium/main/net/base/is_potentially_trustworthy.cc)
- Capacitor's tracker has no issue about crypto.subtle, SubtleCrypto, webcrypto, or isSecureContext (gh issue searches on ionic-team/capacitor returned nothing relevant). The only 'secure context' issue, #3418 (2020, https://github.com/ionic-team/capacitor/issues/3418), concerned Secure cookies on Android with a custom scheme, and its reporter later confirmed 'On Android chrome will accept the url http://localhost as a Secure Context.' The maintainer's rule, restated in discussion #5387 after a user saw isSecureContext true on Android with https and a custom hostname, matches the Chromium source. (https://github.com/ionic-team/capacitor/discussions/5387)
- One trap not to conflate with the web secure context: on iOS, HTTPCookieStorage decides 'secure' by URL scheme, so Secure-flagged cookies are not surfaced to document.cookie on capacitor:// even though the page is a secure context. Irrelevant to Web Crypto; relevant only if Pommora Sync ever authenticates with Secure cookies instead of device tokens. (https://github.com/ionic-team/capacitor/discussions/7690)

**Verdict:** Borrow: crypto.subtle is available. capacitor://localhost is a secure context in WKWebView by two independent WebKit rules (localhost host; WKURLSchemeHandler-registered scheme), and a purpose-built WKWebView test on the iOS 26.5 Simulator (runtime 23F77) and on macOS 26.6 / WebKit 21624 returned isSecureContext:true, typeof crypto.subtle 'object', and a working PBKDF2-SHA256 -> AES-256-GCM (12-byte IV) -> HMAC-SHA256 round trip at both capacitor://localhost and capacitor://app.example; on Android both https://localhost (Capacitor default) and http://localhost are secure contexts in Chromium. No Capacitor config change is needed, just keep hostname at localhost.

**Unresolved:** (1) Which shipped Safari/iOS release first carried WebKit commit 1985ef105c (the any-host-on-a-handler-scheme rule) was not established; it is moot for an iOS 26.5-only target, and the localhost-host rule predates it anyway. (2) Android was not tested empirically (no Android SDK on this Mac); that answer rests on Chromium source plus the Capacitor maintainer's statement. (3) Web Crypto algorithm-parameter parity between WebKit's SubtleCrypto and Node 24 beyond the three operations exercised (PBKDF2 deriveKey, AES-GCM encrypt/decrypt, HMAC sign) was out of scope and not checked. Note: the Simulator run's navigator.userAgent reads 'iPhone OS 18_7'; that is WebKit's frozen UA string, not the runtime, which simctl reports as iOS 26.5 (23F77). #### Capacitor Filesystem

- @capacitor/filesystem 8.1.3 (npm latest, 2026-08-19; GitHub main is identical to tag v8.1.3) readdir is non-recursive and returns, per entry, name, type, size, ctime, mtime, and uri — a walk needs no per-file stat call from JS. mtime is in milliseconds. (https://raw.githubusercontent.com/ionic-team/capacitor-filesystem/main/README.md)
- On iOS the per-entry stat happens natively in Swift inside a single bridge call: readdir lists the directory with FileManager.contentsOfDirectory, then calls attributesOfItem for each entry and returns the whole array at once. So a walk costs one bridge round-trip per directory, not per file. mtime is computed as timeIntervalSince1970 * 1000 and rounded to an integer. (https://raw.githubusercontent.com/ionic-team/capacitor-filesystem/main/ios/Sources/FilesystemPlugin/FilesystemOperationExecutor.swift)
- There is no batching or multi-path method and no way to set a file's mtime: the plugin exposes exactly 15 single-path methods. A pulled file written on iOS gets mtime = time of write, so the sync client must carry the authoritative mtime in its own envelope/index rather than reading it back from disk. (https://raw.githubusercontent.com/ionic-team/capacitor-filesystem/main/ios/Sources/FilesystemPlugin/FilesystemPlugin.swift)
- readdir entry order is not deterministic and differs between iOS and Android (open issue #74, 2026-04-16; fix PR #73 still open). The iOS implementation applies no sort to contentsOfDirectory output, so a walker must sort by name itself. (https://github.com/ionic-team/capacitor-filesystem/issues/74)
- No issue, benchmark, or documentation about readdir slowness or bridge cost for walking many files exists in the plugin repo, the old capacitor-plugins monorepo, or the ionic-team org. The only 'slowdowns' language in the docs is about the deprecated downloadFile progress events, not readdir. (https://api.github.com/search/issues?q=repo:ionic-team/capacitor-filesystem+readdir)
- Path resolution on iOS: with `directory: Directory.Documents` the path is appended to FileManager's documentDirectory URL via appending(path:) with no URL-string parsing. Omitting `directory` switches to raw mode, and in the shipped ion-ios-filesystem 1.1.2 (what 8.1.3's `from: "1.1.1"` pin resolves to) raw mode is `URL(string: path)` only — so pass a `file://` URI, not a bare `/var/...` path; the scheme-less fallback exists only on unreleased main (HEAD 8456bf2c, 2026-09-01, vs tag 1.1.2 = 0d81e26e). Data, External, ExternalStorage and ExternalCache all alias the Documents directory on iOS. (https://raw.githubusercontent.com/ionic-team/ion-ios-filesystem/1.1.2/IONFilesystemLib/IONFILEManager.swift)
- writeFile is NOT atomic on iOS: string data is written with atomically: false and binary data with Data.write(to:) whose default WritingOptions is [] (.atomic is an opt-in bit). A crash mid-write can leave a truncated file. With recursive:false a missing parent throws OS-PLUG-FILE-0011; recursive:true creates parents. Identical at tag 1.1.2 and main. (https://raw.githubusercontent.com/ionic-team/ion-ios-filesystem/1.1.2/IONFilesystemLib/IONFILEManager.swift)
- rename on iOS: source must exist (OS-PLUG-FILE-0008); same source and destination is a silent no-op success; an existing FILE at the destination is deleted first and then FileManager.moveItem runs — two separate operations, so temp-write-then-rename gives a single moveItem only when the destination is absent, not an atomic replace over an existing file. An existing DIRECTORY at the destination is not deleted; the call falls through to moveItem as-is. RenameOptions is the same shape as CopyOptions: from, to, directory, toDirectory. (https://raw.githubusercontent.com/ionic-team/ion-ios-filesystem/1.1.2/IONFilesystemLib/IONFILEManager.swift)
- deleteFile checks existence then calls FileManager.removeItem with no file-vs-directory check. mkdir throws OS-PLUG-FILE-0011 if the parent is missing and recursive:false, OS-PLUG-FILE-0010 if the target already exists, then createDirectory(withIntermediateDirectories: recursive). rmdir throws OS-PLUG-FILE-0008 if missing; with recursive:false it lists the directory first and throws OS-PLUG-FILE-0012 if non-empty; then removeItem deletes the tree. Error codes are stable since 7.1.0 and are the way to detect not-found (there is no exists() method; issue #18 is open). (https://raw.githubusercontent.com/ionic-team/capacitor-filesystem/main/README.md)
- Native readFile always returns a string: UTF-8 text with encoding: Encoding.UTF8, otherwise base64 of the bytes; writeFile without an encoding requires base64 input. 8.1.0 added native-only offset/length partial reads. stat returns the same FileInfo shape as a readdir entry via attributesOfItem — one bridge call per path. For the sync client this means Markdown crosses the bridge as UTF-8 strings and ciphertext crosses as base64 strings. (https://raw.githubusercontent.com/ionic-team/capacitor-filesystem/main/README.md)

**Verdict:** Borrow: one readdir bridge call per directory returns name/type/size/mtime (ms) for every entry with the per-entry stat done in Swift, so a few-hundred-file walk is a few dozen round-trips with no per-file stat — sort the result yourself (#74 open) and use directory: Documents + relative paths; but writes are not atomic, rename over an existing file is delete-then-move (not an atomic replace), and mtime cannot be set, so the sync client must own its own mtime record and treat on-disk mtime as advisory on iOS.

**Unresolved:** (1) No benchmark or issue exists for readdir walk cost through the bridge; per-call latency for a few hundred files is unmeasured, not shown to be fast. (2) Whether FileManager.moveItem is atomic on iOS/APFS, and what it does when the destination is an existing directory, was not verified from Apple documentation (developer.apple.com pages are JS-rendered; not fetched). (3) Android and web implementations were not examined; all native semantics above are iOS (ion-ios-filesystem 1.1.2) only. (4) fixPathComponentsIfNeeded appends a trailing "/" to a NON-EXISTENT path whose pathExtension is empty, treating it as a directory — .md/.json files are unaffected, but writing a fresh extensionless file (e.g. inside a .trash/ bundle) should be tested before relying on it. (5) How URL(string:) in raw mode treats spaces or other characters needing percent-encoding was not tested; the directory-relative route avoids the question entirely.

Whether aparajita's hard @capacitor/core dependency can produce a duplicate core under strict package isolation (pnpm) was not tested; the project uses npm, which dedupes on a compatible ^8 range.

#### ATS And CORS

- ATS governs every connection made through the URL Loading System (URLSession), so it applies identically to a fetch() issued by Capacitor's WKWebView and to CapacitorHttp's native URLSession path; a blocked cleartext load fails at connect time with a console message, and the only web-view-scoped exemption is NSAllowsArbitraryLoadsInWebContent (which needs App Store justification). (https://developer.apple.com/documentation/security/preventing-insecure-network-connections)
- No Info.plist ATS key is required for plain http:// to an unqualified host such as `localhost` on iOS 10 and later; NSAllowsLocalNetworking=YES is Apple's recommended but optional 'declaration of intent', and setting it makes newer OS versions ignore NSAllowsArbitraryLoads. The page never uses the word 'localhost'; that `localhost` is an 'unqualified domain' is an inference, corroborated by a local test (see evidence). (https://developer.apple.com/documentation/bundleresources/information-property-list/nsapptransportsecurity/nsallowslocalnetworking)
- NSAllowsArbitraryLoads is the wrong tool for localhost development: it disables ATS for every domain not listed in NSExceptionDomains, requires App Store justification, and on iOS 10+ is ignored outright (treated as NO) whenever NSAllowsLocalNetworking, NSAllowsArbitraryLoadsInWebContent, or NSAllowsArbitraryLoadsForMedia is present in the plist. (https://developer.apple.com/documentation/bundleresources/information-property-list/nsapptransportsecurity/nsallowsarbitraryloads)
- The narrow, per-host exception (for a deployed plain-HTTP host, or for 127.0.0.1 if the IP is ever used instead of the name) is an NSExceptionDomains entry with NSExceptionAllowsInsecureHTTPLoads=YES: the key is lowercase, carries no port, may be an IP address or CIDR range on iOS 17+, and a domain entry (even an empty one) makes ATS ignore all global keys for that host. A DNS-name exception does not cover a connection made by IP and vice versa. (https://developer.apple.com/documentation/bundleresources/information-property-list/nsapptransportsecurity/nsexceptiondomains)
- Capacitor's iOS defaults are server.iosScheme = `capacitor` and server.hostname = `localhost`, so the WebView's origin is `capacitor://localhost`; Capacitor recommends keeping `localhost` because it makes the origin a secure context. The native side hardcodes the same defaults (CAPInstanceDescriptor.m: `CAPInstanceDescriptorDefaultScheme = @"capacitor"`, `CAPInstanceDescriptorDefaultHostname = @"localhost"`), and iosScheme cannot be http/https because WKWebView already owns those schemes. (https://raw.githubusercontent.com/ionic-team/capacitor-docs/main/docs/main/reference/config.md)
- A plain fetch() from `capacitor://localhost` to `http://localhost:PORT` is cross-origin, so Pommora Sync must answer CORS: `Access-Control-Allow-Origin` set to the reflected `Origin` (or the literal `capacitor://localhost`; `*` works but weakens CSRF posture), and because a device-token `Authorization` header and `Content-Type: application/json` are outside the safelist, every authenticated request is preflighted — the server must answer OPTIONS with `Access-Control-Allow-Methods` (including PUT/DELETE if used) and `Access-Control-Allow-Headers: Authorization, Content-Type`, optionally `Access-Control-Max-Age` to cache the preflight. Ionic's own recommendation for servers you cannot control is CapacitorHttp, with the note that CORS is still needed anywhere the app runs as a web page. (https://ionicframework.com/docs/troubleshooting/cors)
- CapacitorHttp is off by default; enabling `plugins.CapacitorHttp.enabled` in capacitor.config makes the runtime replace window.fetch and XMLHttpRequest with native-backed versions (plus explicit CapacitorHttp.get/post/... methods). The plugin page says nothing about ATS, Info.plist, or CORS, and warns that large payloads crossing the native-to-web bridge are a problem — directly relevant to pulling whole-file ciphertext blobs. (https://raw.githubusercontent.com/ionic-team/capacitor-docs/main/docs/apis/http.md)
- How CapacitorHttp sidesteps CORS without touching ATS: with it enabled, the WebView never issues the cross-origin request itself. Requests to the app's own server URL fall through to the real fetch; GET/HEAD/OPTIONS/TRACE are rewritten to the app's own origin at `/_capacitor_http_interceptor_?u=<target>` — same-origin for the WebView — and the WKURLSchemeHandler performs the real request with `URLSession.shared` (only when `CapacitorHttp.enabled` is true, otherwise it fails with unsupportedURL); every other method (POST/PUT/DELETE/PATCH) goes over the bridge to native `CapacitorHttp.request`, a `URLSession.dataTask`, and a JS `Response` is rebuilt from the native result. Both paths are URLSession, so ATS policy still applies exactly as it would to the WebView. (https://raw.githubusercontent.com/ionic-team/capacitor/main/core/native-bridge.ts)
- Mixed-content blocking is a third gate distinct from ATS and CORS, and it does not bite for this setup: WebKit only classifies a subresource request as mixed content when the document's origin protocol is literally `https` (a `capacitor://` document is not), and even for https documents a localhost/loopback target counts as potentially trustworthy and a non-Public address space is never blocked. Caveat: this is WebKit's main branch today, not necessarily the WebKit build shipped in iOS 26.5, and the https-only check carries a FIXME. (https://raw.githubusercontent.com/WebKit/WebKit/main/Source/WebCore/loader/MixedContentChecker.cpp)
- Capacitor's SPM iOS template (the one `cap add ios` uses for an SPM, no-CocoaPods project) ships no NSAppTransportSecurity dictionary at all, so a fresh companion project runs under default ATS policy; any ATS key is a manual addition to ios/App/App/Info.plist and nothing in the template pre-opens arbitrary loads. (https://raw.githubusercontent.com/ionic-team/capacitor/main/ios-spm-template/App/App/Info.plist)

**Verdict:** Borrow plain fetch() plus CORS on Pommora Sync (reflect Origin or allow the literal capacitor://localhost, answer OPTIONS with Allow-Methods and Allow-Headers: Authorization, Content-Type); no ATS key is needed for http://localhost from the iOS 26.5 Simulator (verified: default policy passed both loopback targets while refusing external cleartext with -1022), so NSAllowsLocalNetworking=YES is an optional declaration of intent and the Decision Log's G-3 overstates it as a requirement; never NSAllowsArbitraryLoads; CapacitorHttp stays an opt-in escape hatch that removes CORS but not ATS and marshals whole payloads through the bridge.

**Unresolved:** (1) Apple's text says iOS 17+/macOS 14+ "no longer allows connections to IP addresses by default", yet http://127.0.0.1 passed under default policy in both the iOS 26.5 Simulator and macOS 26.6; whether loopback IPs are a documented carve-out or a Simulator/host quirk could not be sourced — use the name `localhost` in the dev URL (covered as an unqualified domain), and if the IP is ever needed, key an NSExceptionDomains entry `127.0.0.1` with NSExceptionAllowsInsecureHTTPLoads rather than guessing. (2) The probe was a bare URLSession process spawned into the Simulator, not a Capacitor WKWebView fetch; Apple's docs put WKWebView under the same policy, but the end-to-end WebView path was not exercised. (3) No Apple page was fetched stating that the Simulator shares the Mac's loopback; that was established only empirically (Simulator process reached the Mac's python server on 127.0.0.1). (4) The exact Origin header bytes WKWebView sends for a capacitor://localhost page were not packet-verified; the value rests on Ionic's documentation. (5) The mixed-content conclusion comes from WebKit's main-branch source, not the WebKit build in iOS 26.5. (6) capacitorjs.com could not be fetched from this environment (WebFetch returned an API error) and https://capacitorjs.com/docs/guides/cors is a 404; the Capacitor pages were read from their source markdown in ionic-team/capacitor-docs, and the CORS guide lives at ionicframework.com/docs/troubleshooting/cors. (7) Apple's developer.apple.com pages are JS-rendered; their content was retrieved through the site's JSON data endpoint at the same documentation path, and the canonical page URLs are cited.

#### Live Reload

- The official Capacitor live-reload guide's manual (framework-CLI) flow is: find the Mac's LAN IP (ifconfig, en0/inet), start the dev server bound to 0.0.0.0, put `server.url` (LAN IP + port) and `server.cleartext: true` in the Capacitor config, run `npx cap copy`, open Xcode with `npx cap open ios`, and press Run; the guide warns not to commit that server config. (https://capacitorjs.com/docs/guides/live-reload)
- The guide states the same-Wi-Fi requirement only for physical devices (the Simulator is not called out), and offers `npx cap run --live-reload --port <port>` as the CLI alternative to editing `server.url` by hand. (https://capacitorjs.com/docs/guides/live-reload)
- `npx cap run ios` runs sync first, then builds and deploys; `--live-reload`/`-l` overrides `server.url`, with `--host`, `--port`, `--https` to shape the URL, and `--list`/`--target <id>`/`--target-name` to pick the Simulator. (https://capacitorjs.com/docs/cli/commands/run)
- The CLI's live-reload defaults are the Mac's first non-loopback IPv4 address (falling back to `localhost`) and port 3000 unless `--https`; Vite serves on 5173, so `--host localhost --port 5173` must be passed explicitly. The URL is written only into the native project's copy (`ios/App/App/capacitor.config.json`, spread over any existing `server` block) and reverted on Ctrl+C, so nothing lands in the source `capacitor.config.ts`. (https://raw.githubusercontent.com/ionic-team/capacitor/main/cli/src/tasks/run.ts)
- The iOS Simulator shares the Mac's network stack, so `http://localhost:<port>` inside the Simulator reaches a dev server on the Mac; a LAN IP is only required for hardware devices. (https://help.apple.com/simulator/mac/current/en.lproj/static.html)
- `server.cleartext` is documented as an Android (API 28+) concern and is implemented only as the Android manifest attribute `android:usesCleartextTraffic`; a code search shows no `cleartext` handling anywhere in Capacitor's iOS runtime, so on iOS it is a no-op. (https://capacitorjs.com/docs/config)
- With `server.url` set, the WKWebView's start URL is that external URL verbatim (otherwise `capacitor://localhost`), so the page's origin — and therefore its secure-context status — is the dev server's. WebKit treats `localhost`, `*.localhost`, and loopback IPs as potentially trustworthy even over plain http; a LAN IP over http is not. Ionic's docs warn that plain-HTTP live reload breaks Web Crypto, which this project's client crypto depends on. (https://raw.githubusercontent.com/WebKit/WebKit/main/Source/WebCore/page/SecurityOrigin.cpp)
- Capacitor's iOS SPM template ships no `NSAppTransportSecurity` keys (the old `NSAllowsArbitraryLoads` default was dropped in Capacitor 4 because only the http live-reload server needed it). Apple's ATS docs say ATS applies to web views, that since iOS 17 ATS no longer allows connections to raw IP addresses by default, and that unqualified domains (e.g. `localhost`) have been allowed by default since iOS 10 — so the LAN-IP approach on iOS 26.5 is the one Apple documents as restricted. (https://developer.apple.com/tutorials/data/documentation/bundleresources/information-property-list/nsapptransportsecurity/nsallowslocalnetworking.json)
- Vite's dev server binds to `localhost` by default (enough for the Simulator); `server.host: true`/`0.0.0.0` or `--host` exposes it on the LAN; the default port is 5173 but Vite silently moves to the next free port unless `strictPort: true`, which would desync a hard-coded `--port 5173`; `allowedHosts` permits localhost and IP addresses by default, so the WebView's Host header is accepted either way. (https://raw.githubusercontent.com/vitejs/vite/main/docs/config/server-options.md)
- The Ionic CLI's live-reload path (not the Capacitor CLI) temporarily writes `NSAllowsArbitraryLoads=true` into Info.plist for iOS only when `--external` is NOT used (i.e. a localhost dev-server URL), and leaves ATS untouched when the URL is a LAN IP; the Capacitor CLI's own `--live-reload` never edits Info.plist on iOS. (https://raw.githubusercontent.com/ionic-team/ionic-cli/develop/packages/@ionic/cli/src/commands/capacitor/base.ts)

**Verdict:** Borrow the CLI flow, not the guide's LAN-IP recipe: from the Simulator use `server.url = "http://localhost:5173"` (or `npx cap run ios --live-reload --host localhost --port 5173 --target <id>`, which edits only the native config copy and self-reverts), skip `cleartext` (Android-only no-op on iOS), leave ATS alone, and bind Vite with `strictPort: true`; avoid the LAN IP because plain-http over an IP is not a secure context in WKWebView (kills `crypto.subtle`) and is the exact case Apple documents ATS restricting since iOS 17.

**Unresolved:** Not empirically run on the iOS 26.5 Simulator: (a) whether ATS's iOS 17+ IP-address restriction is actually enforced on a WKWebView live-reload load of `http://192.168.x.x:5173` in a Capacitor 8 app — no Capacitor issue confirming or denying it was found, and the Capacitor CLI adds no ATS exception in that mode; (b) whether `http://localhost:5173` needs any ATS entry on iOS 26.5 — Apple's text says unqualified domains have been allowed by default since iOS 10 and the iOS 17 change is scoped to IP addresses, yet the Ionic CLI still injects NSAllowsArbitraryLoads on its localhost path with no documented rationale. Both sit on or beside the LAN-IP path; the localhost recommendation holds either way. Also unverified: no Apple document was found stating explicitly that Simulator `localhost` maps to the Mac's loopback (only that Simulator uses the Mac's network connection; the direct statement comes from a user-authored Capacitor issue).

#### App, Preferences, Asset URLs

- @capacitor/app `appStateChange` on iOS is driven by focus notifications (willResignActive / didBecomeActive), payload `{ isActive: boolean }`; the separate `pause` and `resume` events map to didEnterBackground and willEnterForeground respectively. (https://capacitorjs.com/docs/apis/app)
- Because `appStateChange` tracks *focus*, `isActive: true` re-fires after Control Center, a call banner, or lock/unlock without any real backgrounding — it is a noisy foreground trigger. (https://developer.apple.com/tutorials/data/documentation/uikit/uiapplication/didbecomeactivenotification.json)
- `resume` (willEnterForeground) is the true background-to-foreground edge and also posts at a cold launch into the foreground, so it is the right sync trigger; a background launch (silent push) does not fire it until the app actually comes forward. (https://developer.apple.com/tutorials/data/documentation/uikit/uiapplication/willenterforegroundnotification.json)
- (Source-level) The iOS App plugin emits `appStateChange`, `pause`, and `resume` without `retainUntilConsumed`, so any notification that fires before the JS listener is registered (launch-time didBecomeActive / willEnterForeground) is dropped; startup must call `App.getState()` (which resolves `isActive` from `UIApplication.shared.applicationState == .active`) and run its own initial sync rather than rely on the event. (https://raw.githubusercontent.com/ionic-team/capacitor-plugins/main/app/ios/Sources/AppPlugin/AppPlugin.swift)
- @capacitor/preferences is documented as a lightweight key/value store backed by UserDefaults on iOS; the docs state no numeric size limit but explicitly say it is not for large data, and values are strings only (JSON via stringify/parse). (https://capacitorjs.com/docs/apis/preferences)
- (Source-level) On iOS every Preferences key lands in `UserDefaults.standard` under the prefix `CapacitorStorage.` (the default group), and `keys()` enumerates `dictionaryRepresentation()` filtered by that prefix — so a few-hundred-KB JSON string sits inside the app's single standard defaults plist alongside everything else. (https://raw.githubusercontent.com/ionic-team/capacitor-plugins/main/preferences/ios/Sources/PreferencesPlugin/Preferences.swift)
- Apple's only documented UserDefaults size enforcement is on tvOS (512 KB warning, termination at 1 MB); iOS has no documented ceiling and no size-exceeded notification — which is 'no documented enforcement', not 'no limit'. (https://developer.apple.com/tutorials/data/documentation/foundation/userdefaults/sizelimitexceedednotification.json)
- `Capacitor.convertFileSrc()` rewrites a device path into the WebView's own origin using the `_capacitor_file_` prefix; the capacitorjs.com page only shows the Android form (`http://localhost/_capacitor_file_/...`), and its code comment contradicts its own prose by omitting the prefix. (https://capacitorjs.com/docs/basics/utilities)
- (Source-level) On iOS the output is `capacitor://localhost/_capacitor_file_<absolute path>` (default scheme `capacitor`, host `localhost`), and the native WKURLSchemeHandler strips the prefix and reads the raw path with `Data(contentsOf:)` with no bundle-containment check — so files in the app's Documents folder (or anywhere the process can read) render in `<img>`; MIME comes from UTType, HTTP Range is honored. Caveat: the rewrite is plain string concatenation with no percent-encoding, so a filename containing `?` or `#` produces a URL whose path is truncated before it reaches the handler. (https://raw.githubusercontent.com/ionic-team/capacitor/main/ios/Capacitor/Capacitor/WebViewAssetHandler.swift)
- The Filesystem plugin documents the iOS directory mapping needed to build those paths: `Directory.Documents` and `Directory.Data` both resolve to the app's Documents folder on iOS, `Directory.Library` to Library (a sensible home for per-device sync state written as a JSON file instead of Preferences); `getUri()` returns the full `file://` URI to hand to convertFileSrc, and full `file://` paths are accepted directly. (https://capacitorjs.com/docs/apis/filesystem)

**Verdict:** Borrow all three, with adjustments: trigger sync on App `resume` (the real background→foreground edge) plus an explicit startup sync via `getState()`, not on `appStateChange` (focus-noisy, and launch-time events are dropped); keep Preferences for tiny values (device token, vault id) and write the few-hundred-KB sync state as a JSON file under `Directory.Library` via Filesystem, since the docs call Preferences "lightweight"/"not a local database" and iOS has no documented UserDefaults ceiling either way; render Nexus images with `Capacitor.convertFileSrc((await Filesystem.getUri({directory: Directory.Documents, path})).uri)` — the iOS handler serves any readable absolute path, Documents included, but avoid `?`/`#` in filenames.

**Unresolved:** capacitorjs.com never states the iOS `convertFileSrc` URL form or that it serves files outside the bundle — both are read from Capacitor source (native-bridge.ts, CapacitorBridge.swift, WebViewAssetHandler.swift), as is the no-percent-encoding caveat. Neither Capacitor nor Apple publishes an iOS UserDefaults size ceiling or a performance figure for hundreds-of-KB values; only the tvOS 512 KB / 1 MB numbers are documented, so "a few hundred KB works on iOS" is an inference from the absence of enforcement, not a fetched claim. Apple's UserDefaults overview prose on caching/plist serialization did not surface beyond the property-list-types sentence. Whether Capacitor's JS listener registration reliably beats the launch-time didBecomeActive/willEnterForeground notifications is not documented anywhere fetched — hence the `getState()` recommendation rather than a claim about ordering.

#### Files App Exposure

- UIFileSharingEnabled=YES exposes the app's Documents folder to the user; default is NO. It is a Documents-folder switch, not a per-file one. (https://developer.apple.com/documentation/bundleresources/information-property-list/uifilesharingenabled)
- LSSupportsOpeningDocumentsInPlace=YES lets the app open originals (not copies) from file providers. The current reference page carries only the abstract — no discussion, no mention of the Files app or of UIFileSharingEnabled — so the pairing behavior must be sourced from the archived Key Reference. (https://developer.apple.com/documentation/bundleresources/information-property-list/lssupportsopeningdocumentsinplace)
- Setting BOTH keys to YES (iOS 11+) makes the local file provider expose the entire Documents directory in the Files app and document browsers, and other apps/users can open AND edit those files in place — and Apple explicitly says in-place-openable documents can be modified by other processes at any time, so you MUST coordinate access via UIDocument or NSFilePresenter+NSFileCoordinator. (https://developer.apple.com/library/archive/documentation/General/Reference/InfoPlistKeyReference/Articles/LaunchServicesKeys.html)
- File coordination is cooperative only: an NSFilePresenter is notified solely of changes made through an NSFileCoordinator; raw read/write calls (which is what Capacitor does) neither notify presenters nor wait for coordinated writers. (https://developer.apple.com/documentation/foundation/nsfilepresenter)
- Apple tells the OTHER side (any app editing your Documents files via the picker/Files) to always use NSFileCoordinator for reads/writes and an NSFilePresenter while displaying — so third-party editors writing into your Nexus will typically be coordinated writers; your app only benefits from that if its own access is coordinated too. (https://developer.apple.com/documentation/uikit/uidocumentpickerviewcontroller)
- iOS-specific presenter/coordinator obligations: a registered NSFilePresenter must be removed when the app backgrounds (or the system may kill the app to break a deadlock) and re-added on foreground; every coordinated read/write auto-starts a background task, a suspended waiter gets NSUserCancelledError, an expired task terminates the process; coordinators are per-operation and single-thread. (https://developer.apple.com/documentation/foundation/nsfilecoordinator)
- Apple's general carve-out — files private to your sandbox (Application Support, Caches, tmp) don't need coordination or presenters — does not cover a Documents folder you have chosen to expose in place; Apple's own list of what to monitor is 'user documents' and managed media directories, which is exactly what an exposed Nexus is. (https://developer.apple.com/library/archive/documentation/FileManagement/Conceptual/FileSystemProgrammingGuide/FileCoordinators/FileCoordinators.html)
- Capacitor's Filesystem docs require exactly these two keys for Files-app visibility, and on iOS Directory.Data, External, ExternalStorage and ExternalCache all alias the Documents directory — so storing the Nexus under Directory.Data still exposes it; only Library, LibraryNoCloud and Temporary stay out of Files. (https://capacitorjs.com/docs/apis/filesystem)
- @capacitor/filesystem 8.1.3's iOS implementation performs NO file coordination and NON-atomic writes: the plugin delegates to IONFilesystemLib, whose saveFile calls Data.write(to:) with default options (Apple documents the default as [] — not .atomic) or String.write(to:atomically:false,...), and appendData opens a FileHandle, seeks to end and writes. Neither repository contains a single reference to NSFileCoordinator or NSFilePresenter. (https://raw.githubusercontent.com/ionic-team/ion-ios-filesystem/main/IONFilesystemLib/IONFILEManager.swift)
- Documents/ is by definition the user-exposed, iCloud/iTunes-backed-up directory; anything you don't want the user to see or edit (e.g. .nexus/ config, .trash/ bundles) belongs under Library/ — Apple's QA1699 says the same for file-sharing apps and recommends a Library subfolder such as 'Private Documents'. UISupportsDocumentBrowser is the document-browser-app variant of the same exposure ('other apps to open and edit the files stored in your app's Documents folder') and additionally lets users set the app as a default save location in Settings. (https://developer.apple.com/library/archive/documentation/FileManagement/Conceptual/FileSystemProgrammingGuide/FileSystemOverview/FileSystemOverview.html)

**Verdict:** Borrow both keys (they are the documented pair that surfaces Documents in Files on iOS 11+), but with eyes open: Apple mandates NSFileCoordinator/NSFilePresenter for anything editable in place and Capacitor Filesystem 8.1.3 does neither (raw, non-atomic Data.write / FileHandle appends) — so either ship a thin native plugin that wraps writes in coordinate(writingItemAt:) and registers a directory NSFilePresenter (removed on background) to learn of external edits, or consciously accept that Files-app/third-party edits race with the app and rely on most-recent-wins; either way keep .nexus/ and .trash/ out of Documents (Library/LibraryNoCloud) unless exposing them is intended.

**Unresolved:** (1) Whether the Files app hides dot-prefixed folders (.nexus/, .trash/) inside an exposed Documents directory — no Apple documentation found either way; only the general 'Documents should contain only what you wish to expose' guidance. (2) Whether the iOS local file provider / Files app performs any locking beyond cooperative coordination — Apple documents coordination as notification-based and explicitly says uncoordinated low-level writes bypass it; nothing fetched describes how the provider behaves when a Capacitor write interleaves with a coordinated external write, so interleaving/partial-read outcomes are undocumented. (3) The current LSSupportsOpeningDocumentsInPlace reference page has no discussion text; the pairing-with-UIFileSharingEnabled rule and the 'you must coordinate' mandate exist only in the archived Info.plist Key Reference (marked no longer updated) and are corroborated by Capacitor's docs — I could not find a current-generation Apple page restating them (WWDC 2017/229 and 2018/216 transcripts were not retrievable as text). (4) iOS Simulator behavior for Files-app exposure is not documented anywhere I fetched. (5) No JS-reachable coordination API exists in the plugin (verified by absence in source, not by a doc statement); a custom native plugin would be required to add it.

#### SPM Project Layout

- Folder layout: `npx cap add ios` (SPM) extracts the CLI's shipped `ios-spm-template.tar.gz` into `ios/`, producing `ios/.gitignore`, `ios/debug.xcconfig`, `ios/App/App.xcodeproj` (with an internal `project.xcworkspace/xcshareddata/IDEWorkspaceChecks.plist` only), `ios/App/App/{AppDelegate.swift, SceneDelegate.swift, Info.plist, Assets.xcassets, Base.lproj/{Main,LaunchScreen}.storyboard}`, and `ios/App/CapApp-SPM/{Package.swift, README.md, .gitignore, Sources/CapApp-SPM/CapApp-SPM.swift}`. There is no top-level `App.xcworkspace`, no `Podfile`. The xcodeproj references the package as a local package. (https://registry.npmjs.org/@capacitor/cli/-/cli-8.5.1.tgz)
- `CapApp-SPM` is a CLI-owned 'Base SPM' package that aggregates every plugin dependency; do not hand-edit it. (https://capacitorjs.com/docs/ios/spm)
- No doc page prescribes what to commit; the only evidence is the template's two `.gitignore` files. Generated (ignored) set: `App/App/public` (the copied web bundle), `App/App/capacitor.config.json`, `App/App/config.xml`, `App/build`, `App/Pods`, `App/output`, `DerivedData`, `xcuserdata`, `capacitor-cordova-ios-plugins`; and inside `CapApp-SPM/`: `/.build`, `/Packages`, `/*.xcodeproj`, `xcuserdata/`, `DerivedData/`, `.swiftpm/config/registries.json`, `.swiftpm/xcode/package.xcworkspace/contents.xcworkspacedata`, `.netrc`, `.DS_Store`. Everything else under `ios/` (xcodeproj, app sources, `debug.xcconfig`, `CapApp-SPM/Package.swift` and its stub source) is intended to be tracked. (https://registry.npmjs.org/@capacitor/cli/-/cli-8.5.1.tgz)
- `ios/App/CapApp-SPM/Package.swift` is tracked but rewritten by the CLI on every `sync`/`update`: the shipped template pins `capacitor-swift-pm` with `from: "8.0.0"`, and `generatePackageText` regenerates the whole file with `exact: "<installed @capacitor/ios version>"` plus one `.package(name:, path:)` entry per plugin (relative to `ios/App/App.xcodeproj`'s directory) and a matching `.product` in the target's dependencies. Expect a diff after every Capacitor or plugin bump, and commit it. (https://registry.npmjs.org/@capacitor/cli/-/cli-8.5.1.tgz)
- On Capacitor 8 the SPM template is the default; `--packagemanager SPM` is accepted but redundant, and the flag only changes behavior when set to `CocoaPods`. The SPM guide still shows the explicit flag. (https://capacitorjs.com/docs/updating/8-0)
- Requirements for Capacitor 8 iOS: Xcode 26.0+, iOS 15+ deployment target, Node 22+, macOS. CocoaPods and Homebrew are optional when using SPM. The template pins `IPHONEOS_DEPLOYMENT_TARGET = 15.0`, `SWIFT_VERSION = 5.0`, `objectVersion = 60`. (https://capacitorjs.com/docs/getting-started/environment-setup)
- The loop: build the web bundle → `npx cap add ios` (runs `sync` automatically if `webDir` already exists, otherwise warns) → `npx cap sync` = `copy` (web bundle + `capacitor.config.json` into `ios/App/App/public` and `ios/App/App/`) then `update` (rewrites `CapApp-SPM/Package.swift`) → `npx cap open ios` → `npx cap run ios` (sync, then `xcrun xcodebuild -project App.xcodeproj -scheme App -configuration Debug -destination id=<target> -derivedDataPath ios/DerivedData/<target>`, then native-run deploys the built `.app`). Useful flags: `--list`, `--target <id>`, `--target-name "iPhone 17 Pro"`, `--no-sync`, `--scheme`, `--configuration`. (https://capacitorjs.com/docs/cli/commands/run)
- The iOS overview page is CocoaPods-era text and contradicts the SPM layout: it says projects are managed with CocoaPods and suggests `open ios/App/App.xcworkspace`. Under SPM there is no `App.xcworkspace`; `npx cap open ios` opens `ios/App/App.xcodeproj`, and manual opening should target the xcodeproj. The CLI code is the tiebreak. (https://capacitorjs.com/docs/ios)
- The SPM dependency chain is `CapApp-SPM` (local) → `ionic-team/capacitor-swift-pm` (tagged per Capacitor release, e.g. 8.5.1), which is a `swift-tools-version:5.3` package exposing two products, `Capacitor` and `Cordova`, each a prebuilt binary xcframework fetched from the GitHub release. The `main` branch of that repo is stale (6.2.2), which is why the CLI pins `exact:` to the tag. (https://raw.githubusercontent.com/ionic-team/capacitor-swift-pm/8.5.1/Package.swift)
- Migrating an existing CocoaPods project to SPM is either delete-`ios/`-and-re-add (only safe if Xcode was never hand-edited) or `npx cap spm-migration-assistant`, which removes `Podfile`, `App.xcworkspace`, `Podfile.lock`, creates `CapApp-SPM`, generates `Package.swift`, and adds `debug.xcconfig`; two manual Xcode steps remain (add the local package, attach `debug.xcconfig`). After adding plugins, 'reset package caches' in Xcode is the documented fix for stale resolution. (https://capacitorjs.com/docs/ios/spm)

**Verdict:** Borrow: commit `ios/` wholesale (including the CLI-owned `CapApp-SPM/Package.swift`, which `cap sync` rewrites with an `exact:` pin every bump), let the template's `.gitignore` drop `App/App/public`, `capacitor.config.json`, `DerivedData`, `xcuserdata`; open and build `ios/App/App.xcodeproj` (no workspace exists under SPM, the docs/ios page is stale on that); `--packagemanager SPM` is optional on Capacitor 8; the loop is `npm run build` → `npx cap sync` → `npx cap run ios --target <sim id>` or `npx cap open ios`.

**Unresolved:** No Capacitor doc page states a commit policy; the committed-vs-generated split above is inferred from the template's `.gitignore` files. Where Xcode writes `Package.resolved` for an `.xcodeproj` with a local package (and whether to commit it) is not in any fetched source. Whether the `docs/ios` page's `App.xcworkspace`/CocoaPods wording is deliberately CocoaPods-only or simply unrevised is unknown. Nothing fetched addresses running on the Simulator without a paid Apple Developer account. Xcode 26.6 specifically is not named anywhere; the floor is "Xcode 26.0+". The GitHub source for the docs pages (raw.githubusercontent.com/ionic-team/capacitor-docs) 404'd for the SPM, iOS, and getting-started pages, so only the rendered capacitorjs.com pages were read.
