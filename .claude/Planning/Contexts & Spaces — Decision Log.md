## Contexts & Spaces — Decision Log

> **Status: RATIFIED** — Nathan signed off after three adversarial review rounds (all findings verified and folded). No open items — the Obsidian-visibility question resolved to the Sapphire CSS shield (A-8). The implementation plan lives alongside this log.

### Frame

- **Purpose:** Redesign the Contexts layer from a fixed three-tier tag list into a user-manageable organization system — **Contexts** (the groups, e.g. Areas/Topics/Projects) containing **Spaces** (the individual members), each Space a SurfacePM block surface with its own settings, color, and linked-entity awareness.
- **Core Value:** Contexts become something you *manage and live in* — creatable groups, dashboard-capable Spaces — rather than a fixed taxonomy you can only tag.
- **Success Criteria:** Create/rename/delete Contexts and Spaces from the sidebar; a Space opens as a block surface (2×2 blank tiles on creation); Space chips carry their assigned color everywhere; every Space can immediately enumerate the Pages/Tasks/Events linking to it.

### Decisions

#### A — Vocabulary & Model

- **A-1:** [confirmed] **Context** = the group (formerly "tier") — Areas, Topics, Projects are the *default* Contexts. **Space** = an individual member (a single area/topic/project). Vocabulary replaces tier-speak across surfaces and docs.
- **A-2:** [confirmed] Contexts are **user-defined in v1** — created/managed like Properties: a nexus-wide registry (`contexts.json`), "a property-type kinda thing." Each Context manifests as its own relation-property whose picker holds its Spaces.
- **A-3:** [confirmed] The default three (Areas/Topics/Projects) are **pre-configured but user-managed** — seeded into the registry on nexus creation, then ordinary entries: renamable, reorderable, hideable, deletable like any user-created Context. One mechanism, no protected-entry special case.
- **A-4:** [confirmed] **Title-keyed root frontmatter.** A context link is `"[<Context Title>]": [<Space Name>, ...]` at the frontmatter/JSON root (bracket sigil per A-8) — no wrapper map, no ULIDs, no `$rel` tag. The registry (`contexts.json`) carries the ids; member files carry only titles; the read path resolves title → id through the registry. Titles therefore become file-level identity: **Context titles are unique nexus-wide, Space names unique within their Context** (the latter already enforced on disk — same-context folder siblings can't collide). Replaces `tier1/2/3` via a one-time migration (ULIDs resolved to titles through the sidecars).
- **A-7:** [confirmed] **Renames cascade.** Renaming a Context or a Space rewrites its key/value across every tagged member file — the established value=title precedent (Select/Status option renames cascade; connection renames cascade). Ids in the registry never change, so internal references (index, order, settings) stay stable.
- **A-8:** [confirmed] **Context keys wear literal brackets:** `"[Projects]": [Pommora]`. YAML requires the bracketed key quoted on disk (unquoted `[…]:` parses as a flow-sequence complex key — Pommora always writes it quoted; an unquoted hand-write simply never registers). Brackets partition the keyspace — no collision with modeled root keys is possible, so no reserved-name blocklist; the one new rule is that Context titles can't contain `[` or `]`. The bracket also self-describes the key's kind to any reader, and shields against casual Obsidian property-editor collisions (Obsidian's bare `Projects` is a different key by construction). **Obsidian visibility (live-tested + researched):** Obsidian's Properties panel displays every top-level key — bracketed, nested, any character — so no natively-ignorable frontmatter syntax exists (nested objects still render as an inert unsupported row). The shield is **Sapphire**: it injects one prefix-matched CSS rule (`.metadata-property[data-property-key^="["] { display: none }`) hiding every context key from the panel — the bracket sigil is exactly what makes one rule cover them all — with chip-rendering as its later ceiling; plugin-less vaults get the same rule as a documented one-line CSS snippet. A-10's validation remains the data-level guard either way.
- **A-9:** [confirmed] Values are always YAML arrays (multi-value stays, as today's tiers), even single-element.
- **A-10:** [confirmed] **Registry-validated resolution.** A root key registers as a context link only when the key exactly matches a registry Context title AND each value exactly matches an approved Space name in that Context — fragile outside edits (a bare `Projects:` from Obsidian, a typo'd value) never register. Validation is an in-memory registry-map lookup during the existing parse — no added queries or lookup sweeps. Outside edits with *valid* titles DO register (the agent-legible workflow working as intended).
- **A-11:** [confirmed] **Inert-on-read; the next real write repairs, never wholesale-drops.** Invalid entries never register (invisible to UI/picker/index), the read path stays write-free, and normalization happens on the file's next real write — where the directive is *fix it, don't just drop the space*. Claude's proposed repair semantics: (1) an unambiguous near-match (case/whitespace-only difference from an approved Space title) **repairs to the canonical title**; (2) per-value surgery — valid sibling values and the key itself always survive; (3) a genuinely unknown value (no match) **drops on the file's next real write** — it never registers while present, and the rewrite discards it. No fuzzy-match repair beyond case/whitespace, ever. (Until that write happens, resolution stays title-based — so creating the Space it names before any rewrite still registers it.)
- **A-5:** [confirmed] **No pre-assignment, no empties.** A Context is "on" an entity exactly when the entity holds a value for it — setting the value *is* the assignment; clearing it removes the key entirely. The properties no-empties rule applies in full; the tier empty-array exception (`area: []` surviving a clear) is **abolished** under the new model.
- **A-6:** [confirmed] Availability is universal via **the same mechanism as today** — every registry Context is automatically part of every Collection's effective schema (the synthesized-relation merge, generalized from `_tier1/2/3` to one per registry entry) and offered through the picker; no per-Collection opt-in gate. Only on-disk *presence* is value-driven (A-5).

- **D-2:** [confirmed] **On-disk layout generalizes to one root:** `.nexus/contexts.json` (the registry: per-Context id, title, singular, icon, order) + `.nexus/contexts/<Context Title>/<Space Title>/_space.json` (per-Space id, icon?, color?, banner?, blocks/layout/blocks_locked, its own bracketed relation keys, modified_at — the `tier` number field dies; membership comes from the parent folder). The seeded three migrate out of `.nexus/areas|topics|projects/`; `area_order/topic_order/project_order` in state.json generalize to per-Context space orders.
- **D-3:** [confirmed] **Deletion generalizes today's cascade:** deleting a Space unlinks its title from every tagged file then trashes its folder (recoverable); deleting a Context unlinks its bracketed key from every file, trashes its folder tree, and removes its registry entry.
- **D-4:** [confirmed] **Rename cascades ride existing machinery:** a Space rename = folder rename + value rewrite across tagged files; a Context rename = registry + folder rename + key rewrite across tagged files (the connection-rename cascade pattern, batched + serialized like today's).
- **D-5:** [confirmed] **Agenda parity:** Tasks/Events carry the same bracketed title keys at their JSON root — one shape across all three entity kinds, as `tierN` is today.
- **D-6:** [confirmed] The YAML seam is safe — `doc.set("[Projects]", […])` auto-quotes and re-parses to the exact key (verified against the bundled `eemeli/yaml`). A-8's mechanical risk is closed.
- **D-7:** [confirmed] **The title cascade must be synchronous and spans THREE file scopes.** Context/Space renames don't cascade today (membership is id-keyed) and the existing `renameCascade` walks `.md` bodies only — so the title cascade is net-new work covering, each atomically: (a) `.md` frontmatter bracketed keys, (b) Task/Event `*.json` root keys, (c) `_space.json` root keys under `.nexus/contexts/`. It cannot be lazy: a stale title is unknown to A-10 and A-11 then *drops it* — silent data loss. As part of this, the agenda/sidecar writers join the per-file-lock + `writeEcho` regime (today only `.md` writes hold it — widening without the lock re-opens the F1 race class for those kinds).
- **D-7a:** [confirmed] **Crash contract — the pending-rename journal.** Ordering: a `.nexus/` journal record `{contextId, oldTitle, newTitle}` commits FIRST → the three-scope cascade runs → the registry title commits → the journal clears. A crash at any point leaves a journal that **replays idempotently on next open** — an exact recorded old→new mapping, the one heal A-11's no-fuzzy-match rule permits (it's a record, not a guess). Without this, both registry-first and files-first orderings leave a window where A-11 eats valid tags unrecoverably (the option-rename precedent's re-run recovery does NOT transfer — it survives only because unmatched option values *persist*, which A-11 forbids for contexts).
- **D-7b:** [confirmed] **The journal is skip-aware and crash-only.** The cascade records any file it could not read; the journal does **not** clear while skipped files remain — it survives for retry on subsequent opens. The net-new JSON-scope cascade writer is built **skip-on-unreadable, never fallback-to-empty** (`mutateJson`'s missing-file fallback would clobber a transiently-unreadable `_space.json` — an evicted iCloud placeholder — down to a near-empty object). Replay **re-verifies before cascading** — the registry still maps `oldTitle → contextId` and no other Context has claimed `oldTitle` since (a freed, re-minted title discards the journal rather than hijacking the new entity). And a **live** (non-crash) cascade failure rolls back AND clears the journal — rollback means abort; the journal exists only to complete a crash forward.
- **D-9a:** [confirmed] The reconcile's trigger scope is **per-file, inside that file's own next governed write** — never a sweep. Rename orphans are healed exclusively by journal replay; the reconcile never guesses.
- **D-8:** [confirmed] Dangling values from a deleted Space strip silently (matching today's silent `unlinkTier` id-strip) — deletion already runs the unlink cascade (D-3), so orphans only arise from outside edits, which A-10/A-11 govern.
- **D-9:** [confirmed] Validation lives in a runtime reconcile pass against the in-memory registry, not the static zod schema (per-nexus dynamic keys can't be schema fields; `looseObject` already carries bracketed keys through as foreign data today).

### Core (must-have)

- **The registry + layout:** `contexts.json` (id, title, singular, icon, order) · `.nexus/contexts/<Context>/<Space>/_space.json` · the one-time migration (labels seed the three Contexts' titles; folders move; `tierN` ULIDs rewrite to bracketed title keys; index rebuilds).
- **The value model:** bracketed quoted title keys at every entity root (Pages, Tasks, Events, Spaces) · registry-validated resolution, in-memory, at parse · no-empties · inert-on-read with repair-case/drop-unknown on next real write, per-value · ids in memory, titles only at the write boundary.
- **Cascades:** synchronous title cascades on Context/Space rename across all three file scopes — `.md` frontmatter, agenda JSON, `_space.json` (transactional + writeEcho-suppressed; agenda/sidecar writers join the per-file lock); unlink-then-trash deletes with the same three-scope reach.
- **Per-node context values:** the walk retains the raw bracketed keys its parses already read and resolves them onto each entity's own node (`_space.json` the one new input); reverse lookups derive on-demand at their first consumer; SQLite stays the off-read-path graph accelerator, still written with all four source kinds.
- **The pipeline generalized:** dynamic context columns in every view, hidden by default through one DRY-ed mechanism · per-Context pickers (Spaces in sidebar order) · per-Space chip color via the ten chip solids (Area enum migrated, no accent, unset = neutral Default) · `context_links` carrying Space sources for future graph acceleration.
- **Sidebar:** dynamic disclosure groups (persisted per-Context, new mounts open) · group-header menu New (Singular) · Settings · Rename · Delete · **HoverCreate** (reusable) as the sole New Context entry · background right-click dead · optimistic create + focused rename at both levels.
- **SpaceView:** second BlockHost with dynamic host enumeration · 2×2 markdown seed at creation only · per-Space lock · banner above, Subfield active-but-unpopulated below · the blank grid-icon toolbar dropdown left of the trio.
- **Settings surfaces:** the blank reusable floating chassis FIRST (Nathan live-drives its UIX), then the Context/Space Settings windows — (Icon)(Title) heading, Space color at BottomRow-right, Space relation rows (G-4), lock footer — and SpacePanel off the toolbar settings button with color at its SidePane bottom-left.
- **The assign-reveal flow** unified across properties and contexts: hidden until assigned → auto-open picker → `X: —` when blank (session-only) → right-click Remove.
