## PM-108 Webpage Integration — Decision Log

### Frame
- **Purpose:** Version 1 of webpage/internet integration into Pommora — the editor learns to embed live webpages the way it embeds Pages, the right-click menu is reorganized around it, and the app decides how external links open.
- **Core Value:** A webpage, addressed by URL, renders as a live tile inside a Page body — making Pommora a surface the web can sit inside rather than a thing links lead away from.
- **Success Criteria:** A URL embedded on its own line loads and displays as a tile on the shared embed framework; its hover-title opens the site; the right-click menu reads Insert / Format / Embed / Heading / Lists; nothing about page embeds, tables, or the existing menu behavior regresses.

- `shared/blocks.ts` — the block-surface tile payload union (`BlockEntry`), `looseObject` so future tile types survive rewrites; where a dashboard webpage tile would eventually join.
- **Webview clipping spike (scratchpad, 08-18-2026, this repo's Electron 42.4)** — a `<webview>` inside an `overflow:auto` scroller in an `overflow:hidden` 16px-radius tile: renders and clips correctly (rounded corners included) while the tile is fully inside the scrollport, but **bleeds outside its bounds once the tile is partially scrolled past the container edge** — guest content paints above/below the tile border. Screenshot-verified. A naive inline webview is disqualified; inline liveness requires a visibility-managed webview (live only while fully visible, a static face otherwise) or a different mechanism. A second spike verified the hide path: a guest survives `display:none` and `visibility:hidden` with its JS state intact — hiding, not destroying, is viable for the static-face swap.
- Second research pass (app survey) — **no shipping app puts webviews inline in a scrolling editor.** Obsidian's audited Web viewer is tabs/Canvas only; its inline mechanism is a plain typed `<iframe>`. VS Code notebooks use one overlay web surface with per-cell position syncing. Notion/Tana/Anytype allow live embeds only for allowlisted providers via iframes; arbitrary URLs degrade to bookmark cards. electron/electron#9147 matches the spike's clipping result.
- Electron research (docs + live header checks, 08-18-2026) — three mechanisms exist: `<iframe>`, `<webview>`, WebContentsView (BrowserView is a deprecated shim over the latter). **WebContentsView is main-owned and cannot be clipped or scrolled by renderer DOM — impossible for inline tiles; right for a surface that owns a whole region.** `<iframe>` clips fine but framing is blocked by nearly every login-bearing site (Google/GitHub/X/NYT/Notion all send XFO deny; YouTube's `/embed` and Wikipedia allow), shares the renderer process, and third-party-cookie rules break iframe logins regardless — header-stripping via `onHeadersReceived` is a known trick but whack-a-mole and wrong as the primary mechanism. **`<webview>` is the only process-isolated mechanism that is also a real DOM element** (OOPIF — lays out, scrolls, clips with the document); Electron's docs discourage it, yet it is exactly what Obsidian's Cure53-audited Web viewer ships. Requires `webviewTag: true` on the host window; coexists with `sandbox`/`contextIsolation`; ~1 renderer process (50–150MB+) per live guest, so many-embeds surfaces lazy-attach near-viewport with snapshot placeholders. Sessions: a shared `persist:` partition gives one sign-in across every embed surface, surviving restarts; Google blocks embedded sign-in through server-side policy detection (naive Chrome-UA spoofing stopped sufficing ~2021) — the proven-in-production recipe is Ferdium's surgical UA treatment, best-effort by nature (→ D-2). Hover previews: live rendering per hover is cost-prohibitive; the sane default is a metadata card (title/favicon/og:image via main-process GET) — what Notion/Slack/Discord do.

### Decisions
#### A — Menu Redesign
- **A-1:** [confirmed] Submenu order becomes **Insert / Format / Embed / Heading / Lists** — Insert moves to the top, Embed is the new third row.
- **A-2:** [confirmed] Embed ▸ holds **Webpage** and **Internal Page**; Insert ▸ loses its Page item (it becomes Embed ▸ Internal Page).
- **A-3:** [confirmed] Insert ▸ keeps Blockquote / Horizontal Rule / Code Block / Callout / Table after Page leaves — the submenu stays substantive, so moving it to the top isn't hollow.
- **A-3a:** [confirmed] The conditional top-level **Insert Link** item keeps its seat above the reordered submenu block.
- **A-4:** [confirmed] The submenu label is **Embed**.

#### B — Webpage Embed
- **B-1:** [confirmed] A webpage embeds only when its syntax is the only thing on its line — same rule as page embeds.
- **B-2:** [confirmed] The tile's hover-title is a clickable link that opens the page per the open-in knob (→ C-2a). It's a small new component wearing the same hover-reveal treatment as the page embed's crumb — not a reuse of `EmbedCrumbs`, which resolves a page id through the tree and whose reveal CSS is scoped to the page-embed payload.
- **B-3:** [confirmed] The tile's title is **display-only** (simplification pass, Nathan-ratified 08-18): the tile resolves what it shows at render — a hand-written on-disk label wins outright; an empty label derives per `defaultLinkFormat` through the *existing* fetched-title display path the table cells and link properties already use (`linkDisplayText` + the `linkTitles` store/cache, domain placeholder until a Page Title fetch lands or when it never does). **Nothing is ever written into the document** — the fill one-shot, the deferred whole-line swap, and their undo/escape machinery are all deleted with it. Door-created embeds rest on disk as `![](url)`; a user titles one by editing the label themselves.
- **B-3a:** [confirmed] The embed *detector* reads an empty-label-tolerant grammar (`MD_LINK`-shaped): the shared `markdownLinkRegex` requires a 1+-character label (its cap is ReDoS-load-bearing and stays), so `![](url)` — the insert door's own output — is invisible to it. The grammar's compose half (`![${escapeAlias(label)}](${url})`) remains the only assembly path for the few writers that remain (the grip re-aim), since the house link serializer emits no bang and collapses an empty alias to the bare URL.
- **B-4:** [confirmed] The on-disk syntax is **`![Title](url)`** lone on its line — the CommonMark embed-a-resource form, exclamation mark confirmed. Images are done "the other way" (the `![[…]]` wiki-embed form) in the future, dissolving the discriminator concern: bang-paren with a scheme-bearing URL is a webpage embed, wiki-embed is pages (later files/images), and a plain `[Title](url)` link is never an embed. Superseded candidate, for provenance:
  - `![[https://…]]` — rode the existing lone-line embed grammar and scheme rule, but Nathan assigned the wiki-embed form to images/files instead.
- **B-5:** [confirmed] The tile mechanism is a **visibility-managed `<webview>` tag**. The spike proved a webview clips and rounds correctly while its tile is fully inside the scrollport but bleeds outside its bounds when partially scrolled past the container edge — so the webview is live only while the tile is fully visible (plus margin), swapping to a static face (captured snapshot or loading face) at the edges and off-screen, VS Code-notebook style but per-tile. Swaps fire on intersection transitions, not per scroll frame, honoring the no-expensive-work-on-every-scroll rule. Entails `webviewTag: true` on the main window (sandbox/contextIsolation kept), `will-attach-webview` validation, no webview preloads, and the shared `persist:` partition. Alternatives on the table if this proves heavy: iframe-with-header-stripping (clips perfectly, but framing-blocked sites and unreliable iframe logins make it site-dependent), or a static bookmark-face tile with liveness only in the in-app browser (Notion's model — rejected as V1's primary since Nathan wants pages genuinely loaded in place).
- **B-6:** [confirmed] The grip menu carries a source-style arm above Delete: a menu item opening the `TextPicker` link popover (what Nathan meant by "LinkInput") anchored at the tile, to re-aim the URL. Mechanics pinned by review: the grip action union gains a form the renderer answers by opening the popover (no current grip action opens UI after the native menu); the commit **replaces the whole block span** in one dispatch exactly as Page Source ▸ does, writing the bare `![](newUrl)` form — the display layer derives the new title (B-3), and any old hand-written label is dropped since it described a different page; and the persisted tile height migrates to the new URL key on re-aim so the tile doesn't snap to default.
- **B-7:** [confirmed] The Embed ▸ Webpage door types the fenced empty syntax and **seats the caret inside the empty `()` target** — the user types or pastes the URL raw. Two guards make this door sound (adversarial finds, verified):
  - The paste/⌘K link-rewriter declines when the caret sits inside an existing link's destination span — otherwise G-1's always-on formatting writes a *nested* link into the target (`![]([domain](url))`). This also fixes ⌘K's pre-existing twin of the same bug. The guard reads **B-3a's empty-tolerant grammar**, not the tokenizer's — every shipped link grammar refuses `![]()` (empty label or empty destination), so a tokenizer-based guard would never fire at the very door it protects.
  - The tile claim is **formation-gated, not selection-dependent** (round-2 refinement): a line claims when it first satisfies lone+valid *while the selection is not on it* — so typing never tiles the line mid-keystroke (`isValidLink` passes prefixes like `https://example.c`) — but once formed, **the tile persists regardless of caret**, preserving the page-embed invariant that settled raw syntax never shows at any caret position. The trigger set is complete on three events — **doc change, editor mount, and selection-departure** — each checking only unclaimed candidate lines (a bounded, near-always-empty set, not a per-caret-move rebuild). The *predicate* ("selection not on the line") is what keeps typing from tiling mid-keystroke; the triggers are what reach candidates the selection was never on (a multi-line paste, an undo, a fresh mount — where the caret seats at 0 and every existing tile must still form).

#### C — Link Opening & Settings
- **C-1:** [confirmed] The in-app browser ships in V1, and Files & Links gains the "open external links in-app vs system browser" knob. Plumbing: one `Personalization` key, one coercion line, one row, and the branch lives at the **three renderer call sites** — the in-app browser is an in-renderer pane, so a main-side `link:open` branch would need a push channel back to the renderer anyway (review correction: the two seams are not equivalent).
- **C-2:** [confirmed] The browser is a flavor of the same floating PreviewPane window: the toolbar's left promote glyph (full-page open) is absent, back/forward glyphs take the left side, and the centered floating title is the link itself. A `<webview>` fills the body — it owns a whole static region there, so the tile's clipping constraint doesn't apply (window-drag repaint behavior to be verified in build).
- **C-2a:** [confirmed] A webpage tile's hover-title click respects the open-in knob; inside the in-app browser, clicking the floating title escalates outward — it opens the page in the external browser. The floating title tracks the **current** page as the guest navigates (back/forward included), and escalation opens that current URL, not the origin.
- **C-3:** [confirmed] The security posture, stated truthfully (the earlier phrasing contradicted B-5/C-2): the main window *does* gain `webviewTag: true`, and every webview lives in its renderer DOM. Isolation comes from the guest side — each guest is its own sandboxed process on the embed partition, `will-attach-webview` validates every attach (no preloads, no node, partition enforced), and the window's deny-by-default `setWindowOpenHandler` + `will-navigate` hardening stays untouched for the app's own content.
- **C-4:** [confirmed] A new main-process **guest-lifecycle module** is real, named scope (the review's largest omission): it hooks guest attachment (`web-contents-created`/`did-attach-webview` — nothing like it exists in main today), wires each guest's `setWindowOpenHandler` so F-3's popup routing actually routes — the handler always *defers*: it pushes the popup URL to the renderer, whose C-1 branch is the knob's **single adjudicator** — syncs the host zoom factor onto guests (main owns zoom sync; the renderer never re-derives it) (the app runs at 0.9-base host zoom that guests don't inherit — without sync every tile renders at a visibly different scale, and ⌘+/−/0 drift it further), and owns the partition/session access the Accounts section reads through IPC.

#### D — Accounts & Auth
- **D-1:** [confirmed] The **Accounts section in General settings ships in V1** — Nathan pulled it into scope ("if this is possible to add an internet account into Pommora, lets do it"). It manages *web sessions* for embedded content, not Nexus-level identity (that remains a separate future project).
- **D-1a:** [confirmed] Its V1 shape (simplified, Nathan-ratified 08-18): **Add Account records its row immediately** — the domain and name derive from the address being added — and opens the sign-in page in the in-app browser on the shared partition; there is no completion signal threading through the browser's chrome. An abandoned sign-in leaves an unauthenticated row that Sign Out removes in one click. Rows are never derived from the cookie store (it cannot distinguish "signed in" from "visited"). A Clear Browsing Data affordance sits beside the rows. Exact rows and presentation stop for design direction before building.
- **D-2:** [confirmed] All embed surfaces share one `persist:` partition — one sign-in authenticates every tile and the in-app browser, surviving restarts. The partition presents a cleaned user agent so Google sign-in can work; Nathan explicitly accepted the policy fragility. Late research sharpened the risk: Google's block is server-side policy detection, not a pure UA sniff — naive Chrome-UA spoofing stopped sufficing around 2021, and the proven-in-production recipe is Ferdium's surgical one (no Electron/app tokens in the UA, plus a targeted Chrome-version-suffix strip on `accounts.google.com`, applied post-navigation). V1 copies that recipe and treats Google sign-in as **best-effort**: it may fail even initially, the arms race is live, and the Accounts section and every non-Google site work regardless.
- **D-3:** [confirmed] The storage model: sessions are Chromium cookies/site-storage held in the partition's folder under Electron's app-data directory — machine-local, never in the Nexus (cookie jars are machine secrets; consistent with the Reasonable Legibility carve-out for per-machine operational data). Pommora never sees or stores passwords — sign-in happens on the site's own page; what persists is the site's cookie, exactly as in Chrome. The Accounts section is a window into that store, and sign-out clears the site's **full storage** (`clearStorageData` per origin — cookies alone leave localStorage/IndexedDB logins alive, so a cookies-only sign-out visibly fails on many sites). **Clear Browsing Data wipes the partition wholesale, account rows included** (Nathan's ruling, 08-18): the accounts-survive reading required enumerating every storage-holding origin, which Electron cannot do reliably — one honest button beats an unenumerable exemption.
- **D-4:** [confirmed] V1's persistence bar is **per-machine**: one sign-in per site per machine, surviving every restart with no re-login. Cross-device **Session Roaming** — a passphrase-encrypted cookie vault in `nexus.db` carrying logins between machines, doubling as the first true Nexus-identity primitive — is the committed follow-up cycle, not V1 (raw session cookies in a synced file are account keys; roaming ships only with real encryption and its own passphrase design).

#### E — Hover Previews on Website Links
- **E-1:** [confirmed] Website-link hover previews ship in this plan: a **live, non-interactive render that waits for the page to load** before the card opens — matching the hover card's resolve-before-open contract. A webview mounts in the card (the card is fixed-position while open, so the tile clipping constraint doesn't bite), rendered inert.
- **E-2:** [confirmed] The arming seam is two gates, not one (adversarial correction): a cheap class gate fires first (`.md-connection-resolved`, which external links never wear — they get `.md-link`) and returns before the target-kind branch. The selector widens to admit `.md-link` *and* the kind branch below it routes website targets — changing only one of the two ships a hover that never fires.
- **E-2a:** [confirmed] Resolve-before-open with a webview means the guest must **mount and load before the card blooms** — a webview can't load unattached, so the card's website flavor attaches it hidden and opens on load-complete, preserving the a-page-that-can't-load-opens-nothing contract.
- **E-3:** [assumed] Cold-load latency is inherent to the live choice — a first hover can wait seconds before the card blooms; a session-scoped keep-warm or snapshot cache for recently-previewed URLs is the smoothing lever if it feels slow. Raised once; Nathan's live-render direction stands.

#### F — Sweep Findings (interaction, validation, adjacency)
- **F-1:** [assumed] Only explicit **http/https** targets embed — `file:`, `javascript:`, and every other scheme rests as the inert dim token. Non-negotiable security floor for a surface that loads what the markdown says.
- **F-2:** [assumed] The same URL may embed twice in one document — page embeds dedupe because a tile *is* its page in an editing sense; webpage tiles carry no such identity, so first-occurrence claiming doesn't apply. Review pinned the mechanism: the shared claim predicate keys on the normalized *label*, and Short Link makes labels collide by construction (two GitHub pages both label `github.com`) — the webpage claim keys on the **URL** through a kind-aware key, not a fork of the predicate.
- **F-3:** [confirmed] A guest page's `window.open` routes through the open-in knob like any external link (in-app browser window or system browser); never a raw popup window.
- **F-4:** [confirmed] **The engagement model:** the tile renders live but **inert until clicked in** — scroll passes through to the document; a click engages the guest for real interaction; click-out disengages. The same click-in/click-out contract page embeds already teach.
- **F-5:** [confirmed] Scrolling an engaged tile into the clip zone disengages and swaps to the static face — one invariant, no exception path (Nathan deferred to the simplest; this is it).
- **F-5a:** [confirmed] The swap **hides the webview, never destroys it** — a destroyed guest loses scroll, half-typed forms, and playing media on the most casual gesture there is. Spike-verified in this Electron: a guest survives `display:none` with its JS state intact through hide, reshow, and `visibility:hidden`. The eviction order is total (round-2 fix): **visible tiles are always live** — their count is naturally bounded by the scrollport over the height cap — and the guest cap bounds *hidden* retainees, least-recently-visible evicted first, its tile keeping the static face. B-5's "live only while fully visible" governs *painting*; process lifetime is this cap's.
- **F-5d:** [confirmed] A tile's rendered height caps to fit its scrollport (`min(stored, fit)`, stored value untouched), **re-evaluated on scrollport resize** — a one-shot at apply would go stale the moment the inspector opens or the window shrinks, permanently benching the tile. The resize observation shares the scroller-watching site B-5's visibility observer already needs, and the widget's `estimatedHeight` reports the *capped* value so the scrollbar never lies by the difference.
- **F-5b:** [confirmed] "Fully visible" is judged against the tile's **nearest scroller at ancestor depth 0 only**: a webpage tile nested inside another embed surface (a page-embed tile, the hover card's page render, a dashboard block) shows its static face, mirroring the page-embed depth rule. Per-ancestor visibility tracking is not V1.
- **F-5c:** [confirmed] The engagement mechanics are explicit, not inherited: an inert tile carries `pointer-events: none` on the guest plus a click-catcher overlay that performs the engage (the page-embed widget's host-DOM click path doesn't exist inside an out-of-process guest), and disengage is **click-out only** — an engaged guest consumes Escape, so Escape is not a disengage path.
- **F-6:** [assumed] A load failure (offline, dead site) shows a quiet failure face on the tile — the page-embed failed-fallback precedent; never meta/status text.
- **F-7:** [assumed] Tile heights persist in the existing `embedHeights` mechanism keyed host → URL, beside the host → PageID rows.
- **F-8:** [confirmed] The `Default Format` row becomes always-visible — resolved by construction through G-1.
- **F-9:** [confirmed] Foreign or historical lone-line `![…](https://…)` image links in existing Nexus content become webpage tiles — measured against NexusOS: **zero such lines exist today**, so the reinterpretation has no blast radius on real content.
- **F-10:** [confirmed] Reconciliation forecast — docs and contracts this ships against: [[MarkdownPM]] (menu order, Insert contents, a Webpage Embeds section, the image-seam Pending note), [[ConfigurationPM]] (open-in knob, Accounts section, the Pasted Links rows), [[ConnectionsPM]] + [[MarkdownPM]] (a lone-line bang-paren stops being a live external link and becomes the embed form), [[PagePreviewPM]] (the browser flavor), [[SymbolsPM]] (back/forward + webpage glyphs), `shared/bridge.ts` (new channels), and the main window's `webPreferences` (`webviewTag: true`).

#### G — Scope Additions
- **G-1:** [confirmed] **Auto-formatting pasted links stops being a setting — it's built-in behavior.** A pasted address is always written as a link in the default format; the `autoFormatPastedLinks` toggle and key are removed (the stale key survives harmlessly in old `settings.json` files under the preserve-unknown-keys write discipline). `pasteLinkIntoText` is the separate wrap axis and stays a knob. ⌘⇧V's no-selection inverse keeps its meaning: it pastes the address as literal text. Two ride-alongs from review: removing the toggle orphans the settings rows' `when` disclosure mechanism (it was the sole consumer — it goes too), and *with a selection* no gesture pastes an address as literal text anymore (the inverse chord is spent on the wrap axis first) — already restored by the **existing Paste As ▸ Plain Text row** (shipped; verified in `shared/PasteAsMenu.ts`), which reads the clipboard alone and is untouched by the toggle's removal. No new row.

#### H — Build-Phase Checks (verify in the running app; unverifiable statically)
- Whether an engaged guest starves the host of `mousemove`/`keydown` — if so, the hover card's leave lifecycle freezes while the pointer rests on its webview and needs a guest-side or bounds-based fallback.
- The exact post-claim keystroke feel around a freshly-formed tile (B-7's formation gate should prevent the bad case; confirm).
- Whether ⌥-word-motion can seat the caret on a tile line (the atomic-range comment says it can) — the guard covers it, but the seat's feel needs eyes.
- Whether a hidden guest keeps *media* playing (JS state survival is spike-verified; playback throttling wasn't exercised).
- Whether `webview.setZoomFactor` on attach visually matches the host's zoomed rendering, given zoom also changes the guest's CSS-pixel viewport.
- The PreviewPane browser flavor's repaint behavior during window drag (already flagged in C-2).

### Core (must-have)
- The context-menu redesign: Insert / Format / Embed / Heading / Lists, with Embed ▸ Webpage · Internal Page.
- The webpage embed tile: `![Title](url)` lone-line syntax, visibility-managed webview on the existing tile chassis, clickable hover-title honoring `defaultLinkFormat`, grip-menu source arm (TextPicker) + Delete, height drag and persistence inherited from the framework.
- The in-app browser: the PreviewPane browser flavor (back/forward left glyphs, no promote, floating title as the outward link) and the Files & Links open-in knob governing external-link opens, tile hover-titles included.
- The shared `persist:` web-session partition with the cleaned UA, and the General ▸ Accounts section managing those sessions.
- Website-link hover previews: live, non-interactive, resolve-before-open.

#### Prospects (allowed later, not now)
- **Webpage tiles on the dashboard layer** — a `webpage` member of the `BlockEntry` union; the tile payload is designed renderer-agnostic so this slots in without rework. Don't-foreclose: keep the webpage face a standalone component, not editor-coupled.
- **Snapshot warm-cache for hover previews and off-screen tiles** — the smoothing lever if cold loads feel slow.
- **Image rendering via `![[file]]` / the wiki-embed form** — Nathan's assigned direction for the image seam; a separate feature cycle.
- **Session Roaming** (committed follow-up) — the passphrase-encrypted cookie vault in `nexus.db` that carries web logins across machines; the first true Nexus-identity primitive. Needs: cookie export/import across partitions, key derivation from a user passphrase, and its own design cycle. Don't-foreclose: nothing — it layers on the partition without changing V1.
- **Nexus accounts proper** — Pommora-level identity/auth; a future project the Accounts section deliberately does not attempt (Session Roaming's passphrase is its seed).
- **Multiple accounts per site** — two Google accounts means two partitions; V1 is one shared session, per-account partitions are the later mechanism. Don't-foreclose: key embed surfaces to a partition *name* rather than hard-coding the one partition.

#### Out of Scope (won't do — distinct from Prospects)
- Header-stripping to force stubborn sites into iframes — whack-a-mole against framebusting and cookie partitioning; not this feature's mechanism.
- Multi-webview per hover / interactive hover previews — the card renders inert by decision.

#### Considered & Rejected
- **`![[url]]` embed syntax** — rode the existing lone-line grammar, but Nathan assigned the wiki-embed form to images/files; bang-paren won.
- **Bare `[Title](url)` as the embed trigger** — would convert every pasted lone-line link into a live tile; the bang is the discriminator.
- **WebContentsView for inline tiles** — main-owned, cannot be clipped by renderer DOM; kept for nothing (the browser flavor uses the webview inside the DOM pane instead).
- **`<iframe>` as the primary tile mechanism** — framing-blocked by most login-bearing sites, renderer-process sharing, unreliable embedded logins.
- **Always-live naive webview tiles** — spike-proven to bleed outside their bounds when partially scrolled past the container edge.
- **Static bookmark-face tiles (the Notion model)** — cheapest and most robust, but Nathan wants pages genuinely loaded in place; kept as the named fallback if visibility management proves heavy.
- **Metadata-card hover previews** — the Notion/Slack pattern; Nathan chose the live non-interactive render.
- **Written-into-document tile titles** (the label fill one-shot + deferred whole-line swap) — three review rounds of machinery deleted by the simplification pass: the cells' existing display-only fetched-title path shows the same title with no document writer at all.
- **An Add Account completion signal in the browser chrome** — cross-surface flow state; recording the row immediately costs only a removable unauthenticated row on abandonment.
- **Accounts-surviving Clear Browsing Data** — required enumerating storage origins Electron can't enumerate; the wholesale wipe won.

#### Lessons
- When two research passes contradict on a load-bearing technical fact, a minutes-long empirical spike beats adjudicating their citations — the webview-clipping dispute was settled by running the actual scenario and reading screenshots.
- A spec amendment that bans or replaces a mechanism inherits the obligation to restate everything that mechanism was doing incidentally — banning the link serializer nearly dropped its escaping; deferring the tile claim nearly dropped the mount trigger. State both halves of every replaced rule.
