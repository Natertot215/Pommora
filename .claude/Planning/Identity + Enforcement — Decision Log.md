#### What This Changes

Constraints, assumptions, and philosophies that are **no longer true** for Pommora under the settled design — each was load-bearing; none survives:

- **"Only Pages are Markdown; Tasks and Events stay JSON."** Architecture's first principle loses its parenthetical. One `.md` grammar covers all operational content; JSON remains for sidecars, configs, and registries only.
- **"An entity's kind never lives in its own file."** Dead — the kind-stamped ID key is the first in-file kind marker. With it dies "frontmatter never participates in classification": the ID key is now a classification input (the *only* frontmatter key that is).
- **"The one extension-borne kind."** The `.task.json`/`.event.json` suffix authority dies; the folder-sidecar law loses its sole exception and becomes total, with the ID key as its per-file agreement check.
- **"`id` is the universal key; the universal question is 'what's this entity's id.'"** Inverted. The law is kind-first: *what is this* (the folder's sidecar) → *then what's its ID* (that kind's key). No reader ever multi-key-checks.
- **"Silent-fail is forever."** Replaced by *silently invisible until fixed on reload*. A violating file is not an error, not rendered, not indexed — and no longer permanently abandoned: the open-path repair pass (adoption's family: idempotent, from-record, never-guess) fixes what it has a record for.
- **"Most-recent-wins is absolute for external changes."** Bounded. Content stays most-recent-wins; *structure* — what kind lives where — is now Pommora-authoritative, and a structural violation with a record reverts on reload.
- **"External changes are never reverted."** Dead, for exactly the structural class above. Content edits remain untouchable.
- **"Any root folder carrying an agenda config IS an agenda singleton."** Dead — registration by sidecar id is now the authority; an unregistered, duplicated, or nested config is inert bytes. (Today two `_taskconfig.json` folders would BOTH feed the task list; that ends.)
- **"Agenda files never join the tree walk."** Dead — D-9 signed. The lazy `agenda:list` loader, its snapshot, and its separate freshness rules die with it.
- **"A `.md` in a valid location is always indexed."** Dead — the membership predicate gains the ID-agreement clause; location alone no longer admits a file whose key contradicts the folder.
- **"`description` is a field."** Dead — the body *is* the description, and every task/event gains full MarkdownPM prose (connections-as-sources included) by construction.

### Decisions

#### A — Current Identity Model (the verified catalog)

- **A-1:** [confirmed — `ids.ts` read whole] One monotonic-ULID space for all entities (`newId`); no per-kind prefix or namespace for entity ids. Exactly two prefixed sub-namespaces exist, both non-entity metadata: `view_<ulid>` (`shared/views.ts`) and `prop_<ulid>` (`ids.ts`), plus `_`-reserved built-in property ids. The one format outlier: tab ids are renderer-minted UUIDs, never touching a nexus file.
- **A-2:** [confirmed — `ids.ts:30`, `readNexus.ts:224/301/347/375/443`] The synthetic-id tier: `adopted-<sha256(relPath):16>` for anything read without a persisted id — stable across launches, distinguishable from a ULID, checked in production only once (tile-id filename gate). Every kind's read site carries the fallback.
- **A-3:** [confirmed — `paths.ts:13-19`, `readNexus.ts:487-492`] Kind authority: five sidecar filenames in one map (`_space` / `_pagecollection` / `_pageset` / `_taskconfig` / `_eventconfig`). A root folder with an agenda config is hidden from Collections; a root folder with `_pagecollection.json` is a Collection; every non-excluded subfolder below is a Set *by position alone* (no sidecar check); a Space IS its `_space.json` (missing/corrupt → the Space silently vanishes). Agenda item kind = filename suffix (`agendaKindOf`) — the one extension-borne kind.
- **A-4:** [confirmed — `readNexus.ts:185`, `sidecarIO.ts:14-27`] Two `readSidecar`s with opposite failure semantics: the walk parses sidecars with NO zod (null → `{}` for containers), while the write side zod-validates and treats a failing sidecar as `null`/not-found. Consequence: a corrupt `_pagecollection.json` still surfaces as a Collection but under a *different id* (`adoptedId` fallback) with no views/schema/order — silently — while every write op against it reports not-found.
- **A-5:** [confirmed — `adopt.ts` read whole] Adoption is the existing repair precedent and the only steady-state-adjacent write-on-read: on every open, stamps missing page `id`s (preserving merge) + missing collection/set sidecars, heals `parent_id` at mint time only, refuses to mint over an unreadable sidecar, skips agenda folders wholesale and empty sidecar-less folders. Silent, idempotent, best-effort. No adoption exists for agenda items, block tiles, or views.
- **A-6:** [confirmed — `readNexus.ts:239-248`] A Page is: regular file + not `_`-prefixed + `.md` (case-insensitive) + directly inside a Collection/Set. Frontmatter never participates in classification; a frontmatter-less or YAML-broken `.md` is still a Page with empty fm. Dot-prefixed *files* are NOT filtered (`.foo.md` becomes a Page); dot/underscore *folders* are.
- **A-7:** [confirmed — `readNexus.ts:481-492`, `mutate.ts:170-179`] Invisibility zones: a `.md` at the nexus root, in an agenda folder, or in a sidecar-less root folder is walked by nothing — yet `createPage` explicitly supports `parentPath: ''` (root), so the app can create a page the walk then never surfaces. Agenda folders nested inside a Collection are NOT skipped — the agenda-config check runs only in the root loop, so a nested `_taskconfig.json` folder reads as an ordinary Set.
- **A-8:** [confirmed — `collectAgenda.ts` read whole; `agendaEntity` grep] Agenda today: discovery is a separate lazy root-only scan (not the tree walk), config-sidecar-gated, suffix-discriminated; a zod-failing item (including id-less — `id` is required) is silently dropped; an unparsable-JSON item throws uncaught and fails the whole `agenda:list` call. The write CRUD (`agendaEntity.ts`, agenda schema ops) exists tested but is wired to no IPC channel; nothing in the app can even create an agenda container. Agenda items DO join the context rename cascade and `NavRef` admits `'task' | 'event'`.
- **A-9:** [confirmed — `walkCache.ts`, `db/schema.ts`] Kind is re-derived every walk (raw `stat` existence checks, uncached); only parsed *content* is mtime-cached. `nexus.db` holds no kind or tree data — chrome scopes only.
- **A-10:** [confirmed — three sites compared] Agenda-container detection is triplicated with divergent behavior: the walk (root-only, either config hides), adoption (root-only, either config skips), the agenda loader (root-only, task-wins-over-event, and — unlike the others — NO exclusion filter, so a dot/underscore/excluded root folder still gets scanned). No shared predicate.
- **A-11:** [confirmed — census verified: navKey/crumbs/dnd-index/embed-resolution/bridge args/parent_id all opened] The consumer split. **Kind-constrained (structurally collision-immune):** everything downstream of `navKey` (`<kind>:<id>` — tabs, back/forward, pins, favorites, recents, resolve index, warm cache, thumbnail filenames), `reconcileWith`'s per-kind tables, connections (title-resolved over a pages-only universe), context identity maps, all path-addressed mutation IPC, the watcher/stabilize (path/positional, no id matching). **Kind-blind flat lookups:** breadcrumbs (`crumbs.ts` — one predicate matches collection OR set OR page ids), the sidebar drag index (one `byId` map across five kinds, last-wins), view-embed source resolution (`findCollection ?? findSet`), `store.findContainerPath`, the `folds`/`headingCols`/`activeView` db scopes (bare ids), sidebar disclosure persistKeys, and the `.nexus/assets/<id>/` folder scheme.
- **A-12:** [confirmed — grep verified] Dangling machinery: `parent_id` is the ONE id-valued cross-entity FK on disk and is write-only — no reader exists (tree uses folder nesting). `ConnectionEdge.targetId` is declared, consumer-less. **No id-uniqueness check exists at mint, adopt, or walk time** — nothing detects or reports a duplicate id, same-kind or cross-kind; the only duplicate-aware code is title-ambiguity in connections and treeIndex's last-wins collapse (same-kind copied-`.md` case, deliberately listed).

#### B — Current Enforcement Philosophy (the verified catalog)

- **B-1:** [confirmed — census verified across ~15 sites] The read law: **lenient per-field, never writes, never surfaces.** Broken frontmatter → empty `{}`; unreadable page → skipped from the tree; corrupt collection/set sidecar → `{}` + identity swap to `adoptedId`; corrupt `_space.json` → Space vanishes; corrupt `contexts.json` → ALL Contexts vanish (walk-side only). Exactly one walk-fatal file: an unreadable `nexus.json` (a lenient null would flip the nexus to raw mode). No read/parse failure ever reaches the user; no quarantine mechanism exists anywhere.
- **B-2:** [confirmed — `atomicWrite.ts:59-102`, `pageFile.ts:57-79`] The write law: **strict — a write may act on a fact, never on ignorance.** `rmwJsonStrict` separates absent (a fact, seedable) from unreadable (ignorance, refuse + no write); `readJsonObject` is stamped READ PATH ONLY. The strictest instance: a field write onto broken frontmatter throws a user-facing refusal ("Pommora left it untouched") rather than normalizing; a body-only write passes the broken frontmatter bytes through verbatim.
- **B-3:** [confirmed — five open-path writes traced] Repair happens **only at open, only from a record, never from a guess**: identity mint, registry seed, the ID-stamping pass, crashed-rename journal replay, db version drop. Plus one write-time normalization: `reconcileContextKeys` repairs coercion-only near-misses (case/NFC/whitespace) to canonical Space titles — but only inside a root the user's own write is already rewriting. The watcher repairs nothing, reverts nothing; its whole vocabulary is "re-walk and push," and a throwing walk keeps the last-good tree silently.
- **B-4:** [confirmed — `result.ts:6-17`, `ipc.ts:8-9`, site sweep] Refusals are a closed 11-code union surfaced via native error dialog; the two session refusals (`no-nexus`, `busy`) are single-spelling constants. Reserved-entity guards (root, `.nexus`, `.trash`) refuse rename/delete/context-tagging.
- **B-5:** [confirmed — `mutate.ts:491-518`, `sidebarDndModel.ts:150-179`] **The cross-kind move rule lives only in the renderer's DnD model** (a Set may only join a Collection/Set; context rows return null; no cycles). Main's `movePage`/`moveSet` validate path containment + collision only — no kind check at commit time. Nathan's B-2 rejection idea therefore has no main-process backstop today; a programmatic or future-surface move can put anything anywhere.
- **B-6:** [confirmed — `page.ts:86`, `propertyValue.ts`, pipeline `value.ts`] Schema conformance is **definition-first and non-enforcing**: unknown wrapped keys are inert-preserved; a value the declared type can't hold decodes to null per-cell (no fallback ladder, no rewrite); a cross-collection move runs zero schema logic. `strict` decode exists solely as the remove-cache restore gate.
- **B-7:** [confirmed — no code found; two compensating reverts only] Nothing external is ever reverted. The only reverts are in-op compensations: a failed rename-cascade un-renames the page; the schema transaction rolls back its own staged files.
- **B-8:** [confirmed — census verified] Under a cross-kind id collision today, the misbehavers are the kind-blind list in A-11 — worst: breadcrumbs (wrong container chain), the sidebar drag index (an entry silently overwritten → corrupt drop targeting), embed source resolution (collection silently shadows set), `activeView` (a collection and set share one slot). Navigation, reconcile, connections, and every path-addressed write are immune.
- **B-9:** [confirmed — Nathan's constraint, hard rule] Whatever enforcement/repair lands, **no full-nexus scan on a per-event trigger** — the "never expensive work on every X" law governs. The budgeted O(N) moments already exist: the open path (where adoption runs) and the watcher's debounced verification walk (which already enumerates + stats everything, parsing only mtime-changed files). Detection must piggyback on data those passes already hold; repair must be a scoped per-offender write, never a sweep.

#### C — Agenda-as-Markdown (Nathan's starting hypotheses, not current fact)

- **C-1:** [confirmed — Nathan] Tasks + Events become `.md` files; kind from the parent folder's config sidecar (existing `_taskconfig.json` / `_eventconfig.json` — note: real names are `_`-prefixed, not `.`-prefixed).
- **C-2:** [confirmed — Nathan revised] The in-app cross-kind guard is **by construction, not by rejection**: Collections and Agenda live on separate access surfaces, and any future "Move To" enumerates legal destinations only (the sidebar-DnD pattern — illegal targets are never offered). No interactive rejection gate needed. The **external/manual filesystem path is the real enforcement surface** (revert-on-reload, C-2b).
- **C-2a:** [confirmed — Nathan: "yes, but minimal"] When Agenda lands, main's `movePage`/`moveSet` gain a minimal destination-kind backstop (refuse a cross-kind move at the choke point) — nothing more; no surface pattern can currently even offer such a move, so the backstop guards the programmatic accident only.
- **C-2b:** [confirmed in model — record design is plan-level] The external-move revert runs at open/reload from a record of last-valid position (C-3a); no such record exists yet anywhere (B-7), so the plan designs it fresh (nexus.db is the natural home; per-entity rows vs a per-walk snapshot is the open plan detail). Most-recent-wins is reconciled by the bounding in What-This-Changes: content recency stays absolute, structure is Pommora-authoritative.
- **C-3:** [confirmed — Nathan, via C-3a] The identifier gains file-write powers to fix violations — retiring silent-fail-forever. It extends the adoption precedent (A-5) and lives as its own open-path pass, never inside the walk, preserving the reads-never-write law (B-1).
- **C-3a:** [confirmed — Nathan] The enforcement model: **the renderer never sees an error.** A kind-mismatched file (a `PageID:` file in an agenda folder, a `TaskID:` file in a Collection) is not indexed at any functional level — invisible exactly like a stray `.png` in a Collection — and the open-path repair pass fixes it on reload. Classification's predicate gains one clause: location + extension + **ID-key agreement with the folder's declared kind**. No inert-foreigner rendering, no violation surface. Extends the existing read law (B-1) rather than breaking it.
- **C-3b:** [confirmed — by implication of C-3c's confirm; Nathan may still veto] Mismatch ≠ missing: a `.md` with NO ID key renders immediately as the folder's kind (today's behavior — synthetic id until adoption stamps it; preserves the external-authoring flow). Only a *contradicting* key makes a file invisible. An ID-less `.md` in an agenda folder is an adoptable Task/Event, stamped at open — which means adoption's current skip-agenda-folders-wholesale rule inverts.
- **C-3c:** [confirmed — Nathan] The no-record fallback: a file *born* mislocated has no last-valid position to revert to, so it stays invisible — unclaimed, not trapped — until a human moves it. Never a guessed relocation, never a guessed conversion. (Reaching that state requires hand-authoring a contradicting ID key into a foreign folder while Pommora is closed — a deliberate act nobody performs by accident.)
- **C-3d:** [confirmed — Nathan] The one visible consequence, accepted: a mid-session Finder move of a Page into an agenda folder vanishes it from the UI until the next reload reverts it. No interim state by design.
- **C-4:** [settled → D-1/D-2/D-3] The kind-stamped ID key, ratified as the design's first law. The migration surface it names stays true and lands in Core: every `.md`, `pageFrontmatter` + both agenda schemas, `PAGE_MODELED_KEYS`, adoption's stamp, and every `fm.id` consumer — moved in one stroke (E-2's cascade gate foremost). Wrap-law reconciled at D-2.

#### D — The Settled Identity Design

- **D-1:** [confirmed — Nathan; reach corrected by review] **Kind-stamped ID keys**: `PageID:` / `TaskID:` / `EventID:` replace bare `id`. The kind rides the *key*, the value stays a bare ULID. The law is kind-first: an ordinary *reader* resolves identity from the one key its kind context names — but the **admission predicate is the one reader that checks all three** (distinguishing mismatched-from-missing is definitionally a multi-key check: a `PageID:` file in an agenda folder must read *invisible*, not *adoptable*). The predicate is ONE exported function, shared verbatim by the walk and the repair/adoption pass — two passes, one clause; landing it in only one silently converts mislocated files (the review's C2, executed proof).
- **D-2:** [confirmed — by construction, verified against `governedKeys`] Wrap-blindness is structural: `<PageID>` is a property key, `(PageID)` a context key — different literal strings in different namespaces; a user-created property named "PageID" writes wrapped and collides with nothing.
- **D-3:** [confirmed — Nathan] **No migration code, no synonym read.** Legacy `id:` → `PageID:` is done MANUALLY by Nathan across his pages; until then the app simply doesn't recognize them. Zero transition machinery. Consequence disclosed and accepted with it: the manual rename must happen with the app closed, before the new build's first open — otherwise adoption sees "no ID key," stamps fresh `PageID`s (new identities: pins/tabs/asset folders keyed to old ids detach), and the old `id:` keys ride forever as foreign frontmatter debris.
- **D-4:** [confirmed — Nathan] Validation at admission only: the walk runs the location+key agreement predicate on frontmatter it already parses; every lookup downstream trusts the index. No per-lookup validation anywhere.
- **D-5:** [confirmed — Nathan] Adoption stamps by folder-declared kind (collection/set ⇒ `PageID`, agenda config ⇒ `TaskID`/`EventID`); the sidecar remains the standing validator of correct ID placement. Sidecar-not-name law unchanged — "Task/ and Event/" confirmed as shorthand for the singleton folders, names stay renameable. Additional clause: an agenda config sidecar is only *valid* in its validated location (the registered root singleton, D-8) — anywhere else it is inert bytes.
- **D-6:** [confirmed — Nathan] Collection-scoped consumers (wikilinks, embeds, breadcrumbs) keep excluding agenda **by kind partition, not new guards**: agenda enters the tree as its own top-level branch; connections' universe stays the `kind === 'page'` projection; embed resolution searches collections/sets only. Nothing changes because the treeIndex partition already is the right mechanism.
- **D-7:** [confirmed — Nathan; recorded for the agenda rethink — this is shape, not identity] `description` is dropped entirely — the `.md` body IS a Task/Event's description. Like D-12/D-13/D-14, it binds the future agenda work, not the identification plan.
- **D-8:** [confirmed — Nathan] **Singleton registration**: the nexus records the canonical Tasks + Events singletons by sidecar id (one new pair of state). A duplicate hand-made config ≠ recorded id → inert sidecar → plain invisible folder; a nested agenda-config folder is the same non-question; the real singleton dragged into a Collection is repaired home on reload using the recorded id as its record. Registration is the guard — no special-case code. (Where the pair lives — `nexus.json` vs `state.json` vs own file — is a plan-level detail.)
- **D-9:** [confirmed — Nathan] **Agenda joins the tree walk**, explicitly reversing the documented "agenda files never join the tree walk" decision. treeIndex records, navKeys, search, and the sidebar projections all ride it; mtime-cached cost equals pages.
- **D-10:** [confirmed — Nathan, clarified] Singleton birth: Tasks/Events folders + config sidecars are created at **initial nexus creation** (the contexts-registry ensure pattern), registered in the same breath. Until the agenda rethink defines more, the seeded config is minimal — identity only. **The existing Swift-era agenda folders are manually deleted from the live nexuses (test + NexusOS) during the plan, app closed, recoverably** — so the new seed starts clean and no tolerance/migration code ever exists for the old form.
- **D-11:** [confirmed — Nathan] **The inherited agenda schema is not grandfathered.** The Swift-era item shape (the "not before" `start_at`, `priority`, `due_floating`, the recurrence/alarm forms) predates real Agenda thought and may lock shapes Nathan never chose — the scaffold plan includes a **schema scrub pass** re-deriving every field before the frontmatter models are written. Constraint already ruled: tasks are NOT barred from start/end dates (which unifies `start_at` as "literal start" on both kinds). The task date model settles inside that pass. Field-by-field provenance → the Schema Scrub Inventory below.
- **D-12:** [confirmed — Nathan] Surfacing: Agenda is its own separate sidebar pane, AND app-wide discoverable (search, tabs, navigation) — the Contexts pattern: a dedicated pane, not a walled garden.
- **D-13:** [confirmed — Nathan; later focus] Task/Event detail: minimal `TaskWindow` / `EventWindow` components are the eventual click destination — deferred past the scaffold. The scaffold adds the selection kinds and satisfies the compile-forced router arms minimally; the real surfaces are their own later pass.

#### The Schema Scrub Inventory — Provenance of Every Inherited Agenda Field

Dug from the Swift archive (`Domain/Agenda/AgendaTask.swift` + the Swift `Agenda.md`, both read this session). The headline: **the task schema is EKReminder imported field-for-field, by explicit design** — "EKReminder-aligned," priority "mirrors EKReminder.priority," `start_at` annotated as EKReminder's "not before." Apple's model was adopted wholesale so future sync would be purely additive — a rationale the EventKit research has since voided (sync is a code-level mapping regardless; → Out of Scope).

**Nathan's standing ruling governs the scrub:** Swift-parity is no longer a consideration — anything existing only for compatibility with, or as a remnant of, the Swift app is dead code and gets removed. The burden therefore flips: no inherited field survives by default; each is **re-chosen on Pommora's own merit or deleted**. Per field:

- **`due_at`** — EKReminder `dueDateComponents`. The deadline; core, keeps.
- **`start_at` (task)** — EKReminder's start date, Apple's "active from" semantic. The Swift design already treated it as a real user-facing date (its planned detail panel collapsed matching `start_at`/`due_at` into one "When?" input) — Nathan's no-barring ruling is *consistent with* the original intent, not against it. Note: EKReminder has no end date, so a task `end_at` would be Pommora-native and unmapped at sync — fine, but a knowing choice.
- **`due_floating` + `due_all_day` (+ event `all_day`)** — iCal/EventKit time-zone-less and date-only modifiers. **Prime scrub candidates:** Pommora's own date grammar already expresses date-only by *value shape* (a bare date string folds into Date on read — the Date property's law), so these booleans double-book what the value format states. Apple's modifiers as file fields vs derived at the sync boundary.
- **`completed` + `completed_at`** — EKReminder `isCompleted`/`completionDate`. **Collides with the pending Built-in Status**, which is specified as the engagement tracker mapping onto reminder completion — a task's "done" would live in two places (the boolean AND the Status value), the exact two-writers-for-one-fact defect class. The scrub must pick one owner (Status as the source, `completed` derived at sync, is the shape the Swift doc's own group-mapping implies).
- **`priority`** — bare 0–9 **on Apple's inverted scale** (0=none, 1=high, 5=medium, 9=low). As a native file field this bakes Apple's counterintuitive numbering into user-visible frontmatter. Scrub: a Select-like property or a sane native scale with translation at sync.
- **`recurrence` · `alarm_offsets` · `alarm_absolute` · `calendar_id` · `eventkit_uuid`** — pure sync-era passthrough; zero logic anywhere (H-2), `recurrence` never once written. Since the schemas are loose, **undeclared keys round-trip anyway** — these can leave the modeled schema entirely until the EventKit arc, carried as foreign keys at zero cost.
- **The create defaults** — today's `createAgendaItem` writes `description: ''`, `alarm_offsets: []`, `priority: 0`, `completed: false`, `due_floating: false`, `due_all_day: false` (+ event `all_day: false`, `alarm_absolute: []`) into every new file — **noise keys violating the no-empties law** pages follow ("no value, no key"; an empty value deletes its key). The `.md` models write none of them; absence means false/none.
- **`end_at >= start_at`** (event) — the one Swift validation rule beyond presence; carries.
- **One honest trade recorded:** the Swift doc's stated rationale for the extension-borne kind was "identify the kind *without opening* the file." The kind key requires one file read — negligible in practice (the folder sidecar identifies without any file read), but the original rationale was real, not an accident.
- **Nathan's own live taxonomy — recovered from the deleted configs, and NOT reproduced by any seed.** Both NexusOS agenda configs carried a second property beyond the built-in Status, hand-authored well after the Swift build: a Select named `type` under the reserved id `_type`. Tasks offered **Task** (blue) · **To-Do** (yellow) · **Phase** (purple); Events offered **Event** (green) · **Meeting** (blue) · **Appointment** (purple). The scrub must decide whether these are properties at all or a shape the kind system should express directly — a Task/To-Do/Phase distinction inside the Task kind is arguably three kinds wearing one, and the same question applies to Events. Also settled here: the on-disk Status carried option *values* (`not_started` / `in_progress` / `done`) distinct from their labels, where the in-code seed writes value-equals-label — the scrub picks one convention.
- **Solved-by-this-design, confirmed against Swift:** the dead `properties` map field is the Swift `properties: [String: PropertyValue]` shape surviving as a schema line after React moved values to wrapped root keys; Swift's singleton duplication rule was "first-found wins if duplicated" — hand-waved there, properly closed by D-8 registration.

#### Lessons

- A recorded decision's rationale must be re-priced when the *value* side changes — agenda-off-the-walk was right for a JSON dead-end list and wrong the moment tasks wanted surfaces; the cost side never moved.
- A deliberate second identity source whose *disagreement is the detection signal* is a checksum, not the two-writers defect — but the exemption has to be written into the ledger, or the next consolidation sweep will "fix" it.
- An inherited schema is a decision someone else made — the task shape read as Pommora's design but was Apple's model imported wholesale; provenance-check inherited shapes before treating their fields as product intent.

### What This Unlocks

Verified against code and docs (three sweep lenses, citations re-opened). Grouped: what the design deletes, what it enables, what it merely de-risks, and the reconciliation bill it creates.

- **The renderer's placeholder tier**, with one load-bearing ordering rule: `liveTarget`'s task/event null (the choke point) must fall FIRST or together with the `pinTarget`/`addFavorite` guards — removing the favorite guard before the resolver yields invisible, un-removable rows (the code's own comment warns exactly this). #### Features It Enables

- **QuickCapture's blocker collapses** — "Tasks and Events don't have a create operation" becomes "createPage with a kind": the generic `.md` writer already carries zero collection assumptions. This also re-opens the doc's capture-while-quit ban for the *create-only* class: a new file with no ID key has no read-modify-write hazard, and adoption claims it on next open — which is what makes a Swift share extension, a browser clipper, a shortcut, or a cron job into safe writers with no running-app handshake. (Mobile's v1 scope lists Quick Capture; the courier routes all collapse to "write a file.")
- **A writable agent contract** — the PRD scopes agent-legibility as read-only; kind-stamped keys + the repair pass make the write side documentable as one rule: *drop an ID-less `.md` in a kind-declaring folder; Pommora claims, stamps, and normalizes it on open*. The convention doc is arguably the highest-value page Pommora doesn't have.
- **Agenda surfacing becomes compiler-driven** — tree membership gives every task/event a full record + navKey; `NAV_KINDS` already admits the kinds; every remaining touchpoint (`DetailView`, `reconcileWith`, `select`, `DEFAULT_ITEMS`) is an exhaustive switch that *fails to compile* until handled. Watch the two silent-fallthrough exceptions (`ViewSettingsScope`, `contextTargetToSelect`) and the one unchecked `NavRef → SelectTarget` cast in NavList.
- **Views over Tasks are nearly free** (pipeline source-agnostic, `loadValues` unchanged under `.md`, an agenda `flattenContainer` sibling + a renderer-side `property_definitions` parse are the whole bill) — and the **Calendar/Timeline renderers get their natural data source**, currently sequenced (v0.6.0) *before* that source exists (v0.7.0). Sequencing call surfaced.
- **The Property Panel generalizes** — agenda values already write wrapped keys through the shared codec; one grammar erases the serializer split, so the preview inspector reaches agenda items without a second decoder. Remaining blocker: `setProperty`'s registry-only def lookup needs the sidecar-schema branch.
- **The repair pass is a platform, four jobs deep:** heal `parent_id` steady-state (write-only today; folder nesting is the free record — the precondition for Sub-Pages and the precedent for Context.md's flat-Spaces open question); detect **duplicate ids** at admission (a Finder copy today silently corrupts thumbnails, folds, pins — the walk already holds every id; needs Nathan's tie-break ruling); GC orphaned `.nexus/assets/<id>/` bytes (thumbnail eviction is the working precedent; banner bytes currently live forever — carry the banner-delete gate discipline); count the **unclaimed** (the C-3d Prospect made cheap — a kind-stamped file in a nowhere-folder is identifiable but unplaced).
- **Sapphire's biggest-ever alignment step:** the whole operational layer becomes Obsidian-readable — task backlinks and graph reach arrive with zero Pommora code; `WHERE TaskID` becomes a Dataview kind-predicate that survives any vault reorganization (inexpressible today); Sapphire can *author* a task (drop an ID-less file; Pommora adopts). One rule to add: the kind keys join the wrap-sigil hide list.
- **Deep links + Spotlight get their grammar:** `pommora://task/<ulid>` is a re-parse of `navKey` — the shape already keying tabs, pins, recents, thumbnails; zero protocol code exists today, and half the persistence plumbing already admits the kinds. A future `.mdimporter` can tell Spotlight a Task from a Page — structurally impossible today.
- **The sync story gains its missing mechanism:** NexusSync describes conflict-copy dedupe as working behavior — **no implementing code exists**, and its "every entity carries a stable id" premise is false for block tiles. Kind-stamped keys make "read (kind, id) from any content file" one function, and the repair pass is the natural home for the dedupe when sync lands.

#### De-Risked, Not Delivered
