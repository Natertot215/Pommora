## Sync Groundwork — Decision Log

> **Standing (09-10-2026):** converged and passed to planning after three adversarial review rounds; every decision is `[confirmed]`. One declared stop remains inside the plan: the Nexus heading's layout (D-1). This arc is the pre-work carved out of [[Mobile Companion & Pommora Sync — Decision Log]]: the data-level infrastructure that must exist regardless of how mobile and Pommora Sync are finally shaped. That log's Standing note ("the work is not starting now") stays true for the phone and the server; this arc starts what is host-independent.

### Frame

- **Purpose:** Lay the data-level groundwork Pommora Sync and the mobile companion need regardless of their final shape: a Nexus identity that survives copying and syncing, a device identity every host mints once, a home for the device's secret on the machine, an explicit rule for what travels and what stays, the Nexus heading in Settings those bind to, and the smallest server that gives the device key a counterpart. The phone, the sync protocol, and everything content-bearing stay in [[Mobile Companion & Pommora Sync — Decision Log]].
- **Core Value:** Every device can name itself, prove itself, and be approved or revoked against a Nexus, and the Nexus folder, `.nexus/` included, is a self-sufficient travelling unit with a stable identity, so the sync arc starts from settled identities rather than minting them mid-flight.
- **Success Criteria:** A small test Nexus is created, copied with `.nexus/*.db*` deleted from the copy, and the copy opened in a second Pommora instance (a second `POMMORA_USERDATA` directory), so two instances hold two device keys and one Nexus id. The first binds the Nexus to a server on localhost and is approved by construction; the second binds the copy, registers, appears pending in the first's Nexus heading, is approved there, then revoked; every state survives a server restart and an app relaunch. The what-syncs rule and the identity model are written in [[NexusSyncPM]], and every Mobile-log entry they make false is rewritten.

### Decisions

#### A — Scope

- **A-1:** [confirmed] Windows reaches NexusOS through Obsidian Sync today. Obsidian Sync is prior art only; Pommora never rides it, and the end state lets it be switched off (restates Mobile A-1).
- **A-2:** [confirmed] `.nexus/` syncs. Its JSON files and assets travel; `nexus.db`, `versions.db`, and their journals never do. This enters the project's Locked Decisions as a pointer to [[NexusSyncPM]].
- **A-3:** [confirmed] The origin folder never moves; the receiving end chooses where its copy lives (Documents or Library on a phone, an empty folder on a Windows desktop).
- **A-4:** [confirmed] This arc is identity and its proof: the device key, the secret store, the Nexus heading, the initial server with its four verbs, and the documentation set. No phone code, no content sync, no encryption of content, no deployment.
- **A-5:** [confirmed] The monorepo restructure the Mobile log names as Step 1 is done: six workspaces exist at the root; `Sync/` and `Mobile/` are package stubs outside the typecheck project list.
- **A-6:** [confirmed] Windows path handling leaves this arc: the evidence goes to [[Cross-Platform Compatibility Checklist]] for an independent later session.
- **A-7:** [confirmed] Device-key identity, no account (ruled 09-10-2026 after account + devices was weighed). Each install mints a keypair at first launch; the device's id is the key's fingerprint. A Nexus on the server holds a device list; a new device is approved by an existing one; revoking a device removes one key. Several people on one Nexus is several people's devices on that list, which is the condition Nathan set and the model meets.
- **A-8:** [confirmed] Accounts are a Prospect layered on top; see the Prospects ledger for the don't-foreclose condition and [[Sync Groundwork — Provider Research]] for its evidence.
- **A-9:** [confirmed] One random content key per Nexus, minted once; the user-assigned Nexus password wraps that key and never encrypts content directly, so a password change re-wraps one record (restates Mobile F-2). The password is separate from any device key, entered once per device, held in the platform keychain, and never reaches the server (restates Mobile F-3). The wrapped-key list in the Nexus info record carries two entry kinds: the password-wrapped root and a per-device entry wrapped to that device's public key by the device that approved it, so a paired device holds the key too and unlocks without typing the password. The Ed25519 device key only signs, so the per-device entry is wrapped to a second, X25519 key the device mints when the sync arc arrives: the server's device row gains that column additively under G-5 and connect re-issues it. Ratified 09-10-2026 as the sync arc's starting point; no code in this arc.
- **A-10:** [confirmed] A copied Nexus folder is a replica: the id names the Nexus, not the folder, so both copies reconcile against the same remote. A deliberate "make this a new Nexus" action is a Prospect.

#### B — What Travels

- **B-1:** [confirmed] The what-syncs rule, decision only until the sync client consumes it: every entry the watcher would watch plus `.trash` at the top level, minus any name matching `.db`, `-wal`, or `-shm`. Every other dot-entry stays home (`.obsidian`, `.git`, `.claude`). Written in code as one predicate beside `neverWatched` when the sync arc needs it, never by convention (restates Mobile C-4).
- **B-2:** [confirmed] Aliases sit in `nexus.db` although they are authored content; a known issue, no action in this arc.
- **B-3:** [confirmed] Interface Scale and Webpage Zoom stay in the travelling `settings.json`. The eventual shape is a per-device `settings.local.json` override; a Prospect, not this arc.
- **B-4:** [confirmed] The tree's path-hashed fallback id (`Core/Nexus/readNexus.ts:302`) stays: it fires only in raw mode, when no identity file exists, and the open path writes one before any real Nexus is read; its only readers are the thumbnail folder paths. No action.

#### C — Device Identity

- **C-1:** [confirmed] Minted once per install by the host. The public key, its fingerprint as the device id, and the device's name live in `pommora.json`, the app-level config outside every Nexus; `AppConfig` and `readAppConfig`'s whitelist (`Desktop/Config/appConfig.ts:9-13,23-33`) gain the `device` field. The name defaults to `os.hostname()`, read by Desktop at mint time; Core never asks for it. The public key is spelled base64url wherever it travels (`pommora.json`, the connect body, the server row), matching the signature's encoding. The private key lives in Desktop's secret store and never enters Core; Core sees the device through `HostContext` (F-2).
- **C-2:** [confirmed] The secret store is a Desktop module beside `Desktop/Config/appConfig.ts` over Electron's `safeStorage` (OS-keychain-backed, no native module, no new dependency), writing the encrypted values as one JSON file beside `pommora.json` so the config file itself stays hand-readable. It has no caller in Core in this arc, so it is not a `Core/Platform` seam yet; it becomes one when the Nexus password (A-9) gives Core a caller.
- **C-3:** [confirmed by test] The key algorithm is Ed25519 through WebCrypto; it signs and verifies in Node 24.15 (64-byte signatures), which Electron 42 bundles. The WKWebView half is the Mobile log's E-3 harness and runs before the phone host binds; ECDSA P-256 is the fallback if any engine lacks it. The device id is the lowercase hex SHA-256 of the 32-byte raw Ed25519 public key. `Core/Sync/contract.ts` states the recipe in prose beside the types; the host executes it at mint and the server executes it at connect, and Core never hashes key bytes (the machine seam's `sha256Hex` is text-only). A shortened display form is the design stop's.
- **C-4:** [confirmed] Nothing about the device key syncs. The device list is server state; the device's public key is what it presents to be approved.
- **C-5:** [confirmed] A `pommora.json` that names a device id whose private key the secret store no longer holds (an OS reinstall, a keychain reset) is a lost identity: the app re-mints, reports it once, and the old approval dangles on the server until revoked from another device.
- **C-6:** [confirmed] `updateAppConfig` overlays unknown keys on write (`Desktop/Config/appConfig.ts:36-46`), so an older build reading a `device` field it doesn't model keeps it.
- **C-7:** [confirmed] Electron's `safeStorage` on macOS keys its encryption to the app's code signature. The dev binary in `node_modules` keeps one signature across rebuilds, so this arc's proof never meets a re-prompt; a packaged ad-hoc build (`Desktop/electron-builder.yml` `identity: null`) may, and that belongs to packaging. A value that no longer decrypts is C-5's lost-identity path.

#### D — Settings Surface

- **D-1:** [confirmed] Settings › General gains a **Nexus** heading: this device's name (editable) and fingerprint, the Nexus id, a server address with Connect and its inverse Disconnect, and the device list, pending and approved, with Approve and Revoke. The Nexus password joins it in the sync arc, when there is a key to wrap. The nine existing row kinds are each single-purpose and bound to one settings key; all render through `settingsRow` into `MenuRowView` (`Core/Settings/SettingsWindow.tsx:40,140-159`), three of them (`path`, `exclusions`, `clear`) through the `SettingsFieldRow` wrapper. The menu layer already carries `caption`, `action`, and `heading` rows and a `Trailing` slot with `field`, `button`, `switch`, `value`, `picker` (`UIX/Menus/menu-index.tsx:12-29`), so the heading's rows reuse those and the only new thing is a device-list row; the design stop's brief carries that roster as the reuse list. A Frame may be a bespoke Surface but a Section may not (`Core/Settings/frames.ts:139-147`), so whether the heading is a Section or its own Frame is part of that brief. The existing `kind: 'device'` means a `DevicePrefs`-backed toggle, and the new kinds avoid that word. Its layout is Nathan's; the plan stops to ask before it is built (the Mobile log's H-3 stop, restated for the new model).
- **D-2:** [confirmed] Disconnect clears this device's binding for this Nexus and nothing else: the device key stays, and the server's approval stays until revoked. The device's name is server state too, on the device's one global row (G-1), so connect carries it and upserts it, and a rename re-issues connect for the open Nexus and is visible from every Nexus at once. Connect against a server that already holds the Nexus id registers this device pending unless it is the device that created the row.
- **D-3:** [confirmed] The device list is fetched when the heading opens and on a manual refresh; no background poll and no push in this arc, since there is no change feed. The heading has three states: unbound; bound and approved, showing the list; and bound but not approved (pending, or revoked, which the server answers as not-found per G-3), showing the binding and that this device awaits approval. When the bound server is unreachable, the heading shows the binding and the failure. Every action is one request, so nothing applies partially. Approve and Revoke are idempotent, so a repeated press is a no-op. A device name is bounded and non-empty; the server refuses a malformed public key or a non-ULID Nexus id.
- **D-4:** [confirmed] The Mobile plan's Tasks 12 and 15 describe some of this design (the secret store, the Settings row kinds) and are inherited where they still hold.

#### E — Placement

- **E-1:** [confirmed] Three homes. The app holds what belongs to the device or the person: the device key, id, and name, and any future login. The Nexus folder holds what belongs to the Nexus: its id in `.nexus/nexus.json` and its travelling config. The server holds what every device must share: the device list and, in the sync arc, the info record with the wrapped-key list, keyed by Nexus id.
- **E-2:** [confirmed] Which server a Nexus is bound to is per Nexus, per device: a `sync` scope in `local_state`, a singleton since `nexus.db` is already per Nexus. Two Nexus' may live on two servers. This replaces Mobile H-2's app-level server address.
- **E-3:** [confirmed] The server's data lives where the server runs, in its own SQLite file in an env-configured directory; never in the app's config and never in a Nexus.
- **E-4:** [confirmed] The initial server is one Node file in `Sync/` on built-ins alone (`node:http`, `node:sqlite`, `node:crypto`), run as `node` on the source with type stripping, so it uses erasable syntax only. It runs as its own process on Nathan's Mac for this arc, started by one command from the repo, never bundled into the app and never inside a Nexus. Docker, TLS, and deployment wait for the sync arc (restates Mobile G-1's shape, minus items, versions, blobs, and the feed).

#### F — Seams

- **F-1:** [confirmed] Wire types live in Core (`Core/Sync/contract.ts`): the device record, the Nexus record, the request and response shapes. `Sync/` reaches them with `import type` only, which type stripping erases at run time; Core never imports `Sync/`, since the engine gate's allowlist is `ulidx`, `yaml`, `zod` (`Core/Contract/engineGraph.test.ts:12`). This settles the Mobile log's H-1 against its plan: the client model is Core's, the server is `Sync/`'s. A value import would work under type stripping but drags `ulidx` and the machine seam into a built-ins-only process, so the server re-spells what it must execute and this entry owns that duplication: two validators (a ULID pattern, a 32-byte key length), the fingerprint recipe, and the canonical signing string. `Core/Sync/contract.ts` stays type-only and imports nothing, since Core is CommonJS-format under `nodenext` and any value-exporting Core file pulled into Sync's program, transitively and even through `import type`, fails Sync's `verbatimModuleSyntax` gate with TS1287; its wire replies are plain objects, never `Result`, for the same reason; Core's executable half (the canonical-string builder, the validators) lives in a sibling `Core/Sync/` file the server never imports, and both suites assert the same test vectors, kept as one JSON fixture under `Core/Sync/` that Sync's tests read from disk.
- **F-2:** [confirmed] The device and the transport are two members of `HostContext` (`Core/Contract/handlers.ts:16-42`), since every channel the heading needs is an Ask whose handler already holds `ctx`, and `Core/Platform`'s ambient seams are for what the whole engine reaches. The device member exposes id, public key, name, and `sign(bytes)`; the host owns the private key, so generation, storage, and signing are the host's: Desktop generates with Node's WebCrypto, stores the exported PKCS8 bytes through `safeStorage`, and signs on request. Core sees only the public half and a signature. Outbound HTTP follows the existing precedent, `HostContext.fetchTitle` over Electron's `net` (`Core/Contract/handlers.ts:16-42`, `Desktop/Web/linkTitles.ts:1,12`): the client's requests go through the transport member (method, path, headers, body in; status and body out), which sends a string body as UTF-8 bytes unmodified, which Core's tests fake, and which a phone host binds to native HTTP. The body hash uses the machine seam's existing text `sha256Hex`.
- **F-3:** [confirmed] The server's HTTP surface is declared once in Core beside the wire types as a route table type of string-literal paths and typed bodies; the server's handler map is written `satisfies` that type, so a missing or mismatched route is a compile error under the type-only import, and the client derives its calls from the same table. The transport is the host member on the client and `node:http` on the server.
- **F-4:** [confirmed] The client runs in the host-run half of Core, in main, never in the renderer; the renderer reaches it through bridge channels like every other engine call, so no CORS exists on desktop. The phone's cross-origin case is the Mobile log's G-3.

#### G — Bootstrap And Request Auth

- **G-1:** [confirmed] Four verbs: connect (register this device for a Nexus id; the Nexus row is created if absent and that device is approved by construction, otherwise the device is pending), list devices, approve, revoke. A device is one global row keyed by fingerprint (public key, name); its state per Nexus is a membership row, so a name is the same on every Nexus and approval is per Nexus. A deploy-time admission secret for creating Nexus rows belongs to the sync arc, when the server leaves localhost.
- **G-2:** [confirmed] Every request is signed by the device key over one canonical string pinned in `Core/Sync/contract.ts` and re-derived by the server: the uppercased method, the path, the lowercase hex SHA-256 of the body (of the empty string when there is none), and the integer millisecond timestamp, joined by newlines. The body is stringified once, hashed as UTF-8 (the machine seam's default), and sent as those bytes; the server hashes the raw bytes it received. The device id, the timestamp, and the base64url signature ride as headers; the server verifies against the registered public key and refuses a timestamp more than five minutes from its clock. Connect carries the public key and is verified against it, proving possession. No session table, no token. A session token is a later optimization if measurement asks for it.
- **G-3:** [confirmed] Connect is idempotent on the public key. A Nexus id the caller's device isn't approved for answers not-found, never forbidden, so a foreign id is never confirmed to exist (carries Mobile G-2). List, approve, and revoke require an approved caller.
- **G-4:** [confirmed] Revoke removes server access and nothing else; it does not un-know a Nexus key a device already holds. Key rotation is the sync arc's.
- **G-5:** [confirmed] The server's schema carries a version row and grows additively, on the rule `nexus.db` follows (carries Mobile G-4).

#### Prospects (allowed later, not now)

- A desktop-hosted server (the Mac's app serving the phone directly) — why deferred: it sleeps with the laptop, and v0 establishes the always-on shape; Nathan may weigh it later as a deliberate trade; don't-foreclose: the server is one process over `node:http` and SQLite, and nothing in the client assumes where it runs.
- Accounts (a user grouping devices, roles, invites, a hosted identity provider) — why deferred: a workspace of a few people pairs devices; don't-foreclose: the device id is the key fingerprint from day one, and the server's model treats device ownership as a layer that can be added, never as the device's identity.
- Relocating `nexus.db` and `versions.db` out of the Nexus folder into app storage keyed by the Nexus id — why deferred: Nathan wants to explore it later and records it in [[ContextPM]]; don't-foreclose: the store-open path takes a root and nothing else keys on the databases' location.
- "Make this a new Nexus" (fresh id, thumbnail folder renamed) — why deferred: a copy is a replica by rule; don't-foreclose: the id is written in one place, `ensureIdentity`.
- A per-device `settings.local.json` overriding display-bound settings (Interface Scale, Webpage Zoom) — why deferred: the final settings shape isn't this arc's; don't-foreclose: `settings.json` stays the one travelling settings file and the device tier stays `devicePrefs`.

- A session token in place of per-request signing — why deferred: four verbs don't need it; don't-foreclose: the signature check is one function on the server.

#### Considered & Rejected

- Account + devices with a hosted OpenID Connect provider (Auth0, WorkOS AuthKit, Firebase Auth, Clerk) — set aside 09-10-2026 as the day-one model: a vendor, a browser redirect flow on two hosts, and token verification, for a grouping layer that adds nothing until more than a few people share a Nexus. Kept as the Accounts Prospect's evidence.
- Self-hosted identity servers (Keycloak, Authentik, Ory, Zitadel, Better Auth) — rejected 09-10-2026: maintenance Nathan will not carry.
- Pommora-held password hashes with a reset flow — rejected: a user database of Pommora's own, and a built-ins-only server has no mailer for resets.
- The Nexus password as the only credential — rejected: nothing to revoke without re-keying the Nexus.
- A random ULID as the device id — rejected: it would need re-minting once devices must prove themselves; the key fingerprint is stable and self-certifying from day one.
- Two instances opening one Nexus folder as the end-to-end proof — rejected: `Desktop/main.ts:294` states a second process on one Nexus races every write; a copy is the replica the model already defines.
- Decisions-only with no code — rejected 09-10-2026: an unconsumed seam is dead code by the project's standard; the initial server is the consumer that makes the pavement verifiable.
