## File History — Decision Log

### Frame

- **Purpose:** Pages gain **File History**: device-local snapshots taken around editing, browsed in a floating History window that lists a page's snapshots beside a read-only render of one, with restore replacing the body alone and deletion beside it.
- **Core Value:** A page's prose is recoverable to any point in the retention window without leaving Pommora, and without touching its properties, identity, or location.
- **Success Criteria:** Editing a page over time produces a bounded set of snapshots; each opens readable in the window; restoring one replaces the live body and is reversible from the same list; frontmatter and path never change through a restore; the retention default prunes without user action; an unchanged body never produces a duplicate snapshot.

### Decisions

Every entry is a settled call unless tagged `[assumed]` or `[open]`. Vocabulary: the feature is **File History**; its window is the **History window**; a stored entry is a **snapshot**.

#### S — Scope

- **S-1:** [confirmed] Recovery is body only: a restore replaces the body and leaves frontmatter, identity, and path untouched, by construction, since the only restore path writes through the body writer.
- **S-2:** [confirmed] A snapshot stores the whole file text (Nathan, 09-02-2026), deduped by body, with body-only enforced as a projection at the restore boundary through `splitEnvelope`. Frontmatter is a few hundred bytes against a 9.5 KB average, and storing it keeps the SQLite store and a later git provider reading identically, since git can only store files. That parity is the whole reason: a frontmatter-only change never captures (T-4), so the blob is not a property history.
- **S-3:** [confirmed] Surfaced per page; GitHub is out of scope.
- **S-4:** [confirmed] Pages only for now (Nathan, 09-02-2026). The hook sits on `updatePageBody`, the one user-edit body writer; the ULID kind mark (`P`) admits a page and nothing else, so Tasks and Events stay out until a decision lets them in.
- **S-6:** [confirmed] Space tiles and Space markdown blocks are not tracked (Nathan, 09-02-2026); the Homepage's blocks are the same case. They write through `blocks:save` / `blocks:updateMarkdown` (`src/main/blocks.ts`), never `updatePageBody`, so nothing filters them; the plan must not extend the hook there.
- **S-5:** [assumed] A file without a real ULID (path-hash adopted id, pre-adoption) has no key and takes no row; adoption stamps at open, so the window is small. A file above a size cap takes no snapshot — VS Code's 256 KB is the precedent; proposed 1 MB.

#### T — Trigger

- **T-1:** [assumed] One gate governs every capture: **a page captures only when its last snapshot is older than the interval.** Two moments ask it. Before a user-edit write lands, the outgoing on-disk text is offered (the "before" of a burst, and the every-interval capture inside a long one); and a per-page timer, reset on every write and on every watcher event for that page, offers the current file once the page has been quiet for the interval (the "after"). A Nexus switch and app close offer every armed page ungated, dedupe only, since a just-edited page can never pass the interval; close is best-effort, since the renderer's final flush is un-awaited. A page gets at most one snapshot per interval, and the state before an edit is always kept. The system rewriters — cascade, sweeps, adoption, remint — never trigger it.
- **T-2:** [confirmed] External edits feed the same machinery: the watcher's `page-upsert` marks the page pending with source `external`. Under per-device locality this is the only route a phone's or Obsidian's edits have into this machine's history; the before-write hook fires only when this machine edits. Coverage is best-effort — the echo window hides writes inside it.
- **T-2a:** [assumed] The gate has one exception, for the lost-update case: when the outgoing on-disk text is not what Pommora itself last wrote to that path — someone else's write landed since — the before-write hook captures it regardless of the interval, dedupe only. Main keeps a `Map<path, hash>` of the body `updatePageBody` last wrote — fed by that writer alone, so a cascade or sweep rewrite that a stale editor then overwrites is also caught; the comparison costs one hash of bytes already in hand. This catches foreign writers only: a second Pommora host clobbering the first (see Lessons) writes through the same map and is invisible to it. Without this, an external write landing inside the interval and then overwritten by the stale editor's autosave would never exist anywhere, and the Lessons claim would be false.
- **T-3:** [assumed] One capture function, three callers. `captureIfDue(pageId, fileText, source)` holds the whole rule — the toggle, the gate, body dedupe, size cap, the insert. The body writer reads the outgoing text inside the page's file lock — `writePageFile` reads the file internally and returns nothing, so it returns the previous text as an additive return — and its read-failure branch changes (Nathan, 09-02-2026, "absolutely unacceptable"): today every read error is treated as a new file and the page is rewritten from empty frontmatter, body only, its `ID` destroyed. After: only a missing file (`ENOENT`) starts from empty frontmatter, and that only on the creation path; any other read failure refuses the write, on the standing rule that a write built on a failed read must refuse (`rmwJsonStrict` is the precedent). A refused body write returns its `Result` to the renderer's writer, which already requeues on `!ok`. Nothing is captured for a refused write — and offers it after the write returns, outside the lock (source `edit`); the page id comes from the live tree by path, never from parsing frontmatter per save; the per-page timer calls it with the current file (`edit` or `external`, whichever armed it last); restore calls it ungated (`restore`). The gate reads an in-memory `Map<pageId, lastTs>` seeded lazily from the store, so the hot path — every 400 ms autosave — touches SQLite only when a capture is due; the hash runs only after the gate passes. Timers live in one `Map<pageId, Timeout>` holding no path: the path is resolved at fire time by inverting the per-tree path→id index (`pageIdIndex`, 0.03 ms at NexusOS scale), so none of the five relocation paths — page rename, container rename or move, trash, restore, root rename — needs a hook; an id the tree no longer holds disarms, and so does an id two paths claim, since a Finder-duplicated page shares its twin's `ID` until the next open's remint. Both the timer map and the gate map clear where the store closes, so nothing armed in one Nexus fires into another's store. Capture is synchronous once the text is in hand (`DatabaseSync`), so nothing is ever in flight across a switch. On a Nexus switch main offers every armed page ungated (dedupe only) before it closes the store and drops the live tree; the renderer's `flushAllPageSaves` already precedes the switch, so the final bodies are on disk by then. App close is the same offer, best-effort behind the renderer's un-awaited final flush.
- **T-4:** [assumed] Dedupe by the body `splitEnvelope` returns: a capture whose body equals the page's latest snapshot's body writes nothing. Never by mtime or raw bytes: the envelope normalizes CRLF and the leading blank line on every write, and system rewriters change bytes without moving mtime.
- **T-5:** [assumed] A restore captures the current text first, ungated (source `restore`), then replaces the body. Typing coalesces under the interval; a restore never does. Restore is therefore undoable through the same list.
- **T-6:** [assumed] Capture is best-effort and outside the save's success path: it runs after the body write returns, its failure is logged and never surfaces to the writer, and the write's `Result` is settled before it starts. The store is never read to produce current state; a missing or corrupt store loses history and nothing else.

#### R — Retention

- **R-1:** [confirmed] Age is the only cap: 90 days default, user-configurable. No per-page count cap; the interval already bounds the rate (~12 per hour of continuous editing at 5 min).
- **R-2:** [assumed] Retention is one age-bounded `DELETE`, run at open and from the settings write when the timeframe shrinks.

#### W — Where It Lives

- **W-1:** [assumed] The seam is the store module, the way `driver.ts` is a module rather than an interface: `add`, `latest`, `list`, `read`, `delete`, `clear`, `sweep`, and nothing above it. Capture policy (T-3) and restore (T-5, U-5) sit above the store and are provider-independent, so a second provider is a second module behind a switch when it exists, not an interface built now. The renderer sees rows only, shaped in `src/shared/types.ts` backend-neutral: opaque snapshot id, timestamp, source (`edit` / `external` / `restore`).
- **W-2:** [assumed] The watcher ignores every `.db`, `.db-wal`, `.db-shm` name directly under `.nexus`, as one more `segs[0] === NEXUS_DIR` clause beside the two at `watcher.ts:71-77` — not in `neverWatched`, which takes a bare segment (so can't be scoped) and which `adoptFile` shares (so would refuse `.db` file attachments). SQLite writes never pass `recordWrite`, and an unexcluded `.nexus` entry classifies `full-refresh`; every capture would otherwise cost a verification walk.
- **W-3:** [confirmed] The store is its own SQLite file, `.nexus/versions.db`, opened through the existing `openDb(path)` seam, separate from `nexus.db` so the disposable database stays disposable and history keeps its own lifetime with no migration framework. Nathan (09-02-2026) accepts per-device locality. Files were rejected on storage: at a 1:100 history ratio NexusOS (315 pages, 2.9 MB, 196 pages under 4 KB) would hold ~31,000 small files and ~290 MB with APFS block rounding, where compressed rows are ~100 MB and reverse deltas ~10 MB.
- **W-4:** [assumed] One table — `page_id, ts, source, blob`, primary key `(page_id, ts)` — with `CREATE TABLE IF NOT EXISTS` re-applied on open, the `nexus.db` pattern. No version row: the schema grows additively, a later column arriving as `ALTER TABLE ADD COLUMN … DEFAULT`, and nothing ever deletes the file, since it is the one file in `.nexus` that can't be rebuilt. The DDL is not a health check — a store corrupted past its header opens, passes `CREATE TABLE IF NOT EXISTS`, and throws `database disk image is malformed` on every read and write, Clear History included (executed against `node:sqlite`) — so open runs `PRAGMA quick_check` inside a try/catch (it throws on interior corruption rather than reporting) and, on a failed check **or on `openDb` returning `null` for a file that exists** (a garbage or truncated header never reaches the check), renames the file **and its `-wal` and `-shm` siblings** to `versions.db.corrupt-<stamp>` and opens fresh, logging it — a fresh open beside an orphaned hot WAL adopts and deletes it (executed) —; Clear History falls back to the same rename. `openDb`'s failure log names `nexus.db` and takes the file's name instead. `source` stays because it is known only at capture time and can't be backfilled; the title is the page's current one, known to the page-bound window; a delta encoding and a body hash are columns a later need adds.
- **W-5:** [assumed] Text is stored as zlib-compressed full text (Node's built-in `zlib`, no dependency; 2.9x measured on NexusOS prose). Restore is one row read.
- **W-9:** [confirmed] The store stays inside the Nexus, and Pommora seeds no `.gitignore`: NexusOS's own repository tracks `nexus.db` today and will track `versions.db`, and Nathan (09-02-2026) accepts that as his repository's business.
- **W-6:** [assumed] Per-device locality is accepted knowing the file's bytes still travel with a synced Nexus. A second Mac writing the same file can corrupt it; under T-6 that loses history and nothing else. The per-device-file split (`versions-<device>.db`, each machine writing its own and reading all) is the Prospect that removes it.
- **W-7:** [assumed] Keyed by `ID`, not path. Rename and move preserve the ULID; the trash record already joins on ids. A remint (duplicate id) leaves the history with the original by the baseline's rule; the copy starts fresh.
- **W-10:** [confirmed] Trash recovery preserves history, and it is free (Nathan, 09-02-2026): a page's rows are keyed by `ID`, a delete to `.trash` never touches the store, and a restore returns the page under the same id (the record's restore refuses when that id is already live, so it never re-keys), so the restored page reads its history as if it had never left. Only the age sweep and Clear History remove rows, which also means a page permanently deleted from the trash keeps its full text in the store until the timeframe expires. Nothing to build; the plan must not add a delete-the-rows-on-page-delete step.
- **W-8:** [assumed] Snapshots are frozen. The rename cascade does not rewrite `[[links]]` inside them, same as `.trash`; a restored old body can carry a stale title. Known consequence.

It enters as `opts.history` beside `opts.reveal` with its own `separatorBefore`, so it reads as its own group rather than attaching to Copy or New Page; `main/contextMenu.ts` passes it (the page Settings menu's footer does not — that menu already carries the History row, and its footer chain never reaches the shared router), and the subset consumers — tab, nav row, card, title cell — gain `title:history` in their explicit lists **and** `pageMetaMenuSubset` passes `history: true`, since it hardcodes its opts. The action is routed once, in `runPageSendAction` (`Actions/pageMenuActions.ts:22`), the shared first router every consumer already calls and whose boolean they honor — one `openHistory` there rather than four per-surface chains — resolving the id from the renderer's tree index; the native menu's push is `open-history` on the `open-in-preview` precedent. No exhaustiveness check: the switch is on a cast expression, so none can be written against it. `pageMenu.test.ts` updates.
- **U-2:** [assumed] The History window is a new floating window on `WindowBase` holding a snapshot list and a read-only body render, rather than riding the Page Window. The Page Window is one-at-a-time, fully editable, and its tab strip is bound to `preview.tabs`; a history view needs neither. Its state is a page target, `historyTarget: PreviewTarget | null` on `PreviewSlice` beside `openPreview`, not a boolean flag. Layout is U-9's.
- **U-3:** [assumed] The body render mounts `MarkdownEditor` directly with `readOnly` and a per-snapshot `key`, never `PageTile`, which wires `schedulePageSave` and would write a snapshot over the live page. `readOnly` does not reach a snapshot's `![[embeds]]` — interactivity is a depth question (`embedWidget.tsx:478`) — so the render passes a two-deep ancestors chain the way the hover pane does, and every embed renders inert. - **U-5:** [assumed] Restore is one main-side act for open and closed pages alike: capture the current text ungated, then run the body write's own tail (`updatePageBody` → index → note → push). The renderer flushes the page's pending save first (`flushPageSave`, a no-op on a closed page — this is what stops the 400 ms debounce writing the pre-restore doc back), and afterwards drops the page's warm entry *including* its editor state — `dropWarmDetail` deliberately keeps editor state, so this is a small per-path helper beside it, the rename cascade's nexus-wide `clearWarm` being the precedent — and re-seeds every host holding that path — the shown editor, the Page Window's tile, any `![[embed]]` of it — since a mounted editor never re-seeds and a second host left standing writes the pre-restore body back 400 ms after its next keystroke. The re-seed is a **refresh, never a drop**: there are three warm seams with three keys and three fences (Sources), the outgoing editor's cleanup refills a dropped cache before the incoming editor reads it (executed), and the embed seam's fence is blinded by an absent detail. So restore writes the restored text into the detail slot and the navigation slot's body (the renderer holds it — it just rendered it), the three seams share one fence that compares the cached doc against that fresh body, and each host re-seeds on a `bodyReplaced(path)` signal consumed as an effect inside `PageTile` that resets its `loaded` seed from the refreshed detail — not a key bump, which re-runs nothing above the inner editor, and never at the widget layer, whose nudge reconciles in place; `PageView` needs nothing, since its `initialBody` is the live slot body. The fence takes its fresh body as an argument — `PageView` hands it `slot.body`, tiles and windows hand it `readPageDetail(path)?.body` — and keeps the warm entry when no fresh body is known, since a strict rejection would kill warmth for every cold-detail embed and `DETAIL_CAP` evicts details while the tile cache has no cap. The refresh calls `cachePageDetail` (create-or-update), not `writeThroughBody`, which updates only and has never held the main pane's page. Main's restore answers with the page's *resolved path*, and every path-keyed renderer step — the flush, the detail refresh, the slot patch, the signal — uses that answer rather than the window's target path, which U-8 lets go stale across a rename or move. The rename cascade's `clearCache` is not the precedent: a rename moves every seam's key, a restore moves none. Restore's undo is the snapshot it captured, not ⌘Z. The same signal is what the watcher will drive when the external-edit reload is built (Prospects).

#### Prospects (allowed later, not now)

- **Reverse deltas** once the file is measured to matter: the newest snapshot stays full, each older one becomes a delta against the next newer when a new one lands; `fossil-delta` (2 KB, exact, checksummed) is the codec; an `encoding` column arrives with it.
- **Per-device store files** with union reads (W-6), for a second writing machine or the mobile companion.
- **A git provider** as a second store module behind a setting: list is the commits touching the page's current path, read is that commit's file text, capture is a commit of the armed pages. It must use a separate git dir under `.nexus` with the Nexus root as its work tree, since NexusOS is already the user's own repository; retention doesn't translate (pruning is history rewriting), so the timeframe stays the snapshot store's.
- **External-edit reload** — the watcher's `page-upsert` driving the same `bodyReplaced(path)` signal restore uses, which closes the lost-update bug in Lessons.
- **Diff view** — `unifiedMergeView({original: snapshot})` over the live editor, "what would restoring change"; also serves the trash compare view. Don't-foreclose: keep the snapshot text reachable as a plain string.
- **Per-page opt-out** and **named snapshots** (Trilium, VS Code).
- **Change badges** in the list via headless `Chunk.build`.
- **Copy-out** a snapshot as a new page (Joplin's restore model) beside replace.

#### Out of Scope (won't do)

- GitHub, remotes, any network.
- Frontmatter, property, or location *recovery* — the record layer's arc (NexusRecordPM Pending "Change capture"); the stored text keeps it reachable.
- Homepage and Space block bodies, and Space tiles (S-6).
- Reading Obsidian's File Recovery store — IndexedDB in the global app folder, private API.

#### Considered & Rejected

- **Git first — as the only provider, as one of two from day one, or as a window over the user's own `git log`** — the honest opposite: whole-tree history including sidecars and properties, standard tooling, the user pushes wherever. Fails the mobile lens (a phone can't run it), has no retention, keys by path with rename heuristics, puts a `.git` worth of small objects in a synced `.nexus`, and offers nothing to a user without git. It stays the second store the Prospects admit.
- **Files, one per snapshot, in a root dot-folder** — legible and sync-friendly per file, but the small-file count and APFS rounding make it the least storage-efficient option by an order of magnitude; see W-3.
- **A table inside `nexus.db`** — ties history to the disposable database's drop-on-version-mismatch lifetime.
- **Persisting CM6 undo history per page to disk** — "infinite undo" with no store. The editor already serializes history for warmth, but history is a keystroke log, not legible, not translatable, and breaks the moment another tool writes the file.
- **A renderer-side timer** (Obsidian's model) — the renderer is identity-blind and path-keyed, and only main sees the outgoing bytes before a write lands.
- **Riding the Page Window** — see U-2.

#### Lessons

- The open editor never reloads on an external change, and the next autosave writes the stale doc back — Obsidian, or a phone, editing an open Pommora page is a silent lost-update today. T-2a makes that case recoverable; it does not fix it, and a mobile companion makes it a second live writer. The same loss happens *inside* Pommora: six mount sites share one path-keyed writer and none re-seeds, so a page open in the main pane and the Page Window loses the paragraph typed in whichever host saved first, and T-2a cannot see it because both hosts are Pommora. → a Known Issue in [[ContextPM]]; the `bodyReplaced` signal (U-5) is the seed of the fix.
- `writePageFile` swallowed a failed read into an empty string and wrote the body without its frontmatter, destroying the page's `ID` — an evicted sync placeholder was enough. Fixed inside this feature (T-3); the rule generalizes: a page write built on a failed read refuses.
