#### A19 Tooling Research — Pommora Monorepo Split

Verified against the installed tree on 09-05-2026: electron 42.4.0 (Node 24.16.0), electron-vite 5.0.0, electron-builder 26.15.3, vite 7.3.5, @vanilla-extract/vite-plugin 5.2.2 (integration 8.0.10, compiler 0.7.0), vitest 4.1.8, @biomejs/biome 2.5.1, typescript 6.0.3, npm 11.12.1. Web search/fetch tooling was unavailable this session; documentation was pulled from the projects' own repositories (raw markdown), the installed package sources, `gh api`, and context7.

##### 1. Package Manager: npm Workspaces vs pnpm vs Bun

**Recommendation: stay on npm workspaces.** npm 11.12.1's default `install-strategy` is `hoisted` (verified: `npm config get install-strategy`), so one root `node_modules` holds one copy of React and each workspace is a symlink into it (`node_modules/a -> ../packages/a`, [npm workspaces docs](https://github.com/npm/cli/blob/latest/docs/lib/content/using-npm/workspaces.md)); one `package-lock.json`. electron-builder 26 resolves production deps by running `npm list -a --include prod --include optional --omit dev --json --long` in the app package and realpath-ing symlinks (`app-builder-lib/out/node-module-collector/npmNodeModulesCollector.js`, `moduleManager.js:47`); npm-workspace fixes landed in 26.0.0 ([#8715](https://github.com/electron-userland/electron-builder/pull/8715)) and 26.9.1 ([#9692](https://github.com/electron-userland/electron-builder/pull/9692)). pnpm's default `nodeLinker: isolated` is where the open bugs sit ([#10000](https://github.com/electron-userland/electron-builder/issues/10000) open, #9711/#9903 closed), and electron-vite's troubleshooting page tells pnpm users to `shamefully-hoist=true` or switch to npm/yarn. Bun defaults new workspaces to the isolated linker and documents a `hoistingLimits: "workspaces"` escape hatch specifically because "Electron packagers … walk, prune and repackage one workspace's node_modules" ([Bun workspaces](https://github.com/oven-sh/bun/blob/main/docs/pm/workspaces.mdx)); electron-builder's Bun collector (26.3.0) has a regression trail (#9490, #9494, #9641). Native modules: `npmRebuild` defaults to true; `node:sqlite` exists in Electron 42 (verified `DatabaseSync`), so the SQLite seam can avoid native modules entirely. Add `resolve.dedupe: ['react','react-dom']` to the renderer configs as the belt to hoisting's braces ([Vite](https://github.com/vitejs/vite/blob/main/docs/config/shared-options.md)).

**For Nathan:** npm is the slowest installer but the only one where every tool in this stack is on its tested path; the others trade that for speed and strictness you don't need at five packages.

##### 2. Task Runner at Five Packages

**Recommendation: none yet; npm scripts suffice.** `npm run <script> --workspaces --if-present` runs "in each workspace in the order they appear in your package.json" ([npm docs](https://github.com/npm/cli/blob/latest/docs/lib/content/using-npm/workspaces.md)); there is no dependency ordering, so list Core → UIX → hosts in the root `workspaces` array. Because nothing is compiled before consumption (Q3/Q5: Vite and tsc read Core's TS source directly), order matters only for scripts that emit artifacts, and typecheck/test/lint run as root-level tools anyway (Vitest projects, one Biome root). Turborepo "is built on top of Workspaces" of npm/pnpm/yarn/bun, declared via `devEngines.packageManager`, and adds a `turbo.json` task graph with local/remote caching ([turborepo.dev](https://turborepo.dev/docs/getting-started/add-to-existing-repository)); Nx and moonrepo are the same category with more surface (moon adds toolchain pinning, Nx adds plugins/graph). With one developer and no cross-package build outputs, a cache hit saves seconds while adding a configuration layer every agent must learn. Revisit when a package emits something another package waits on (e.g., Core declaration output for Sync) or CI time hurts.

**For Nathan:** a task runner is an accelerator for repeated builds; you don't have repeated builds, you have one Vite dev server per host.

##### 3. TypeScript: Project References vs Path Aliases Across Workspaces

**Recommendation: no cross-package project references. Import Core by package name; Core's `package.json` `exports` points at `./src/index.ts`; both sides use `moduleResolution: "bundler"`; drop `composite`.** References load a referenced project's *output* `.d.ts` ([handbook](https://github.com/microsoft/TypeScript-Website/blob/v2/packages/documentation/copy/en/project-config/Project%20References.md)); unbuilt, `tsc` fails with TS6305 "Output file has not been built from source file" — only the editor's in-memory redirect hides it. `composite` also demands every file be under `include` (TS6307), which Core source pulled through the workspace symlink violates. Vite treats linked deps as source and auto-allows the workspace root ([dep pre-bundling](https://github.com/vitejs/vite/blob/main/docs/guide/dep-pre-bundling.md), [server.fs.allow](https://github.com/vitejs/vite/blob/main/docs/config/server-options.md)). `paths` is TS-only: Vite 7.3.5 lacks `resolve.tsconfigPaths` (a Vite 8 feature; verified absent in `vite/dist/node/index.d.ts`), so aliases must be mirrored across three Vite configs, as today. Two tsconfigs per package (node/web) stay fine; Core files get checked under each consumer's `lib`, so keep Core DOM-free. TS 6.0 ([release notes](https://github.com/microsoft/TypeScript-Website/blob/v2/packages/documentation/copy/en/release-notes/TypeScript%206.0.md)): `baseUrl` deprecated (`paths` never needed it); `moduleResolution node10`/`classic` deprecated → `bundler`/`nodenext`; `rootDir` defaults to `.`; `types` defaults to `[]` (keep `"types": ["node"]`); `strict` defaults true; `bundler` now pairs with `module: commonjs`; TS 7 removes all of it, `ignoreDeprecations: "6.0"` bridges.

**For Nathan:** project references are a "build the library first" model; you want "read the library's source directly," which the package-exports route gives every tool at once.

##### 4. vanilla-extract Across Packages

**Yes, it works through the workspace symlink; the plugin belongs in each consuming app's Vite config only.** The Vite plugin's `transform` hook accepts any module id matching `/\.css\.(js|cjs|mjs|jsx|ts|tsx)(\?used)?$/` with no root or `node_modules` check (`@vanilla-extract/vite-plugin/dist/vanilla-extract-vite-plugin.cjs.dev.js:183-184`; `integration/dist/…:357`). Its compile step bundles with esbuild, externalizing only `@vanilla-extract`, so a `.css.ts` in UIX importing tokens from Core is bundled from source. Vite resolves symlinks to realpath (`resolve.preserveSymlinks` default false), so a sibling package's files aren't under `node_modules` and are watched (the plugin skips watching `node_modules` paths) — HMR works. `server.fs.allow` defaults to the detected workspace root (a `workspaces` field qualifies), so sibling sources are servable and the `server.fs.strict: false` hack in `electron.vite.config.ts` becomes unnecessary. Library packages (UIX, Core) need no plugin; Desktop renderer, Mobile, and Vitest do. Known issues: [#559](https://github.com/vanilla-extract-css/vanilla-extract/issues/559) (2022, `..` in URL, fixed); [#1717](https://github.com/vanilla-extract-css/vanilla-extract/issues/1717) — Windows `@id/C:/…` ids in a pnpm monorepo dev server, closed 05-16-2026; installed 5.2.2 (03-28-2026) predates that fix, 5.2.3 (06-23-2026) postdates it — only matters on Windows.

**For Nathan:** the styling system doesn't care which folder a `.css.ts` lives in; only the app that renders needs the plugin.

##### 5. electron-vite Consuming a Sibling Package

**Recommendation: real package import `@pommora/core`, declared as a devDependency of Desktop, with Core's `exports` at TS source.** electron-vite 5 externalizes `Object.keys(pkg.dependencies)` of `process.cwd()/package.json` for main and preload by default (`build.externalizeDeps: true`; `externalizeDepsPlugin` is deprecated in v5 and should be removed from the config — `electron-vite/dist/chunks/lib-*.js`, [migration](https://github.com/alex8088/electron-vite-docs/blob/master/packages/en-US/docs/guide/migration.md), [dependency handling](https://github.com/alex8088/electron-vite-docs/blob/master/packages/en-US/docs/guide/dependency-handling.md)). If Core sits under `dependencies`, the main bundle emits `require('@pommora/core')` and Electron 42's Node refuses at runtime — verified in this session: `ERR_UNSUPPORTED_NODE_MODULES_TYPE_STRIPPING: Stripping types is currently unsupported for files under node_modules`. Under `devDependencies` it is bundled ("they will be bundled as long as they are referenced"), and electron-builder's `--omit dev` collection never copies the Core folder into `app.asar`. AFFiNE enforces exactly this in its build script: "Electron workspace dependencies must be bundled and declared as devDependencies" (`packages/frontend/apps/electron/scripts/build-layers.ts`). An alias to `../Core/src` also works but must be repeated in `electron.vite.config.ts`, `vite.config.app.ts`, `vitest.config.ts`, and tsconfig `paths`; the package import is one declaration everything resolves. Renderer bundles deps regardless.

**For Nathan:** "dependency" tells the packager "ship this folder and load it at runtime"; "devDependency" tells the bundler "fold it into the build." Core must be folded in.

##### 6. Capacitor 8 iOS Inside a Workspace

**Recommendation: Mobile owns `capacitor.config.ts`, `ios/`, and its own Vite build; `webDir: 'dist'`.** Capacitor resolves `webDir` and `ios.path` (default `ios`) against `process.cwd()` (`cli/src/config.ts`: `webDirAbs: resolve(appRootDir, webDir)`), so `cap` commands run from Mobile/. `ios.path` can relocate the native project (AFFiNE uses `ios: { path: '.' }`). Plugin discovery reads Mobile's `dependencies` and `devDependencies` and locates each with `require.resolve(name, { paths: [root] })` (`cli/src/plugin.ts`, `cli/src/util/node.ts`) — Node walks up parent directories, so a hoisted root `node_modules` works; npm/yarn/pnpm workspaces are detected generically, NX gets special-casing (`cli/src/util/monorepotools.ts`). Capacitor 8 creates SPM projects by default ([8.0 update guide](https://github.com/ionic-team/capacitor-docs/blob/main/docs/main/updating/8-0.md); Xcode 26, iOS 15 target); `CapApp-SPM/Package.swift` pulls Capacitor itself from the `capacitor-swift-pm` git package and references plugins by a relative path from the Xcode project to their realpath (`cli/src/util/spm.ts`), so hoisting bakes `../../../../node_modules/…` — regenerated on every `cap sync`, never hand-edited. Pointing `webDir` at `../UIX/dist` is path-legal but couples Mobile to UIX's build entry; a Mobile-local Vite config keeps Capacitor plugins and `index.html` where the host lives.

**For Nathan:** the iOS folder is just a build artifact of Mobile; hoisting only changes how many `../` end up in a generated file.

##### 7. Biome 2 in a Monorepo

**Recommendation: one root `biome.json`; no nested configs until a package genuinely needs different rules.** Biome 2 supports nested configs with `"root": false` and the `"extends": "//"` microsyntax (which implies `root: false`); globs inside a nested file resolve relative to that file; a nested config without `extends` is standalone ([big projects guide](https://github.com/biomejs/website/blob/main/src/content/docs/en/guides/big-projects.mdx)). Scoping per workspace is done at the root with `files.includes`: `!` removes files from lint/format, `!!` also removes them from indexing, and negations must follow a `**` entry — the current `["**", "!!**/dist", "!**/graphify-out"]` is correct ([configure guide](https://github.com/biomejs/website/blob/main/src/content/docs/en/guides/configure-biome.mdx)). Per-package rule differences fit `overrides[].includes` in the same file. `biome check .` from the root honors everything. The formatting hook keeps working as-is because it runs against whatever config Biome discovers upward.

**For Nathan:** one file agents can grep beats five files that drift; nesting is for teams with different standards, which you aren't.

##### 8. Vitest 4: Root Projects vs Per-Package Configs

**Recommendation: root `vitest.config.ts` with `test.projects: ['Core', 'UIX', 'Desktop', 'Sync']` (folder entries) and a small `vitest.config.ts` per package via `defineProject`.** Vitest 4 removed `test.workspace`; `projects` accepts folders, config files, or inline objects; a folder entry is named from its `package.json` ([projects guide](https://github.com/vitest-dev/vitest/blob/main/docs/guide/projects.md)). Per-package configs set their own `environment` (Core `node`, UIX `jsdom`) and plugins (React + vanilla-extract only where components mount); `// @vitest-environment jsdom` per file keeps working inside a project, as today. Root-only options — `coverage`, `reporters`, `resolveSnapshotPath` — stay in the root. In 4.1.8, inline projects inherit root options only with `extends: true` (type comment in `vitest/dist/chunks/reporters.d.*.d.ts`); Vitest 5 flips that default. File-based projects never inherit — share via `mergeConfig` with a `vitest.shared.ts` if duplication appears. Aliases disappear once Core is a package import (Q3), which is most of what the current `vitest.config.ts` carries.

**For Nathan:** one `npm test` at the root still runs everything; each package just declares which world (Node or browser) its tests live in.

##### 9. Prior Art: Engine / Host / UI Splits

Every mature codebase surveyed uses lowercase `packages/`-style folders; none uses PascalCase. AFFiNE ([toeverything/AFFiNE](https://github.com/toeverything/AFFiNE), yarn workspaces): `packages/{common,backend,frontend}` with `frontend/{core,component,apps/{electron,electron-renderer,web,mobile,mobile-shared,ios,android}}`; iOS is Capacitor (`webDir: 'dist'`, `ios.path: '.'`), Electron is electron-forge with an esbuild-bundled main and the devDependency guard quoted in Q5. Joplin ([laurent22/joplin](https://github.com/laurent22/joplin)): `packages/{lib,app-desktop,app-mobile,app-cli,server,renderer,editor,…}`, yarn workspaces after Lerna. Standard Notes ([standardnotes/app](https://github.com/standardnotes/app)): `packages/{snjs,models,services,encryption,web,desktop,mobile,…}`, yarn berry with `workspaces foreach --topological-dev`; `mobile` is a React Native shell hosting `@standardnotes/web` in a WebView (`MobileWebAppContainer.tsx`) — the shared-renderer pattern with a different host than Capacitor. Logseq ([logseq/logseq](https://github.com/logseq/logseq)): `src/{main,electron}`, engine libraries in `deps/{graph-parser,db,outliner,common,…}`, Capacitor `ios/` and `android/` at the root (`webDir: 'static/mobile'`), with a lint enforcing worker/frontend separation. Anytype ([anyproto/anytype-ts](https://github.com/anyproto/anytype-ts)): `src/ts` + `electron/`, engine in a separate Go repository (anytype-heart) behind a middleware protocol. Zettlr: single package, `source/{app,common,win-*}`, electron-forge + webpack. Obsidian's API ([obsidian.d.ts](https://github.com/obsidianmd/obsidian-api)) is the cleanest published seam: `Vault.adapter: DataAdapter` with `FileSystemAdapter` (desktop) and `CapacitorAdapter` (mobile), plus `Platform.isDesktopApp/isMobileApp` — a host-neutral engine over an injected adapter, which is what Core-vs-Desktop/Mobile should look like.

Public regrets are about tooling and boundaries, not folder names. Joplin left Lerna because it was "essentially deprecated and certain bugs that are becoming more and more of a problem as the repo grows in size will never be fixed" ([forum, 12-20-2021](https://discourse.joplinapp.org/t/switch-to-yarn-3-to-manage-monorepo/22512/1)). AFFiNE's guard exists because a workspace package in Electron's runtime `dependencies` breaks packaging, and its large yarn graph produces peer-conflict noise on plain `yarn install` ([#9866](https://github.com/toeverything/AFFiNE/issues/9866)). Logseq's `graph-parser` README now says the library "mainly exists to convert file graphs to DB graphs" — the architectural regret was file-based storage, and the `deps/` boundary is what made the migration tractable. The transferable lesson: hosts stay thin and bundle the engine; the engine never imports a host; naming (`apps/` vs `packages/frontend/apps`, lowercase vs PascalCase) is convention with no tooling consequence — globs like `projects: ['packages/*']` don't care about case.

##### 10. The CJS Claim

Electron ≥ 28 supports ESM in the main process and in preload scripts through Node's loader, Electron 42 included ([Electron ESM tutorial](https://github.com/electron/electron/docs/tutorial/esm.md)). The constraints: "Sandboxed preload scripts are run as plain JavaScript without an ESM context" and load the API via `require('electron')`, so with the default `sandbox: true` the preload must remain CommonJS (bundled); ESM preloads need the `.mjs` extension and an unsandboxed renderer; an ESM main must `await` its setup before `ready` because imports load asynchronously. electron-vite 5 follows suit: `"type": "module"` (or per-target `build.rollupOptions.output.format: 'es'`) emits `.mjs` for main and preload, and its docs restate that "preload scripts must be unsandboxed" for ESM ([dev guide](https://github.com/alex8088/electron-vite-docs/blob/master/packages/en-US/docs/guide/dev.md)). So the project docs' phrasing "`require('electron')` fails on ESM" is imprecise — in ESM you `import { app } from 'electron'` and it works; the real reason preload stays CJS is the sandbox. The failure Nathan actually hits is `ELECTRON_RUN_AS_NODE=1` making `require('electron')` return a path string — unrelated to module format. Keeping main and preload CJS is a valid choice today and costs nothing; converting main to ESM is optional and buys nothing this stack needs.

##### Summary

Stay on npm workspaces: npm 11 hoists by default, electron-builder 26's collector is built around `npm list` and has its open bugs on pnpm's isolated layout and Bun, and `node:sqlite` in Electron 42 removes the native-module question. No task runner at five packages — `npm run --workspaces --if-present` runs in declared order and nothing is compiled ahead of consumption. Drop cross-package project references and `composite`; give Core a `package.json` `exports` pointing at TS source and let tsc, Vite, electron-vite, and Vitest all resolve it — TS 6 deprecates `baseUrl`/`node10`, defaults `types` to `[]`, and `rootDir` to `.`. Declare Core as a devDependency of Desktop so electron-vite bundles it; as a dependency it externalizes and Electron's Node refuses TS under `node_modules` (verified). vanilla-extract processes `.css.ts` from any path; the plugin lives only in consuming apps. Mobile owns Capacitor config, `ios/`, and its own Vite build; hoisting is tolerated via Node resolution and regenerated SPM paths. One root Biome config with `files.includes`; Vitest root `projects` with per-package `defineProject`. Prior art is uniformly lowercase `packages/`, thin hosts, bundled engines, and Obsidian's `DataAdapter` as the seam to copy. Preload stays CJS because of the sandbox, not because `require('electron')` fails in ESM.
