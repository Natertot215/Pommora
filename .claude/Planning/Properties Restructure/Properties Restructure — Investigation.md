##### Values: Reading, Writing, and Undo

**Explanation (For Nathan):** A property's value is read from a page's front matter (the block of properties at the top of a page's file) or from a Space's settings file, shown in a cell, and written back when you edit it. Reading is clean: nothing that reads ever writes. Writing works, but it's built from pieces scattered across three folders, it reads each page twice per edit, a test helper writes values a way the app never does, and the app's on-screen preview of an edit is computed separately from the real write and can differ slightly. Undo has two real defects. Undoing a Context pick on a page whose tag names a Space Pommora can't find (an Obsidian typo, say) deletes that tag outright. Undoing an edit on a key that was written bare (just "Status:" with nothing after it) writes "Status: null" instead of putting it back as it was. Separately, any edit to one property also quietly tidies every other property on that page, which you might not expect.

**Evidence:** Twelve write routes (02 Write Paths) reach bytes through `assignValue` → `mutate` → `setPagePropertyOp`/`setSpacePropertyOp` → `setGovernedRootKey`, with world-less side doors for creation seeds, the banner, and the test seeder. The pipeline owner is split across `Contexts/contextResolve.ts:42-132`, `Contexts/contextWrite.ts:75-86`, and `Properties/governedWrite.ts`, with a Properties→Contexts→Properties import loop (02-03). `propertyValue.ts` holds ten jobs (02-04); five "value"-named files mean five things (02-08). `setGovernedRootKey` parses twice and splits the envelope three times, and "page not found" is decided twice per write (02-06). `encodeValue`'s refusal guards a state the zod door already prevents (02-01). `writePageValue` lands with no world and no lock across 54 test calls (02-07/09-02). The renderer's `applyValueAtRoot` re-implements the host encode and the undo patch differs from both (02-05). A Collection's `properties` list has three parsers (02-11); creation writes a new page once per Context seed (02-16). **Undo:** the context arm re-sends decoded ids (`assignValue.ts:67`), so unresolved tag titles are lost; a bare key's `null` lands as `Status: null` through `nodeSpelledAs`/`mergeInto` (`pageFile.ts:146,172`); this is the unfixed half of I-063 (02-02, 09-13). A Space clear of an absent key repairs no siblings while a page clear does (02-14). Every write re-encodes every other governed key on the file (02 ledger; `governedWrite.ts:13`). Every value write re-reads and re-validates the whole registry from disk, O(R²) in `validateName` (08-05). The read path is read-only by construction (02 Read Path).

##### Schema Changes and Crash Recovery

**Explanation (For Nathan):** Some property changes rewrite many files: renaming a property, changing its Label Format, deleting it, renaming or removing an option. Before starting one, Pommora writes a small crash-recovery note so it can finish the job if the app quits halfway or a file can't be reached (an iCloud file that isn't downloaded, for example). One such note is shared by every property, with room for one change at a time, and that single slot causes most of the trouble here: while one change is still owed, a second rename or delete runs with no crash protection at all, and option renames, format changes, and option removals on any other property are refused with "An earlier change hasn't reached every file yet." Contexts and Spaces share a second note of the same kind with its own rules, their deletes put everything back and refuse when a page can't be reached, and "Try Again" works four different ways depending on what you were doing. Removing a property from a Collection, or clearing an option, can leave some pages untouched with no Try Again at all, and a second Remove does nothing.

**Evidence:** `journalSlot.write` returns `false` against a different held record or an unreadable slot (`journalSlot.ts:30-41`). `rekeyProperty` and `deleteInner` discard that return and proceed (`registryProperty.ts:183`, `deleteProperty.ts:123`); `rekeyOptions` and `removeOption` refuse `OWED` (`optionOps.ts:242,377`); Context and Space renames discard it and pass `supersedes` (03-01/04-01/04-03). Both property arms still attach `owed: record` to the reply, so the renderer carries a record that may exist nowhere, which is why `property:replay` accepts a record over IPC and the replay grew `answered` branches (`replaySchemaCascade.ts:54,78`). Seven hand-placed guards patch around the one slot (03 Refusal Catalog rows 2-8). A property delete commits the registry last with no reason its record needs, which forces the replay's `crashed`/`freed` disambiguation and `createProperty`'s delete-record consumption (04-02, `deleteProperty.ts:150-161`), and leaves a window where a value write lands behind the strip (04 A-01, INFERRED). The open runs two replays at two points, the Context one before the index is ready (04-07). Context and Space deletes write no note and are all-or-nothing: a missed member runs `undoSweep` and throws, and the Context entry is put back (`Trash/delete.ts:122-134`, `contextCascade.ts:167-181`), while a property delete already finishes and owes (`deleteProperty.ts:123-129`). Try Again has four vocabularies (04-08). Remove has no record and answers its skips as a refusal, so the editor stays open and a second Remove returns `NOTHING_TO_REMOVE` (`removeProperty.ts:33`) (03-03/04-13). `RenameJournal.skipped` is written and never read (04-04). Ten op entry points have seven reply shapes and four count functions (03-05). The schema lock wraps some registry writers and not others (03-04); five `defEditOp` channels are one operation (03-07/01-07).

##### Multi-File Updates, Reach, and Work Done on Open

**Explanation (For Nathan):** When a change has to touch many files, Pommora finds the files that might hold the property, then opens and rewrites each one. The shared machinery for this lives in the Properties folder even though Contexts, the Trash, Settings, and page banners all use it. Different changes pick their files by different rules: a property change only looks inside Collections and the Archive, while a Context rename or delete reaches any page in the Nexus, including loose pages outside every Collection. Space settings files are found by scanning the disk on every property change, even though the app already knows them, and one property delete scans them three times. Four Trash and restore routines write Space files with their own hand-made loops, two of which silently ignore a failed write, and one of those ignores failed page writes too. On every open, Pommora also re-checks every page in every Collection that has a Multi-Select property, to register words added while the app was closed.

**Evidence:** `governedSweep.ts` has 19 non-test importers, 8 outside Properties (04-14). 13 write loops in 10 functions, 12 read-only enumerators, and 9 world builders, of which several are one pattern (04 Mechanism Map). `sweepMembers` reads `queryMembers ?? nexusCorpus` unscoped while property sweeps filter through `governedReach`, and `sweepParse` admits loose files, so the outcomes differ; NexusOS's `Agenda/II. The sidecar arm reads every Space sidecar by disk scan while `spaceArm` and `sweepRootsById` gate from the tree; `scrubReturning` discards sidecar write failures and `refillTrashed` discards both its page and sidecar results (`holdings.ts:83-85`) (04-05). `registerHeldOptions(root)` at open walks every Multi-Select Collection's pages under the schema lock, one `stat` plus cached parse each, where the index already holds every value (04-06/03-12). `runRepairSweep` hand-rolls `pageWorldOf` (04-10); `frozenWorld(linkWorld(...))` is built at three sites (04-11). ##### The Removed-Values Stash and Remove

**Explanation (For Nathan):** When you remove a property from a Collection (as opposed to deleting it everywhere), Pommora strips its values off that Collection's pages and tucks them into the Collection's settings file, so re-adding the property later puts them back. You ruled for this in July, before sync existed. Several problems have surfaced since. It's the only copy of those values, and if two devices each remove a different property from the same Collection before syncing, one device's stash is lost for good and that property comes back as if it had never been removed. Entries for pages that later left the Collection are never cleaned out, which drifted from your July ruling that said they'd be dropped, and a page sitting in the Trash when the property is re-added never gets its value back. Deleting the property everywhere misses Collections sitting in the Trash. A Remove that can't read some pages leaves their values in place, unstashed, and it can't be retried. The stash stays, and these problems are fixed in place or by a better home [Intended as C-1, C-2].

**Evidence:** Remove moves values into `property_cache` then strips (`removeProperty.ts:47-60`); about 170 production lines across 11 files serve the stash (03 L-01, INFERRED count; `propertyCache.ts` is 68 lines, with 36 grep hits in eight other files). Origin: the 7-2 Decision Log C-3/C-6 (`052ceec63`, implemented `f85ccf2b3`) — Nathan's intent. Collection sidecars merge at depth `{}` (`mergePolicy.ts:38-39`), so both the stash and `properties` merge whole (03-02, 08-06, 08 L9). Stale entries live until a global delete, against C-6's "stale page-ids dropped" (03 L-02). A global delete reaches only `collectionFolders` (`governedSweep.ts:36-40`), missing Collections in the Trash, and discards `unassignAndPurge`'s write result (`deleteProperty.ts:163-172`); `restoreProperty` re-assigns before writing recorded blocks back (`restoreProperty.ts:45-54`), so those blocks never refill; Remove ignores `keyedHolders`' `partial` (`keyHolders.ts:61-65`), so an unreadable page keeps an unassigned value unstashed. ##### Option Identity and Saved Views

**Explanation (For Nathan):** Options (the choices in a Select, Multi-Select, or Status) have no permanent identity; they're known by their label. Saved views remember options by label too — a sort's custom order, which groups are hidden or collapsed, a filter's chosen values. So renaming an option forces Pommora to rewrite every view, tile, and graph filter that mentions it, and on two devices a rename can race a view edit and leave a filter that silently stops matching. Sync also has to treat a property's entire option list as one indivisible item, so two devices each adding an option to the same property lose one of the two. Collapsed groups have their own flaw: they're remembered by bare label, so a "Done" you collapsed while grouping by Status stays collapsed when you regroup by another property that also has "Done" — NexusOS's Pommora project tile, grouped by folder now, still holds Status collapses from an earlier grouping.

**Evidence:** Saved views name properties by `prop_` id and options by label in six roles (07 How Saved Views Name Things; `PropertiesPM.md:131`), so an option rename sweeps `configReach.ts:148-196`'s RENAME roles across every sidecar, tile document, `matrix.json`, and `openInPreview`. Options are `{ key, label, … }` with no id (`properties.ts:122-130`); I-006 excludes option lists from per-item merge for that reason (its wording says `value`) (09-14, 08 Sync Shapes). `OptionEditor.test.tsx:267-448` (about 180 lines) and `optionOps.test.ts:245-276` keep popups addressed through renames (09-14, INFERRED as a payoff). `group_id` on Status options is required, written, and read by nothing; a hand edit omitting it makes the whole property unadmitted (08-04, writers only). `collapsed_groups` stores bare labels while `hidden_groups` is property-scoped; NexusOS's `Ideas/_pagecollection.json` views 0-1 hold bare labels (plus a Set id in view 0), and `open`/`closed` there match no current option (07-07). Deleting the grouped property clears every collapsed key, structural ones included (07 ledger). A new view seeds `hidden_properties` with every schema id, redundant with the `property_order` allowlist (07-08).

##### Sync Shapes

**Explanation (For Nathan):** When two devices change the same file before syncing, Pommora merges the two versions, and how finely it can merge depends on how the file is laid out. The property list merges well in general, one setting at a time. The weak spots are: a property deleted on one device while edited on the other ends up as a broken, invisible scrap that sits in the file forever (a test currently pins that as intended); two devices creating a property with the same name leaves one hidden with no notice; option lists, assignment lists, and the removed-values stash each merge as one indivisible item; and a page's own front matter isn't merged at all, so two devices setting different properties on one page lose one of the two edits (it survives only in the conflict capture). A Space's settings file is the one property shape that already merges cleanly.

**Evidence:** 08 Sync Shapes. Delete-versus-edit: `mergeKeys` treats a deleted side as empty (`jsonMerge.ts:36-43`) under `{defs: 2}`, producing `{ defs: { P: { name: 'New' } } }`, pinned by `mergePolicy.test.ts:130-136` (it uses a `name` field the schema doesn't have), which `normalizeRegistry` files as `unadmitted` and `mutateRegistry` re-writes forever (08-01, 08 L1). Fold-equal definitions: a registry read hides every later definition whose label or key folds equal to an earlier one's (`propertiesRegistry.ts:28-36`), so two devices each creating "Priority" leave one invisible (01 ledger). `select_options`/`status_groups` merge whole (I-006). Collection `properties` and `property_cache` merge whole (03-02, 08-06). Page frontmatter isn't merged JSON (`mergePolicy.ts:20-21`; `base.ts:57` keeps no page base bytes) (08 Approach D). `_space.json` merges per root key. Journal files are excluded from sync (`exclusion.ts:58`), so crash-recovery records stay per device (04 Approach A).

##### Views Integration and Hot Paths

**Explanation (For Nathan):** Views (tables, cards, boards) filter, sort, and group pages by their property values. Each type's view behavior — which filter operators it offers, how it sorts, how it groups — is decided in about fifteen separate places. On large Nexuses, a few things may be slow: every single value edit re-runs the whole view (every row filtered, sorted, and grouped again), dates are re-parsed from text on every pass, and each cell looks up its property in a list instead of being handed it. None of this has been measured, since no benchmark Nexus is built. One real bug: a filter rule with an unreadable value (for example, letters typed into a Number filter) passes every row, so inside an "Any" group it makes the whole group match everything.

**Evidence:** The Per-Type Branch Map lists about 40 sites (07). `resolveFieldValue` scans `schema.find` before its memo; 23 view-side id lookups and 21 `declaredType(` calls; an optional `contextIds` defaulted in a dozen places (07-01). The shown-text projection is written twice and the copies differ (07-04). Every value write re-runs flatten, filter, sort, and group (07-05, INFERRED cost). Four ways to get a column's resolved style (07-09); three deciders of "operands name whole options" (07-11); `SettingsFrame` derives the schema by hand (07-12); creation seeds copy `assignValue`'s split (07-14); two hide paths (07-16). ##### Crash Recovery and How Big Changes Finish

**Explanation (For Nathan):** Before a change that rewrites many files, Pommora writes a small note in the Nexus's hidden `.nexus` folder saying what it's about to do, so it can finish the job if the app quits partway or some file can't be reached. Today there are exactly two such notes: one shared by every property, and one shared by every Context and Space. Each has room for one change at a time, neither travels between devices, and neither NexusOS nor the test Nexus holds one right now.

Take renaming Priority to Urgency. Pommora writes "Priority is becoming Urgency" into the property note, changes the property list, then rewrites every page from `Priority:` to `Urgency:`. If two pages sit in iCloud undownloaded, the note stays, you see "2 Items weren't updated" with Try Again, and the next open finishes them. The trouble starts if you then rename Status to Stage before those two pages arrive: the property note is already full, so the Status rename runs with no note at all, and a crash halfway leaves some pages saying `Status:` and some `Stage:` with nothing able to finish it. Try Again works four different ways, and removing a property from a Collection or clearing an option offers none.

The revision gives every property, Context, and Space its own entry in one notes file, so Priority's unfinished rename never touches Status's. ##### The Removed-Values Stash

**Explanation (For Nathan):** When you remove a property from one Collection, Pommora takes its values off that Collection's pages, archived pages included, and keeps them in the Collection's settings file, so re-adding the property brings them back. You chose this in July, before sync, and it stays. Archiving a page doesn't disturb it. The trouble is everything around it. A page that later moves to another Collection or is deleted keeps its entry forever, which drifted from your July ruling. A page sitting in the Trash when you re-add the property gets nothing back and keeps its entry, so if it's restored later it never gets the value. Deleting the property everywhere cleans the stash out of every Collection except ones sitting in the Trash, which come back still holding it. A Remove that couldn't read some pages leaves those pages holding a value the Collection no longer uses, and a second Remove does nothing. ##### Undo

**Explanation (For Nathan):** When you change a value, Pommora remembers an undo for it, and today the screen keeps that memory: it notes what it last read of the page just before the change, and undo sends that back. That's close to the file but not exact. A property written bare in the file (just `Status:` with nothing after it) comes back as `Status: null`. For Context tags the screen only remembers the Spaces it recognized, so undoing a change to a tag that names a Space Pommora can't find (an Obsidian typo, say) deletes the unknown names with it. The part of Pommora that writes the file notes exactly what that one property said in the file before the change and hands that note back with its reply; undo puts that exact text back, only for the property you edited, leaving the small tidy-ups to other properties in place. ##### Edge Rules

#### Approaches

These are the larger restructures worth weighing; each says what it removes, what it costs, what it risks, and which decided directions it follows or what it depends on.

##### A · Removal-First Landing

This removes everything that's dead, legacy, or unread before anything else is reshaped, so later work never builds on it.

- **Risk:** low. **Depends on:** nothing.
