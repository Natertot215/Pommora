### Recent Work

#### The Erasure Campaigns (07-29 → 07-30)

Asking why tabs, pins, and favorites were "needlessly spread" found the consolidation mostly already done — tabs, previews, and recents were db rows — but surfaced what was actually rotten: 19 KB of dead Swift-era keys in `state.json` that nothing reads, a pins folder of per-file tombstones engineering *around* the locked most-recent-wins philosophy, and stored paths as the one duplicate identity left, with real repair scaffolding tending it. Titles were never the problem — the layer already resolved those live by ID.

Two campaigns ran back-to-back on that finding. Swift parity came out wholesale — the settings seed, the date shim, the accent and color exchange maps, the legacy view vocabulary, every Swift-citing comment, and the on-disk residue across both real nexuses, with zero migration code shipped. Navigation then collapsed onto one contract with one validation boundary: seven IPC channels became a read and a write, stored tabs and previews dropped their paths and hydrate at restore through the one owner that prunes dead refs, mints paths, and recomputes the history pointer, and the pins folder, `navFavorites.json`, and `navview.json` left both disks by hand. The design's adversarial review flipped recents back to the db row on moving-parts arithmetic; the post-build review caught an ungated banner pointer feeding a file delete and a patch-writer reading through the lenient reader — both closed the same night, and the banner gate now guards every replaced-image delete in the app. → [[Navigation Consolidation — Decision Log]] · [[Navigation]] · [[Architecture]] · `History.md`.

#### The Hardening Campaign & Its Inverse (07-29)

A ten-lens state-of-the-app pass ranked the systemic risks, and three of them got their root-cause fixes rather than patches. Every read-modify-write now goes through one strict primitive under one law — absent is a fact, unreadable is ignorance, and a write may act on a fact, never on ignorance — which closed the class where a transiently-unreadable file got silently replaced by a default. Glyph resolution collapsed to one rule (`entityIcon`: the user's own icon if renderable, else the nexus default, else the seed), and the nexus walk went parallel with a stat-gated per-page cache, so an untouched file costs no read at all.

Then the inverse pass: an audit of guards defending against states that can't occur, traced path-by-path. Around thirty-four lines came out — resurrection seeds for sidecars only deletion could remove, re-validations of invariants established lines earlier, catch-arms on channels that structurally cannot reject — and the audit's own tracing surfaced one real bug worth having. → `History.md`.

#### The HOIST Consolidation (07-29)

Two HOIST markers in the icon picker turned into a design-system pass: the outlined-box border six surfaces hand-rolled became `--border-cell` beside `--border-heading`, the accent-tint active stroke four surfaces restated became `--accent-stroke` (color only — the weights genuinely differ per surface), the picker's hand-rolled focus ring moved onto the house `fieldRing` channel, and the virtualizer's cell size single-sourced out of its silent-drift pair. → [[DesignPM]].

#### One Syntax For Every Pommora-Owned Key (07-28 → 07-29)

Properties keyed values by ULID inside a nested map while Contexts keyed theirs by name at the root — exact mirror images, Contexts paying a rename cascade to buy a readable file, properties paying an unreadable file to buy a free rename. Legibility had already won once when Contexts were designed; this was the other half of that call. A page now carries `<Status>: Complete` at its root and Contexts moved to parentheses, both reading one module that owns the glyphs, the key build and parse, and every refusal message. The glyphs were picked mechanically: neither opens a YAML flow collection, so a key writes plain and unquoted — what Pommora emits matches what you'd type by hand.

Naming the key removed the reason four different decoders existed, and they became one that reads the declared type instead of guessing from bytes; a title is unique nexus-wide because the title *is* the key its values write under. The follow-up sweep caught a group-by still inferring from which array was present rather than what the property declares, and wrote the color spectrum down exactly once — `:root` and the key lists both derive from the one palette. → [[Properties]] · [[Contexts]] · `History.md`.

**Deferred:** definitions into `nexus.db` + SavedViews into `nexus.db` + an inline field-error surface + duplicate property names.

#### Contexts & Spaces + Closing the tierN Era (07-22 → 07-29)

The three-tier taxonomy was the last fixed thing in an otherwise user-defined system, so it became a registry: Contexts are entries in `.nexus/contexts.json` with ordinary minted ULIDs, Spaces live as folders under `.nexus/contexts/<Context>/<Space>/`, and membership is a parenthesized title key at every entity root — validated by registry membership at read, never guessed. Renames cascade under a pending-rename journal that replays on open, and a Space is the second BlockHost, owning its own block document.

With both nexuses on the registry shape, the entire backward-compatibility surface came out rather than staying dormant — the migration, the read-healing, the legacy key modelling, the tier helpers, the `tier` column vocabulary. **A compatibility path is a liability once its last consumer is gone:** it can never again be exercised against real input. The stated consequence: a nexus left at the old shape can no longer be opened. → [[Contexts]].

### Pending Focuses

#### “For Nathan” Pending Boring Work

Architectural cleanups with no user-visible payoff and permanent editing payoff — deliberately separate from the feature backlog. None is broken; each is a shape that taxes every future edit. Each entry keeps its full picture — what it actually is, why it was built that way, and what a change buys — so the reasoning is never lost.

**The Store — One Giant Notebook.** The renderer keeps everything the app currently "knows" — which tab is active, what's selected, the pins, the open preview, the page being edited — in one shared memory object: a single notebook every part of the UI reads from and writes to. The criticism isn't the notebook; it's that all ~1,300 lines of its rules live in one file, so tab logic, preview logic, and navigation logic sit tangled in one place. It got this way honestly: each feature needed to react to the others — closing a tab must refocus another, a nexus switch must wipe previews — and the cheapest way to let features see each other is one room; one room also means one source of truth, which killed a whole class of two-copies bugs. Every individual decision was right; the sum is a file nobody can hold in their head. Splitting it into domain files (tabs, nav, previews, pages) that compose into the same one notebook changes nothing about how the app behaves — it changes how safely anyone can *edit* it: "where do I change tab behavior" gets a one-file answer. Do it right *before* the next store-heavy feature, not as its own ceremony.

**The IPC Bridge — Hand-Copied Phone Lines.** The app is two programs — the window you see, and a background process that owns the files — talking over named channels, like labeled phone lines: "open page," "save tabs," "read navigation." Each line is currently declared *three times by hand* — once where it's answered, once where it's dialed, once in the shared phrasebook of types. Electron gives you raw wires and nothing else, and hand-writing each line was the obvious zero-dependency start; the discipline around it (never throw across the boundary, always a tidy ok/error envelope) is genuinely good. But hand-copying is why seven navigation lines could quietly accumulate, why two "no nexus is open" phrasings coexist, and why the rich error detail flattens to a plain string at ~34 endpoints — each line was written on a different day by a different hand. The change: declare every channel once, in one map, and derive the other two sides automatically. Adding a channel becomes one entry instead of three edits, and the error shape becomes uniform because there's only one place shapes come from. Highest leverage-per-effort on this list — it deletes a drift *category*, not instances. First of these worth a dedicated session, and it absorbs two long-standing Pending items: the `PommoraError.code` flattening at those ~34 tails, and the two coexisting envelope shapes (`mutate`'s structured error vs the bare-string handlers).

**The Tree Reload — Repainting the Whole Wall.** When anything changes — one rename, one reorder — the app re-reads the *entire* nexus from disk and hands the window a complete fresh picture; `stabilize` then compares new to old and keeps unchanged parts literally identical so the UI only repaints what really moved. This is correctness by brute force: if you always rebuild everything from the files, you can never be out of sync with them — the whole religion of a files-canonical app. Incremental updates are where sync bugs live, so they were deliberately deferred, and the parallel walk + cache keep the full re-read fast enough that this stays a good deal today. But it's the future ceiling: at a few hundred pages it's invisible; at several thousand, every mutation paying a full re-read becomes the app's felt lag. The escape path exists in embryo — the optimistic move-patch proves the tree can be surgically edited and merely *confirmed* by the next full read, and the real version arrives with the content index: once a database can answer "what changed," updates become targeted. Not a task — a constraint to hand the Pages-in-DB session, designed with this ceiling explicitly on the table.

**The Four Sibling Indexes — Four People Counting the Same Room.** Several features need fast lookups over the whole nexus — "does this id still exist," "what's this entry's title and icon," "what matches this search," "which pages link where." Each feature builds its *own* lookup table from the same tree, every time the tree refreshes: four walks, four tables, overlapping contents (`ReconcileIndex`, the nav `ResolveIndex`, the search index, and the connections page-index — the last itself rebuilt per tree change by four separate surfaces). Each was born inside the feature that needed it, correctly scoped to exactly its question — good modular instinct, applied four separate times, with nobody sitting above them because until recently there were only two. The change: one shared index registry built once per refresh, each feature's table derived from it. A modest perf win and a real coherence win — today a new feature needing lookups will inevitably write walk number five, because that's the visible pattern to copy; consolidating makes the pattern itself the right thing to copy. Ride it along with whatever next needs a lookup.

**`mutate.ts` — The Counter With Some Clerks and Some Piles.** Every change the window requests funnels through one dispatcher in the file-owning process — a big switch: "rename? do this. set a banner? do this." Some operations are handled by tidy specialist modules in `crud//`; others by long paragraphs of logic written directly inside the switch arm. Same counter, inconsistent staffing. The funnel itself is deliberate and good — one entry point means one place for safety policy (trash rules, the reserved-path guard, cascade ordering); the inconsistency is just archaeology: early ops got modules, later ops got written where the author was already standing. The change is purely organizational — move the inline arms out so every op lives the same way, and "where do I edit the banner logic" stops depending on when banner logic was written. Cheap and mechanical; do it opportunistically as each arm is next touched.

**Sequencing:** the IPC map and the store split are the two worth dedicated sessions, in that order — one deletes a drift category, the other de-risks every future feature. The index registry rides along with whatever next needs a lookup, the mutate cleanup rides along with whatever next touches an arm, and the tree reload isn't a task at all yet — it's a constraint for the Pages-in-DB session queued below.

#### Open Questions

- **Is a Context's folder worth what its rename costs?** A Space's membership isn't stored anywhere — it's inferred from which Context folder the Space sits in, and that folder is named by the Context's title. So renaming a Context is a filesystem operation rather than a data edit: journal, rename the folder, cascade the key through every member file, commit the registry, settle, and replay forward if it crashes. It's the most complex write in the codebase, and all of it exists because the folder name is load-bearing identity. A `context_id` on `_space.json` would let Spaces sit flat and collapse a Context rename to one registry write, with the frontmatter cascade still needed but no folder move and no journal. The counter-argument is the reason it's built this way: `contexts/Projects/Pommora/` tells an agent what it is without opening a single JSON file, and that legibility is a core construct, not a nicety. Parked as a genuine open question — it's a data-model change, never a cleanup, and the journal only stops being worth it if the complexity starts biting.

- **Redundant identity sources.** Anywhere "what this is" resolves from more than one place, or from a copy of somewhere that already holds it. The exemplar surfaced in the property-syntax work: `PropertyValue.kind` is a runtime copy of `def.type`, four of its call sites already read `select || status`, and the picker *constructs* the tag from the very type it is nominally independent of — so a bare status value would have rendered as a select chip with no error anywhere. The same shape covers two decoders for one encoding, a label derived in one place and re-derived in another, and any enum mirrored across a boundary. The sweep for these hasn't run and the suspicion is that more are hiding.

- **The NavPane toolbar dropdown** is still a blank placeholder — what a compact nav dropdown holds versus the fuller NavWindow is an open call before building into it.

### Lessons

- Two-writers-for-one-fact is the defect class the tab and nav work kept breeding — every real bug reduced to it, and the fix was always one writer or a lockstep rule. The navigation consolidation made it structural: one validation boundary, one strip (`toNavRef`), one hydrator owning restore lockstep, one keeper owning the active pointer.
- HMR only goes so far: CSS and React Fast-Refresh work, but CM6 extension code needs ⌘R, `src/main` and preload need a full dev-process restart, a vanilla-extract `*.css.ts` can serve stale (a plain restart heals it, ⌘R never does), and a component's focus-effect / handler / attribute change often gets skipped by Fast-Refresh.
- CDP has two quirks that keep biting: synthetic clicks work on tabs/rows/buttons but never fire PickerMenu items (drive those via `el.click()` in `Runtime.evaluate`), and a non-integer dpr (1.7 on this machine) throws off screenshot clip math — crop the full-frame PNG with PIL instead.
- Where the navigation code lives: `Tabs/` (`tabsModel.ts` pure with its own tests — the hydrator, the pinned derive, `sameTabs`; `warmCache.ts` for the session LRU; every tab-bar visual knob in `tabBar.css`'s `.tab-bar` block); `main/io/navigationFile.ts` is the one persistence owner; `select` is the single nav entry point; the pin toggle shared between list rows and gallery cards is `NavPinButton` in `NavList.tsx`.
- A whole-surface drag handle steals its own children's clicks: the drag engine `setPointerCapture`s on pointerdown, retargeting the derived click to the drag node, so any interactive descendant has to stop pointerdown — a container only on its own empty space, so the title still drags. Also: Zod 4's `z.number()` already rejects Infinity/NaN where Zod 3 didn't, and native Electron menus are OS-level — CDP can't screenshot or drive them, so their pure models get unit-tested and the popup needs a human.
- The Cards renderer lives in `Detail/Views/Cards/` with its pure seams unit-tested (`cardsOrder`, `cardValueInput`, `cardsBand`); the cell/card right-click model is single-sourced in `@shared/cellMenu.ts` + `@shared/cardMenu.ts` + `@shared/pageMenu.ts`; cards flatten via **Group By: None** and order via **Sort By: Location**, gated on `flattenStructural` so neither can touch a table.
- Two rules any future in-app window must respect, both learned the hard way on PreviewPane: **openness drivers stay declared per-window** (a driver declared once at app level leaks into every consumer), and **a FLIP measures from the surface root** via a real ref, never by walking `parentElement`.
- A vanilla-extract `.css.ts` may export only plain values, so a helper that *builds* a declaration sits beside the stylesheet rather than inside it. Neither typecheck nor lint can see the violation — only the plugin rejects it, which makes it a build-time surprise.
- **A defaulted parameter that resolves identity is a silent-failure switch.** Where an argument is the difference between a value and a plausible-looking wrong one, don't give it a fallback — required, the compiler names every caller that can't resolve.
- A bug's visibility and its severity are independent: what changes urgency is how wrong the output *looks*, not how wrong it is.
- **The compiler goes blind exactly where a format change does its damage.** Anywhere a type is erased at an IO seam (`splitFrontmatter` returning loose `Json` is the standing example), the gate has to be a named step, never the typecheck.
- **A `$`-leading token inside shell double quotes is an end-of-line anchor.** Sanity-check any grep gate against a token you know is present before trusting a clean exit — and `\'` doesn't escape inside single quotes either.
- **A mechanical sweep across test files needs its own verification pass.** Dry-run the pattern and read what it would touch before letting it write — one regex nearly rewrote `[[Beta]]` wikilinks; another under-matched a multi-line fixture and failed three steps from its cause.
- **The syntax module is the one place a glyph is written down.** `src/shared/governedKeys.ts` owns the pair, the build and parse, the governed-key predicate, the reserved leading `$` and every refusal string. Changing a sigil is one line there, and the tests derive their fixtures from `wrapKey` so a swap retargets them.
- **Recognizing a key isn't resolving one.** A wrapped key is Pommora's — safe to sweep, safe for Sapphire to hide — but only a registry title match makes it a live value. Resolution runs definition-first: walk the schema, build each key from its name, read that key.
- **Most of the live nexus is Obsidian's frontmatter, and Pommora is right to ignore it.** Around thirty-five pages carry bare `Projects:` / `Topics:` / `Status:` keys Obsidian wrote, so their columns render empty on purpose — the check is whether the key is wrapped, and converting them is a per-page call Nathan owns, never automated. Worth knowing before anyone diagnoses an empty table as broken.
- The context machinery splits cleanly: pure resolution in `src/shared/contexts.ts` + `contextResolve.ts`, the write family in `crud/contextWrite.ts`, the cascade/journal/replay in `crud/contextCascade.ts` + `contextJournal.ts`, and every renderer surface resolving identity through `pipeline/contextIdentity.ts`. Context columns are default-OFF: absence from a view's `property_order` IS hidden, which is why creating a Context can never change an existing view.
