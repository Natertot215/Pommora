### PM-004 — The Write Path: One Lock Per File, and One Instance Over a Nexus

**Dates:** 08-08-2026

#### Summary

The serialization primitive behind every read-modify-write keys on the literal string it is handed, and nothing checks that two callers touching one file hand it the same one. A container's sidecar is rewritten whole by an unusual number of unrelated surfaces — saving a view, reordering views, deleting one, persisting a within-folder order, writing the open-in configuration, assigning or unassigning a property, writing and clearing a Remove cache, and patching the icon or banner. Between them they took three different keys and several took none, so none of them waited for the others. Each reads the file, merges its own change, and writes the whole thing back, which means a writer that read before a sibling's write landed put the file back without it. Dragging a page into a Collection while a view saved could revert either one, with no error on either side.

The key moved into the path module and behind one helper placed beside the sidecar read/write pair, which left every writer of that file queuing on the same string by construction. The banner and icon patches had been assembling the same path by hand through a template literal, a second spelling that would have diverged from the built one on any folder path the two normalized differently; both were routed through the same builder. The four call-site locks keyed on the bare containing folder came out with it, an outer lock under a second name having been the defect rather than a defense.

**The page half** applied the same rule across a path change. A rename or a move is one primitive that relocates the file, and it held no lock while the body write, the property write, and the banner and icon writes all held the page's own path. A save already in flight could therefore pass its existence check, have the rename move the file out from under it, and then write its content back to the path just vacated — recreating it. The result is two files: the renamed page holding the older body, and a ghost under the old title holding the newer one, kept quiet by the watcher's own self-write suppression. The relocate was placed under the source path's key, and the body write's existence check moved inside that key from the IPC handler that had been wrapping it, which left the guarantee with the writer rather than with a caller remembering to apply it. A write arriving after a rename fails not-found against a path that has gone.

**A move stopped reporting failure after it had succeeded.** Relocating a page or a Set is followed by a write of the destination's order, and a failure in that second step had returned a failed Result for the whole operation. The renderer's rule for a failure is to change nothing, so the sidebar kept showing an entity at a location it had already left, and a retry met a name collision. The order write is a preference on top of a change already committed, so it became best-effort, with order falling back to title until the next reorder. An order-only reorder still fails honestly, nothing having moved.

**One instance** closed the outer boundary. Every chain above is module state, so a second process over the same Nexus shared none of it, and its writes raced the first process's with no coordination. A single-instance lock was added: a losing launch exits before it can open a session, and a relaunch raises the window that already exists. Multiple windows remain reachable, one process being able to own many; a second process over one Nexus is what the lock prevents.

The regression tests were confirmed against the unfixed tree before being kept: three of the five went red without the change, and the ghost reproduced exactly, the page folder listing both the renamed file and the resurrected one.

#### Changes Made

- **`main/paths.ts`:** `sidecarPath(absFolder, kind)` — the sidecar's own file path, and the canonical lock key for it. Built here so no call site spells it a second way.
- **`main/sidecarIO.ts`:** `withSidecarLock(absFolder, kind, fn)` runs a sidecar read-modify-write under that path's chain, beside the read/write pair it governs. `readSidecar` and `writeSidecar` resolve through `sidecarPath` too, so the lock key and the path actually written are one expression rather than two that agree.
- **`main/crud/views.ts`, `containerConfig.ts`, `folderEntity.ts`:** `saveView`, `reorderViews`, `deleteView`, `setContainerConfig` and `updateFolderSidecar` each had their read-merge-write wrapped in the shared lock. `updateFolderSidecar` is what within-folder order persistence rides, and it had taken no lock at all.
- **`main/crud/assignment.ts`:** the assign and reorder internals took the lock around their read-merge-write only. The Remove-cache restore was left outside it — it walks and rewrites every member page, long enough that holding the lock across it would stall every sibling.
- **`main/crud/removeProperty.ts`, `deleteProperty.ts`:** the cache-and-unassign write, the cache clear at the end of the restore, and the per-collection purge were each brought under the same lock, having been raw read-merge-writes against the same file. The restore's clear takes the lock for itself rather than inheriting one, the page walk before it running unlocked by design.
- **`main/crud/page.ts`:** `relocatePage` was placed under the source path's key. `updatePageBody` took its own lock across the existence check and the write, in place of depending on the IPC handler to apply one. `updatePageProperty` deliberately does not, and says so: its callers resolve the definition inside the same slot as the write, so taking the lock here would deadlock a span that has to be wider than this function.
- **`main/index.ts`:** gained the single-instance lock and its `second-instance` handler, on which the losing launch exits and the winner's window is restored and focused. The four container-sidecar handlers dropped their folder-keyed locks.
- **`main/mutate.ts`:** the banner, heading-icon and icon arms resolve their config path through `sidecarPath`, and the trailing order write after a page or Set move became best-effort.
- **`main/crud/restoreProperty.ts`:** the value write-home took the page's lock, having been the one `updatePageProperty` call site holding none.
- **`main/crud/writePathRace.test.ts`:** concurrent sidecar writers each survive the others, a value write and a body write on one page both land, and a rename racing its page's body write leaves exactly one file.

#### Issues Resolved

- **A container sidecar's writers were spread across three keys, and several held none:** every one rewrites the file whole, so a read-merge-write racing a sibling silently reverted it. A drag into a Collection during a view save could lose either change with no error.
- **A second spelling of the same path:** the banner and icon patches built the sidecar path by hand rather than through a builder, so their lock key and the sidecar writers' key were the same string only by coincidence.
- **A page relocate took no lock while every other write to that page did:** a body write in flight could recreate the vacated file around its own content, leaving a ghost page holding the newer text beside the renamed one holding the older, hidden from the walk by write-echo suppression.
- **`updatePageBody`'s guarantee lived at its caller:** the existence check and the write sat inside a lock the IPC handler applied, so a second call site would have silently inherited none of it.
- **A successful move reported failure when only its order write failed:** the renderer changes nothing on a failure, so the sidebar kept showing an entity where it no longer was, and retrying met a name collision.
- **A property restore wrote page values with no lock:** `updatePageProperty` takes none of its own, and the restore was calling it bare — so writing a recovered value home could clobber an edit in flight on that page, and be clobbered by one.
- **Nothing stopped a second process opening the same Nexus:** every lock is module state, and the app had no single-instance guard, so two processes over one Nexus had no write coordination at all.
