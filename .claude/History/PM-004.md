### PM-004 — The Write Path: One Lock Per File, and One Instance Over a Nexus

**Dates:** 08-08-2026

#### Summary

The serialization primitive behind every read-modify-write keys on the literal string it is handed, and nothing checks that two callers touching one file hand it the same one. A container's sidecar is rewritten whole by six unrelated surfaces — saving a view, reordering views, deleting one, persisting a within-folder order, writing the open-in configuration, assigning or unassigning a property, purging a Remove cache, and patching the icon or banner. Between them they took three different keys and two took none, so none of them waited for the others. Each reads the file, merges its own change, and writes the whole thing back, which means a writer that read before a sibling's write landed put the file back without it. Dragging a page into a Collection while a view saved could revert either one, with no error on either side.

The key is now built in the path module and taken through one helper beside the sidecar read/write pair, so every writer of that file queues on the same string by construction. The banner and icon patches had been assembling the same path by hand through a template literal, a second spelling that would have diverged from the built one on any folder path the two normalized differently; they now call the same builder. The four call-site locks keyed on the bare containing folder came out, since an outer lock under a second name is the defect rather than a defense.

**The page half** is the same law across a path change. A rename or a move is one primitive that relocates the file, and it held no lock while the body write, the property write, and the banner and icon writes all held the page's own path. A save already in flight could therefore pass its existence check, have the rename move the file out from under it, and then write its content back to the path just vacated — recreating it. The result is two files: the renamed page holding the older body, and a ghost under the old title holding the newer one, kept quiet by the watcher's own self-write suppression. The relocate now runs under the source path's key, and the body write's existence check moved inside that key from the IPC handler that had been wrapping it, so the guarantee belongs to the writer rather than to a caller remembering to apply it. A write that arrives after a rename fails not-found against a path that is gone.

**A move that succeeds no longer reports failure.** Relocating a page or a Set is followed by a write of the destination's order, and a failure in that second step returned a failed Result for the whole operation. The renderer's rule for a failure is to change nothing, so the sidebar kept showing an entity at a location it had already left, and a retry met a name collision. The order write is a preference on top of a change already committed, so it is best-effort — order falls back to title until the next reorder. An order-only reorder still fails honestly, because nothing has moved.

**One instance** closes the outer boundary. Every chain above is module state, so a second process over the same Nexus shares none of it and its writes race the first process's with no coordination whatsoever. The app takes a single-instance lock; a losing launch exits before it can open a session, and a relaunch raises the window that already exists. Multiple windows stay reachable, since one process may own many — what it may not do is become a second process over one Nexus.

The regression tests were confirmed against the unfixed tree before being kept: three of the five go red without the change, and the ghost reproduces exactly, the page folder listing both the renamed file and the resurrected one.

#### Changes Made

- **`main/paths.ts`:** `sidecarPath(absFolder, kind)` — the sidecar's own file path, and the canonical lock key for it. Built here so no call site spells it a second way.
- **`main/sidecarIO.ts`:** `withSidecarLock(absFolder, kind, fn)` runs a sidecar read-modify-write under that path's chain, beside the read/write pair it governs.
- **`main/crud/views.ts`, `containerConfig.ts`, `folderEntity.ts`:** `saveView`, `reorderViews`, `deleteView`, `setContainerConfig` and `updateFolderSidecar` each wrap their read-merge-write in the shared lock. `updateFolderSidecar` is what within-folder order persistence rides, and it had taken no lock at all.
- **`main/crud/assignment.ts`:** the assign and reorder internals take the lock around their read-merge-write only. The Remove-cache restore stays outside it — it rewrites pages rather than the sidecar, and holding the lock across it would stall every sibling.
- **`main/crud/removeProperty.ts`, `deleteProperty.ts`:** the cache-and-unassign write and the per-collection purge take the same lock; both had been raw read-merge-writes against the same file.
- **`main/crud/page.ts`:** `relocatePage` runs under the source path's key. `updatePageBody` holds its own lock across the existence check and the write, rather than depending on the IPC handler to apply one.
- **`main/index.ts`:** the single-instance lock and its `second-instance` handler; the losing launch exits and the winner's window is restored and focused. The four container-sidecar handlers dropped their folder-keyed locks.
- **`main/mutate.ts`:** the banner, heading-icon and icon paths resolve their config path through `sidecarPath`; the trailing order write after a page or Set move is best-effort.
- **`main/crud/sidecarRace.test.ts`:** concurrent sidecar writers each survive the others, and a rename racing its page's body write leaves exactly one file.

#### Issues Resolved

- **A container sidecar had six writers under three keys, two of them none:** every one rewrites the file whole, so a read-merge-write racing a sibling silently reverted it. A drag into a Collection during a view save could lose either change with no error.
- **A second spelling of the same path:** the banner and icon patches built the sidecar path by hand rather than through a builder, so their lock key and the sidecar writers' key were the same string only by coincidence.
- **A page relocate took no lock while every other write to that page did:** a body write in flight could recreate the vacated file around its own content, leaving a ghost page holding the newer text beside the renamed one holding the older, hidden from the walk by write-echo suppression.
- **`updatePageBody`'s guarantee lived at its caller:** the existence check and the write sat inside a lock the IPC handler applied, so a second call site would have silently inherited none of it.
- **A successful move reported failure when only its order write failed:** the renderer changes nothing on a failure, so the sidebar kept showing an entity where it no longer was, and retrying met a name collision.
- **Nothing stopped a second process opening the same Nexus:** every lock is module state, and the app had no single-instance guard, so two processes over one Nexus had no write coordination at all.
